# Apex: 0.4 implementation plan: Entities & assets

**Status: reviewed by the project owner, 2026-10-25; ready for 0.4.1's P0.** No sub-milestone has
started; `version.txt` reads `0.3.10-release`, and the next landed work is 0.4.1. Every decision in the
appendix was put to the owner, and every draft choice was confirmed, along with deferring *Create
Instance from Selection* to 0.5.

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.4: Entities & assets.** MDL rendering (v44–49: skins, bodygroups, non-uniform scale) and
> model-triangle picking (moved from 0.2; plan 0.2 §4), FGD helpers (iconsprite, studio, sphere,
> line, frustum, cylinder, worldtext, catapult…), I/O connection editor with validation and
> autocompletion, `func_instance` rendering, in-context instance preview and collapse, model, sound
> and particle browsers, prefabs, entity report, find & replace, and the Addons panel (mount toggles
> written back to Strata Hammer's addon list, and hints that name the unmounted addon that provides a
> missing asset; plans/addons.md D2, D6).
> **Exit:** a chamber can be fully dressed with props and wired logic.

This document does not supersede [research.md](../research.md) or the roadmap. Where they disagree,
those win, and the 0.4 release lists the amendments they need once 0.4 lands. Three decisions change
what an earlier plan said:

- D3 answers 0.2 D2's reversal check ("model triangle counts at 0.4 making CPU picking too slow to
  refit on edit") by never refitting model triangles: each model's triangle BVH is built once per
  model in model space and shared, so an edit refits only the entity's box. 0.2 D2 (CPU picking)
  stands.
- D10 extends 0.3 D14 ("thumbnails decoded on the CPU, not uploaded to the bindless heap") to models,
  which have no image to decode: model thumbnails are rendered offscreen by the renderer and read
  back, and the panel still draws only CPU images.
- D13 keeps 0.3 D20's tool pie at eight slots by adding **no new tool** in 0.4. 0.3 Bite 16 (a ninth
  tool fails the slot test and forces the "More" decision) stays untriggered.

0.4 also owes answers that earlier plans handed forward:

  corpus test.

- **A render thread "when frame times on the largest maps suffer… check at 0.4 with models"** (0.1

- **The I/O editor** (0.2 §4: "`connections` are preserved, copied and pasted, and listed read-only"):
  D6.
- **Rotating vector-typed keys other than `origin`/`angles`** (`axis`, `lowerleft`, FGD `vecline`;
  0.2 §4, "with the FGD helpers that draw them"): D5.
- **Instances** (0.1 §4, 0.2 §4: contents and collapse): D7–D9.
- **World-space text for `worldtext` and entity names** (0.3 D16 built the glyph atlas "once for
  both"): D5.
- **Model and sound browsers reuse the material index and thumbnail cache** (0.3 §4): D10.

**What 0.4 inherits.**

- **`assets::EntityClass`** (`core/entity_class.hpp`): name, type, bases, `color`, `size` as
  `mins`/`maxs`, `iconSprite`, properties in declaration order, inputs and outputs. `loadEntityClasses`
  copies these from toolpp's `classProperties` and **drops every other class property**, so
  `studio()`, `sphere()`, `line()` and the other helpers are parsed by toolpp and then discarded.
- **SourcePP v2026.9.11**, pinned in `cmake/deps.cmake` with only vpkpp, steampp, vtfpp and toolpp
  enabled. Its tree already contains **mdlpp** (MDL v44–49, VTX v7, VVD; read-only), **kvpp** (KV1,
  binary KV1, and DMX read, which PCF particle files use) and **sndpp** (WAV, XWV).
- **The render mirror's entity path** (`render/render_mirror.cpp`): every point entity becomes a
  coloured box (FGD `color`, `size`) or an icon sprite; brush entities draw their solids. Boxes are
  axis-aligned and ignore `angles`. The whole entity buffer is rebuilt when any entity changes.
- **`editor::PickIndex`** with an `EntityBoundsProvider` keyed by classname, so every entity of a
  class has the same local box.
- **`assets::MaterialCache`** (async VMT/VTF, LRU, placeholder), **`TextureHeap`** (4,096 bindless
  slots), **`MaterialIndex`** and **`ThumbnailCache`** (0.3 D14: worker-built snapshot, 64 MiB CPU
  image budget), `Vfs::walk`, `Vfs::provider(path)` (which addon serves a path; 0.3 D19).
- **The inspector** (0.2 D13): typed rows in FGD order, `target_*` autocompletion from the map's
  `targetname`s, an "other keys" section, raw mode, and a read-only list of `connections`.
- **The Entity tool** (0.2.8, behind `editor::Tool` since 0.3 D1): places one point entity of the
  chosen class on a surface.
- **The clipboard** (0.2 D12): VMF text fragments, fresh IDs on paste, group and visgroup membership
  carried, `connections` carried verbatim. Prefabs and collapse can reuse its paste path.
- **World overlays and labels** (0.3 D16): depth-tested lines, handles and triangles, and a glyph atlas
  rasterised by `ui/` and drawn by `render/`.
- **The offscreen render target** (0.1.9), used today by golden-image tests.
- **`core/kv3`** with value spans, the addon mount layer, and the Addons menu that flips `mounted` in
  place (0.3 D19).
- **Area roles and workspaces** (0.2.12): every new panel is a role.
- **`Document::viewsettings().instanceVisibility()`**: `nInstanceVisibility` is read and preserved, and
  nothing acts on it.
- **The release harness**: headless corpus replays, the srctools cross-check,
  `tools/hammer_wine_check.py`, `tools/vbsp_equivalence.py`, `tools/chamber_compile_check.py`, and the
  0.3 scripted chamber (`tests/editor/chamber_test.cpp`), which 0.4's exit dresses (D16).

**What 0.4 does not have.**

- **No model loader.** Nothing links mdlpp. Worse, mdlpp's own `StudioModel::processModelData`
  **draws every bodygroup at once**: it walks every model of every body part and appends all of
  them, so a prop with bodygroups renders every variant on top of each other. It also builds
  `std::vector<uint16_t>` indices from `meshVertexID + mesh.verticesOffset + model.verticesOffset`,
  which **wraps silently** once a model's vertex offset passes 65,535, and its tristrip loop computes
  `strip.indices.size() - 2` on an unsigned size. Skins (`mdl.skins`, the texture remap table) are
  parsed and never applied. D1, and 0.4.1 P0 tests 1–3.
- **No helpers.** Classes with `studioprop()` draw a box; `sphere()`, `line()`, `frustum()` and the
  rest draw nothing. D5.
- **Entity boxes ignore `angles`.** Invisible today because a box is symmetric about its origin in
  most FGDs. A model makes it visible at once: an `angles "0 90 0"` prop would render rotated in a box
  that is not. D4.
- **One bounds per class.** `EntityBoundsProvider` takes a classname, but a `prop_static`'s bounds come
  from its model, skin-independent but model-dependent. D3.
- **No instance contents.** `func_instance` draws as its FGD box. No VMF other than the open one is
  ever loaded. D7.
- **One document per process.** Opening an instance for editing has nowhere to go. D8.
- **No editor model for connections.** The read-only list shows raw values. D6.
- **No placement of anything but an entity class.** D12, D13.
- **No audio.** Qt Multimedia is not a dependency. D10.
- **No way to answer "which addon would provide this missing file".** `Vfs::provider` knows only
  mounted addons; nothing indexes unmounted ones. D15.

## 1. Decisions

Each records what would reverse it.

### D1: Models are baked by Apex from mdlpp's parsed structures; `processModelData` is never called

`assets::ModelCache` reads the `.mdl`, `.vvd` and `.dx90.vtx` through `Vfs` on a worker (the
`MaterialCache` pattern), opens them with `mdlpp::StudioModel::open`, and then bakes its own
`assets::ModelData` from `mdl`, `vvd` and `vtx`:

- **LOD 0 only**, with VVD fixups applied for LOD 0;
- **`uint32_t` indices**, so no offset wraps;
- **one submesh per (body part, model, mesh)**, recording which body part and which choice it belongs
  to, so a bodygroup value selects ranges at draw time instead of rebaking;
- **the skin table** (`mdl.skins`) kept as data, and each submesh's material resolved per skin through
  `materialDirectories` (cdmaterials) at draw time;
- model-space bounds per body part choice, for D3 and D4.

The bake catches every exception mdlpp throws (it uses `.at()` throughout) and turns a model that
fails into an error model (D2), with the reason logged once per path.

The alternative a reasonable person picks is `processModelData` as shipped: about 120 lines Apex
doesn't write. It's turned down because it merges every bodygroup choice into one mesh, which the
roadmap's "bodygroups" rules out, and because its `uint16_t` indices fail on large models without an
error. Fixing it upstream is welcome, but 0.4 can't wait on a release, and the bake is small.

Accepted cost: Apex owns the VTX strip walk, including the winding flip mdlpp already gets right
(copied by behaviour, tested against `processModelData` on a model with one body part).

*What would reverse it:* the 0.4.1 corpus test showing mdlpp's parser itself failing on a meaningful
share of P2CE models (not the bake). Then Apex needs its own MDL reader, and 0.4.1 grows by that.

**P0 result (0.4.1, 2026-10-25):** the mounted P2CE corpus lists 2,682 `.mdl` files (the 2,204 above was
an earlier, narrower count). 2,673 bake; **0 fail in mdlpp's parser or the bake**. The other 9 are
animation-only MDLs with no `.vtx` or `.vvd` at all (`ballbot_animations`, `eggbot_animations`,
`headless_player_animations`, `player_animations`, `headless_s8player_animations`,
`arm64x64_interior_animation`, `info_character_animation`, `glados_wheatley_boss_animation`,
`personality_sphere_animation`); they carry no geometry, and in `ModelCache` they become error models
with the reason "Asset missing", which is correct. So the reversal condition did not fire.
The four P0 tests (per-choice bodygroup bake, index past 65,535, short strips, rotated entity box)
pass against the Apex bake. Two defects in `processModelData` beyond the ones above: the model
`vertexindex` is a *byte* offset into 48-byte vertices (mdlpp treats it as a count, so the second and
later choices of a body part index the wrong vertices), and the VVD fixup LOD test must take every fixup
with `LOD >= 0` for LOD 0. The equality test against `processModelData` therefore covers single-choice
models only (300 of them, in canonical order).
**Deviation:** `ModelCache::request` reads the three files through `Vfs` on the owner thread and only the
parse and bake run on a worker (the `Vfs` is not safe to read from workers, as in `MaterialCache`).

### D2: One GPU mesh per model, shared and instanced; the draw picks skin and bodygroup per entity

The render mirror keeps one vertex and index buffer per loaded `ModelData` and draws each prop as an
instance with: its transform (D4), skin index, and a body mask (one choice per body part). Draws are
grouped by (model, skin, material) so the 2,178 `prop_static` of a large map cost one draw per
distinct mesh, not per entity. Materials go through the existing bindless path: `VertexLitGeneric` and
`UnlitGeneric` use the textured pipeline with vertex normals for the flat shade; translucency and alpha
test follow the existing per-layer handling.

While a model loads, the entity draws its FGD box as today. A model that is missing or fails to load
draws Apex's error model (a small checker cube with the entity's colour), never nothing, so a missing
asset is visible and selectable. Model loading is mount-aware: an addon toggle or Reload invalidates
`ModelCache` with `MaterialCache` (0.3 D19).

The alternative is to bake each entity's mesh with its skin and bodygroup applied: simpler shaders,
one draw per entity. It's turned down because 2,178 copies of a few dozen meshes cost memory and
upload time for nothing, and a skin change would need a rebake.

*What would reverse it:* a measurement showing the grouped draw path slower than per-entity draws on
the release map, which is unlikely at these counts.

### D3: Model-triangle picking uses one model-space BVH per model, shared; the entity BVH leaf is the model's oriented box

`PickIndex` keeps its entity leaves, but a leaf for an entity with a loaded model is the model's
bounds transformed by the entity (D4), not the FGD box. A ray that hits the leaf is transformed into
model space and tested against the model's triangle BVH, built once when the model loads (on the
worker, with `geometry/bvh`), and shared by every entity using it. Only triangles of the entity's
selected bodygroup choices count. The hit point and normal come back in world space in double
precision, so surface placement on props works like placement on brushes (0.2 D9).

`EntityBoundsProvider` changes from "bounds for a classname" to "bounds for an entity", so a prop's
pick volume follows its model.

The alternative is to keep picking props by their box (0.2's stand-in). It's turned down because the
roadmap moved model-triangle picking here, and selecting a railing through the gap in it, or placing a
cube on a prop's top, needs triangles. A GPU ID buffer is turned down for 0.2 D2's reasons, which still
hold: headless tool tests and exact double-precision hit points.

*What would reverse it:* the P0 measurement of the largest P2CE model's BVH build exceeding a frame
budget on a worker in a way that delays picking noticeably, or pick latency on the release map
exceeding 1 ms. Then the triangle test moves behind the same `pick()` interface to a GPU path.

**P0 result (0.4.1):** the largest P2CE model is `models/stars/allstars.mdl`, 187,676 vertices and
93,834 triangles. `geometry::Bvh::build` over its triangles takes **64 ms** on a release build (4.1 s
under ASan) and is built once per model on a worker, so it is far from a frame-budget problem. The
whole corpus sweep (open and bake 2,682 models on four workers) takes 0.65 s on release. The pick-latency
half of the reversal condition is measured in 0.4.2.

### D4: One function turns an entity's keys into its model transform; skin and body come from keys after instance fixups

`editor::entityTransform(entity)` (pure, `geometry/` math over keys) returns the world transform from:

- `origin`;
- `angles` as Source pitch, yaw, roll (yaw about Z, then pitch about Y, then roll about X), checked
  against srctools' `Angle` matrices in a test;
- scale: `modelscale` or `uniformscale` (whichever the class declares; FGD defaults otherwise), and
  **Strata's non-uniform scale key, whatever 0.4.1's probe finds** (below).

Skin is `skin`; bodygroups are `body` (the packed value) or, where present, per-group keys the probe
finds. Every consumer (mirror, pick index, helpers, instance contents, model thumbnails) calls the same
function, and entity boxes rotate with `angles` from now on.

**Non-uniform scale.** The roadmap promises it, and BSP v25's static prop lump v13 stores a scale
vector (research §1), but `p2ce.fgd` declares no vector scale key, and the corpus has none. 0.4.1's P0
asks Strata Hammer how it writes one (its prop dialog, or a hand-edited key it keeps). If Hammer writes
a key, D4 reads it. If it doesn't, 0.4 renders uniform scale only, and the roadmap's 0.4 text is
amended to say so.

**Probe result (2026-10-25, [hammer_0_4_1.md](probe-results/hammer_0_4_1.md)):** `hammer_dll.dll` has
`modelscale`, `uniformscale` and `scalesettings` and no vector scale key, and `vbsp.exe` has only
`uniformscale`. So 0.4 renders uniform scale only (`uniformscale` on `prop_static`, `modelscale` on dynamic
props), and the roadmap's 0.4 text says so.

The alternative is per-consumer transforms (the mirror reads angles one way, picking another).
It's turned down because that's how the box/model mismatch above happens.

*What would reverse it:* the probe showing Hammer stores non-uniform scale somewhere other than an
entity key (a sidecar, a compile option). Then it's out of scope until 0.5's compile profiles.

**As built (0.4.1):** the function is `document::entityPose(const kv1::Node&)` plus
`document::entityTransform(const EntityPose&)`, in `src/document/entity_transform.hpp`, not
`editor::`: `render` may not depend on `editor`, and both the pick index and the mirror need it. The
basis columns are forward, **left** (minus the right vector `angleVectors` returns) and up; using right
gives a reflection (determinant -1), which the first draft of the test had encoded. The srctools grid
test (`tools/gen_angle_fixture.py`, 3,377 cases, `tests/fixtures/entity_angles_srctools.txt`) pins it.
Scale is `uniformscale` for `prop_static` and `modelscale` for other classes, falling back to the other
key, with non-positive and non-finite values giving 1. Entity boxes use origin and basis only (the FGD
`size` is in the entity's frame, and is not scaled).

### D5: FGD helpers become typed data in `EntityClass`; 0.4 draws a defined set, and vector keys rotate with their entity

`loadEntityClasses` copies every class-header property it doesn't already interpret into
`EntityClass::helpers`, a list of `{name, arguments}` in declaration order, with the arguments split
but uninterpreted. `assets::` gains a small parser per helper kind into typed values (`Sphere{key,
colour}`, `Line{colour, startKey, startValue, endKey, endValue}`, …), and the mirror and overlay code
draw them.

**Drawn in 0.4:** `studio`/`studioprop`/`lightprop` (the model, D2); `iconsprite`/`sprite`; `size`,
`bbox`, `wirebox`; `sphere` (radius from a key, drawn when selected, Hammer's behaviour); `line` (to
entities matched by name, drawn when either end is selected); `frustum`, `cylinder`, `lightcone` (as
outlines, no light); `worldtext` (D16's labels, in world space, rotated with the entity);
`catapult` (the ballistic arc from `trigger_catapult`'s launch target or direction and speed, under
default gravity); `orientedwidthheight(half)`, `quadbounds`, `sweptplayerhull`; `keyframe`/`animator`
(rope and path chains as polylines); `sidelist` (highlights the listed faces by `SideId`, which 0.3
D2–D3 keep stable); `instance` (D7). **Entity names** draw as labels over point entities, off by
default, with a toggle in the viewport header (Hammer's "show entity names").

**Not drawn, listed once in the log:** `light`, `clusteredlight` (lighting preview is 0.6);
`decal`, `overlay`, `overlay_transition` (0.8, with overlays); anything unknown.

**Vector keys.** Keys whose FGD type is `vecline`, `axis` or `lowerleft`-style vectors transform with
the entity under 0.2's gizmos and modal transforms: `vecline` as a point (rotated and translated),
`axis` as two points. This pays 0.2 §4's debt.

`line()` helpers need "entities named X", so `editor/` gains a `NameIndex` (targetname → nodes),
updated from ChangeSets, shared with D6's validation and autocompletion. The mirror's entity buffer
stops being rebuilt wholesale on every entity change: helpers and boxes are updated per entity.

The alternative is the roadmap's named set only (iconsprite, studio, sphere, line, frustum, cylinder,
worldtext, catapult). It's turned down because the corpus count puts `lightcone`, `wirebox`,
`keyframe`/`animator` and `sidelist` in use, and each is a few lines once the typed list exists.

*What would reverse it:* toolpp failing to keep helper arguments intact (quoted strings with commas,
nested parentheses). Then the adapter parses the class header from the FGD text, as it already does for
property order.

### D6: The I/O editor is an *Outputs* and *Inputs* pair in the inspector, over an editor model that keeps every unedited connection byte-identical

`editor::ConnectionModel` parses each `connections` value into target, input, parameter, delay and
times-to-fire, **recording the separator** (ESC or comma; the corpus has both) and the exact text, and
writes a connection back only when a field of it changed, with the separator it had. New connections
use ESC, as Strata Hammer writes. Duplicate output names stay a multimap in file order, and editing
one never reorders the others.

**Outputs tab** (Hammer's): rows of output, target, input, parameter, delay, only once; add, delete,
copy and paste rows; multi-selection shows connections common to all selected entities, as Hammer does.
**Inputs tab**: read-only, the connections in other entities that target this one, with a jump to the
source.

**Autocompletion:** outputs from the source's FGD class; targets from `NameIndex` plus the specials
(`!activator`, `!caller`, `!self`, `!player`, `!picker`) and `*` wildcards; inputs from the FGD classes
of every entity the target matches; parameters by the input's FGD type (choices for `bool`, a target
picker for `target_destination`).

**Validation** marks, never refuses: an unknown output, a target that matches nothing, an input no
matched class declares, a parameter of the wrong type. Instance-aware: a target naming a
`func_instance` with an `instance:<name>;<input>` input is checked against the instance's file (D7):
`<name>` is the targetname of any entity in the template and `<input>` must be an input of that
entity's class (outputs likewise, `instance:<name>;<output>` on the source side); it is not the name of a
`func_instance_io_proxy`. A connection inside an instance file (one containing a proxy) to a name the
parent instance provides is not flagged. The corpus test counts invalid connections and the count goes in this plan;
every flagged one is reviewed before the count is accepted as the baseline.

**Renaming a `targetname`** offers to update the connections and `line()`-style keys that name it
(one transaction, listing what changes), default on. Hammer doesn't do this, and silently broken logic
after a rename is the commonest wiring mistake.

The alternative is a node graph (outputs as wires between entities). It's turned down for 0.4: it is
a second editor for the same data, and the inspector tab is what Hammer users expect. A graph view can
come later over the same `ConnectionModel`.

*What would reverse it:* users renaming to break links on purpose often enough that the default-on
prompt gets in the way. Then the default flips to off; the prompt stays.

### D7: Instance contents are drawn in place from shared read-only templates; they are never part of the document

`editor::InstanceTemplates` loads each referenced instance VMF once into an immutable
`document::Document` (the VMF codec, no history), keyed by resolved path, and shares it between every
`func_instance` that names it. The mirror draws the template's solids and entities transformed by the
`func_instance`'s origin and angles (D4), after applying its fixups (`replaceNN` keys, `$`-variable
substitution into keyvalues and materials) to the keys that affect drawing: model, skin, body,
material on faces, and helper keys. Nested instances recurse with cycle detection and a depth limit of
8 (the corpus nests two deep).

**Path resolution**, from the P0 probe (2026-10-25, [hammer_0_4_1.md](probe-results/hammer_0_4_1.md)),
which traced Strata Hammer's file opens. Hammer tries, in order, and the first root that holds the file wins:
(1) the referring map's own folder, (2) the nearest ancestor folder of the map named `maps`, if there is one,
(3) `<install>/content/p2ce/maps`. A name with subfolders (`instances/foo.vmf`) or `..` is appended to each
root unchanged. Hammer never tried `sdk_content/maps` or an `instances` folder unless the map itself sat
under it, so Apex does the same: the roots come from the referring map's path, not from a fixed
source root. (A corpus map lives in `sdk_content/maps`, so root 1 or 2 finds its `instances/…` files.)
The profile owns root 3. A file that doesn't resolve keeps today's box plus a label with the filename,
and a problem line.

**Instance contents are not selectable objects.** A pick inside them returns the `func_instance`.
`nInstanceVisibility` (Hammer's View → Instances: hidden, tinted, normal) is honoured and toggled from
the viewport header, and stays a per-file setting written where Hammer writes it.

**Hot reload.** `ui/` watches every loaded template file and reloads it when it changes on disk, so an
instance edited in another window (D8) updates the parent without reopening.

The alternative is to load instance contents into the parent document as hidden, locked nodes:
picking, rendering and the outliner would come free. It's turned down because then every save,
undo, copy and ID allocation has to know about nodes that must never be written, and one leak writes
the instance's contents into the parent map. Keeping templates outside the document makes that
impossible by construction (Bite 4).

*What would reverse it:* in-place editing of instance contents (D8's alternative) being wanted in
0.4. That needs instance nodes in the document, and this decision with it.

### D8: "Edit instance" opens the instance file in a second Apex window in a new process

The `func_instance`'s context menu and inspector get *Open Instance*, which starts another `apex`
process on the resolved file. Saving there updates the parent through D7's hot reload. Cross-map copy
and paste already work between processes through the clipboard (0.2 D12).

The alternative a reasonable person picks is in-context editing (Source 2 Hammer's model, and what
"in-context instance preview" might be read as): enter the instance, edit its contents in place in the
parent's frame, save back to the instance file. It's turned down for 0.4 because Apex has one
document per process and one undo history; in-context editing needs a second document in the session,
two histories and transform-aware tools on it. That is a larger change than the rest of the instance
work together. The second alternative, multiple documents in one process (tabs), is the same change
without the in-context part.

The roadmap's "in-context instance preview" is read as D7: the instance is shown, fixed up, in the
parent's frame.

*What would reverse it:* the second-window loop proving too slow in use (the owner's manual dressing,
D16). Then in-place editing is planned for a later milestone, and D7's reversal applies with it.

### D9: Collapse produces what VBSP's instance merge produces, checked against srctools and vbsp

*Collapse Instance* (Hammer's Instancing → Collapse) replaces a selected `func_instance` with its
contents, fixed up exactly as the compiler would: `fixup_style` name prefixing or postfixing (with
`@`-names and `!`-names left alone), `replaceNN` substitution, `func_instance_io_proxy` connections
rewritten into direct connections, `func_instance_parms` removed, and solids and entities transformed.
It's one undoable transaction that allocates fresh solid, side and entity IDs (the clipboard's paste
path), keeps the `func_instance`'s visgroups and groups on what it creates, and collapses nested
instances recursively. *Collapse all* does every instance in the map.

The rules are written in `document/instance_collapse.cpp` (pure), with srctools' instancing
(`srctools.instancing`, MIT) as the reference for behaviour, not code. Two oracles check it: every
corpus map collapsed by Apex equals the same map collapsed by srctools, modulo IDs and number
formatting; and on the release chamber, vbsp's compiled entity lump equals the lump vbsp produces from
Apex's collapsed map.

The alternative is collapse as "paste the instance's contents at its transform" with only name
prefixing. Simpler, and enough for brushes. It's turned down because logic that works in the compiled
map and breaks after a collapse is worse than no collapse: I/O proxies and `$`-variables are where it
breaks.

*What would reverse it:* srctools and vbsp disagreeing on a corpus map. Then vbsp is the truth, and the
srctools oracle becomes a cross-check with an exceptions list.

### D10: Model, Sound and Particle browsers are area roles over one generalised asset index; model thumbnails are rendered offscreen and read back

**Index.** `MaterialIndex` generalises to `assets::AssetIndex<Kind>`, each kind a walk, a per-file
reader and a snapshot, built on a worker at profile load and on mount change (0.3 D14):

- **Models**: `models/**/*.mdl`; per entry the path, the header's flags (static prop or not), body part
  and skin counts, bounds, and the providing addon (`Vfs::provider`). The header read is cheap (no
  VVD/VTX).
- **Sounds**: raw files under `sound/` (`.wav`, `.mp3`) and soundscript entries from
  `scripts/game_sounds_manifest.txt` (KV1, already parsable), with each entry's wave list.
- **Particles**: system names from `particles/particles_manifest.txt` and the element names inside each
  listed `.pcf`, read with kvpp's DMX reader. P0 confirms kvpp reads P2CE's binary PCFs.

**Panels** follow the Materials panel: filter, a thumbnail or list view, "used in this map", recents, and
a pick mode for the inspector's browse buttons (`studio`, `sound`, and `particlesystem`-typed keys),
which 0.4 enables. Clicking a model sets it as the Entity tool's placement item (D13), and dragging one
onto a surface places a `prop_static` there.

**Model thumbnails** are rendered by `render/` into the offscreen target (one model, a fixed
three-quarter camera fitted to its bounds, textured from the model's own skin-0 materials with a flat
tint where a material is missing, skin 0, default bodygroups), read back to
RGBA, and stored in the same `ThumbnailCache`, under the same 64 MiB budget, on disk nowhere. Rendering
happens on the main thread under a tick budget like 0.3 D12's: as many thumbnails per frame tick as fit
in 8 ms (at least one), and none while a viewport interaction is in progress. The panel draws only CPU images, as 0.3 D14 requires.
Thumbnails use a small fixed range of bindless slots (64) that the thumbnail renderer recycles, so
browsing never competes with the map's textures.

**Sound preview** plays through **Qt Multimedia** (`QMediaPlayer` for files, LGPL, linked
dynamically): play, stop, and for a soundscript, cycle its waves. This adds a Qt module to the build,
the Windows package and `THIRD_PARTY.md`, and Qt Multimedia's FFmpeg backend on Windows. P0 confirms
the module is packaged on the reference host and in the Windows VM.

**Particles** are listed by name only. Particle rendering (Hammer++'s preview) is a renderer feature of
its own and is not in 0.4.

The alternative for thumbnails is a list without pictures for models. Cheap and honest. It's turned
down because a model browser without thumbnails is a file dialog, and the offscreen target already
exists. The alternative for sound is no playback (names only), which drops a dependency; it's turned
down because choosing a sound by name alone is what users complain about in Hammer.

*What would reverse it:* Qt Multimedia failing to package on Windows or pulling in a licence 0.1 D4
forbids. 0.4.1 found neither on Windows (above); only the Linux package's FFmpeg is open. Decoding with sndpp and playing through `QAudioSink` doesn't avoid it, because `QAudioSink`
is Qt Multimedia too, so the fallback is no playback.

### D11: Missing assets are reported in one place, by asset kind, with the addon that would provide them

`editor::AssetReport` walks the document and lists every referenced asset that `Vfs` can't find: face
materials, entity `model` and `studio` keys, `sound` keys and soundscript names, particle system names,
and instance files. Each entry records the referencing objects and, if an unmounted addon contains the
path (D15's index), that addon. It is computed on demand and on mount change, never stored in the VMF
(addons.md D7). The entity report (D14) shows it, the error model's and error texture's tooltip name
the addon, and the Addons panel offers to mount it.

The alternative is per-feature reporting (the material browser shows missing materials, the model
browser missing models). It's turned down because "why is this map broken" should be one list, and
D15's hints need one place to attach to.

*What would reverse it:* nothing foreseeable; this is a structural choice.

### D12: Prefabs are plain VMF files in Strata Hammer's `hammer/prefabs` folder, created from the selection and placed through the paste path

*Create Prefab from Selection* writes the selection as a standalone VMF (the clipboard's fragment
writer, wrapped as a full map with a `world`, so Hammer can open it) into a prefab folder, with a
name and an optional subfolder as category. The **Prefabs** list is a section of the Models browser's
role (a tab), with thumbnails rendered like models but of the prefab's solids and entities. Placing one
uses the clipboard's paste path: fresh IDs, groups kept (a prefab of several objects is pasted as one
group), placed on the surface under the cursor by its bounds' bottom centre, like an entity.

The folder is the profile's `hammer/prefabs` by default, so prefabs are shared with Strata Hammer,
plus an optional user folder in Preferences. 0.4.1's P0 checks what Strata Hammer reads from
`hammer/prefabs` (VMF files, Hammer's old `.ol` libraries, or nothing) and whether it shows Apex's
prefabs.

**Probe result (2026-10-25, [hammer_0_4_1.md](probe-results/hammer_0_4_1.md)):** at startup Hammer
enumerates `hammer/prefabs\*.vmf` and its subfolders and watches the folder for changes; its binary
has VMF prefab classes and no RMF one. So the format is VMF and the folder is the one `PrefabDir` names.
Not checked: that a file Apex wrote then appears in Hammer's prefab list (the install's folder is
empty, and the probe was a file trace, not a UI session).

The alternative is Apex's own prefab format (JSON with parameters, or a library file). It's turned down
because a VMF is already what Apex writes losslessly, Hammer can open it, and parameters are what
instances are for.

*What would reverse it:* the probe showing Strata Hammer uses a different format in that folder. Then
Apex's prefabs move to their own folder, so Hammer's isn't polluted.

### D13: 0.4 adds no tool; the Entity tool places a *placement item*: an entity class, a model, or a prefab

The Entity tool gains a placement item, set from the class picker (as today), the Models browser (a
`prop_static` with that model; the class is a setting, `prop_static` by default), or the Prefabs list.
Placement keeps 0.2.8's behaviour: on the surface under the cursor, aligned to its normal if the
setting is on, snapped. A model or prefab item shows a ghost of itself while hovering (0.3 D12's
preview), so the user sees what lands.

The alternative is a new Prefab or Model tool. It's turned down because the pie has exactly eight
slots (0.3 D20) and a ninth tool forces the "More" level that 0.3 deliberately postponed (0.3 Bite 16),
and because "put a thing on a surface" is one gesture whatever the thing is.

*What would reverse it:* a 0.4 feature that genuinely needs its own tool (a sprinkle tool, a path
editor). None is in scope.

### D14: The entity report and find & replace are one *Find* area role with two modes

**Report mode** (Hammer's Map → Entity Report): a filterable table of entities (class, name, key
contains, visgroup, inside selection, brush or point), selecting and framing what's chosen. It has a
**Problems** view: D11's missing assets, D6's invalid connections, and entities whose class the FGD
doesn't know, and an **Addons this map uses** view (addons.md D7) from `Vfs::provider`.

**Replace mode**:
- *keyvalues*: find text in keys and values (with whole-word, case and `*`), optionally in connection
  fields, limited to the report's current filter; preview every change; apply as one transaction;
- *materials* (Hammer's Replace Textures): replace one material with another on faces (whole name or
  substring, in selection or the whole map), with "replace in `material`-typed keys too" for entity keys
  like `material` and `texture`. Preview and one transaction.

The alternative is Hammer's three dialogs (Entity Report, Find Entities, Replace Textures). It's turned
down because they search the same entities and keys with different filters, and one role keeps the
filter between them.

*What would reverse it:* none expected; the split is presentation.

### D15: The Addons panel is addons.md D6 as designed; unmounted addons are indexed by VPK directory, and the followed list is watched

The **Addons** role: mounted checkbox, thumbnail from `.assets`, name, authors, type, source (Local or
Workshop), Workshop ID, tags; a filter; Reload. Warnings for duplicate IDs (a Workshop item and its
local copy) and unresolved paths. Toggling uses the 0.3.7 write path (flip `mounted` in place, byte for
byte), rebuilds the Vfs off the main thread, and invalidates materials, models, the indexes and D11's
report. The 0.3 Addons menu stays as the quick path.

**Unmounted-addon index:** for every addon in the list that isn't mounted, its VPK directory trees
and loose file lists are read once (cheap: no file contents) into a path → addon map, rebuilt when the
list changes. D11 asks it for every missing path.

**Watching:** `ui/` watches the followed `addonlist.kv3` and reloads on change, debounced, so a toggle in
Strata Hammer or the game shows in Apex. Addons P3 (does Hammer rewrite the whole file, and does it pick
up an external edit) is 0.4.1's probe; if Hammer rewrites the file from memory on exit, the panel warns
that Hammer, while running, will overwrite Apex's toggles.

The alternative is to keep the 0.3 menu as the only UI. It's turned down because the hints need a
place to act from, and the menu can't show warnings or thumbnails.

*What would reverse it:* P3 showing Hammer rewrites the list on every toggle and on exit from its own
memory. Then write-back while Hammer runs is unsafe, and the panel refuses to toggle while a Hammer
process holds the list (detected by the lock or the process).

**P3 result (0.4.1, run 2026-10-25 under Wine with `WINEDEBUG=+file`, private Xvfb, no build running; the
live `hammer/addons` and `hammer/cfg` files were backed up first and hash-restored after, all 9 match):**
two sessions with the control map, an external edit of `addonlist.kv3` (`p2ce_player_blood` to
`mounted = true`, in place) 14 s after the main window appeared, then 30 s idle.

- **Hammer rewrites the whole list, but only at startup.** It reads `addonlist.kv3` twice, then reopens it
  `GENERIC_WRITE` with `CREATE_ALWAYS` (a full rewrite from memory, no in-place edit). The bytes it wrote
  were identical to the file it read (CRLF, tabs and the trailing space after `vpks =` included). P2 saw
  the same startup rewrite append local `p2ce/addons/*` folders as `mounted = false`, so a list that already
  names them (as this one did) round-trips unchanged and one that does not gains them.
- **Hammer does not watch the file.** After the external edit there was no open, read or stat of
  `addonlist.kv3` for the rest of the session (about 75 s in run A, 30 s in run B), and the edit was still in
  the file afterwards. It reads the list at startup only; a toggle made while it runs takes effect on the
  next Hammer start, not before.
- **Hammer does not write the list on exit.** A graceful close (`taskkill` WM_CLOSE) wrote `gameconfig.txt`,
  `hammer.vdf` and `HammerConfig.vdf` and left `addonlist.kv3` as the external edit. Window placement and
  MRU positions in `HammerConfig.vdf` changed, so those three files are Hammer's and Apex must not follow
  or diff them.
- **Hammer's own addon toggle was not driven.** `hammer.exe` holds no addon strings beyond the word "addon" (the
  list code is in shared libraries) and I did not look for a toggle in its menus, so the "toggle in Hammer,
  then diff" half was not exercised. Alt+F4 under bare Xvfb (no window manager) did not
  close Hammer; the graceful close above is the exit evidence.

**Decision (replaces "built for the cautious outcome"):** the reversal condition above did not occur. A running
Hammer does not overwrite Apex's toggles, so the panel toggles while Hammer runs and does not refuse. It
shows one fixed notice, "Hammer reads the addon list when it starts; restart Hammer for a change to apply",
and nothing about overwriting. Watching still reloads Apex when the file changes (a toggle in the game or a
second Apex), debounced. Writes keep Hammer's byte format (CRLF, tabs). What is still unmeasured: Hammer's own toggle path, if the build has one, and a
Hammer that is killed rather than closed.

     |
  render/     + model meshes, grouped instanced draws with skin and body mask (D2);          [no Qt]

`assets/` keeps returning plain data: `ModelData` is vertices, indices and tables, and audio playback
lives in `ui/`, so `assets/` gains no Qt. Instance templates are `document::Document` values that no
`EditorSession` owns, and `render/` draws them through the same mirror path as the open document's
nodes, with a transform and tint. `document/instance_collapse` knows VMF and fixup rules, not files:
`editor/` resolves paths and hands it a loaded template. `tools/check_layers.py` gains no new layer;
mdlpp, kvpp and (for the release gate) bsppp are linked by `assets/` only.

### 0.4.1: Prerequisites and the model loader (D1, D4)

(`tests/assets/sourcepp_confirm_test.cpp`). bsppp is enabled and reads the entity lump of the one

installed, `spikes/qt-multimedia` (standalone, not in the Apex build) builds and links `Qt6::Multimedia`, and
`QMediaPlayer` through Qt's FFmpeg backend opens a WAV and an MP3 (1 s each), reports the right duration,
reaches `EndOfMedia`, and decodes 44,100 frames of each. It was run with no sound device attached
(`QAudioBufferOutput` in place of `QAudioOutput`, `PULSE_SERVER` pointed nowhere), so this proves decode and
the player's clock, not audible output. In the `win10` guest (MSVC 2022, Qt 6.10.2, the `qtmultimedia` module
added with `aqt install-qt ... -m qtmultimedia`) the same spike builds and passes with the same decoded frame
counts (the MP3 reports 1,044 ms there against 1,000 ms on Linux, from FFmpeg's timestamp handling). Qt's
Windows FFmpeg is **7.1.2, LGPL 2.1 or later**. Findings that shape 0.4.6:
- **Windows packages itself.** `windeployqt` (already what `tools/package.py` runs) pulls in
  `multimedia/ffmpegmediaplugin.dll`, `windowsmediaplugin.dll` and the five FFmpeg DLLs (`avcodec-61` 13.9 MB,
  `avformat-61` 2.6 MB, `avutil-59`, `swscale-8`, `swresample-5`: about 19 MB, plus `Qt6Multimedia.dll`
  1.2 MB), and the deployed spike plays both files from its own folder with no Qt on `PATH`. Nothing to add
  to `package_windows` beyond `THIRD_PARTY.md` and the licence note.
- **The Windows backend (`QT_MEDIA_BACKEND=windows`) is not the one to use.** It reported an error on both
  files with this spike (which sends audio to a buffer output, and I did not look into why); FFmpeg is the
  default and is what ships.
- **`tools/package.py` does not bundle it on Linux.** Its plugin whitelist has no `multimedia` directory, so the
  FFmpeg plugin would be missing from the Linux package. Reading the script, not running it.
- **The distro's FFmpeg is a GPL build.** The host's `libffmpegmediaplugin.so` links the system `libav*`,
  and `ffmpeg -buildconf` shows `--enable-gpl`; the plugin also pulls in `libx264`, `libx265` and `libmp3lame`
  through it. Bundling that ldd closure would ship GPL libraries, which 0.1 D4's allowed list
  (`tools/check_licenses.py`) forbids. The Linux package therefore either leaves the Multimedia plugin and its
  FFmpeg out (preview shows "unavailable" unless the host has Qt Multimedia) or bundles an LGPL-configured

**Sanitizer run (0.4.1, 2026-10-25):** the 0.4.1 test cases (model bake, bake corpus sweep, ModelCache, entity
transform, kvpp, bsppp: 18 cases, 339,699 assertions) pass under the `linux-asan` ASan+UBSan build. The full

**Then:** mdlpp enabled in `cmake/deps.cmake`; `assets::ModelData` and the bake; `ModelCache` (async,
LRU by bytes, invalidated with materials on mount change); `entityTransform` and the angle matrices;
entity boxes rotate.

**Tests:** P0 tests 1–4 pass against the Apex bake; the bake equals `processModelData` on single-body-part

### 0.4.2: Model rendering and model-triangle picking (D2, D3)

The mirror's model path (shared meshes, grouped instanced draws, skin and body mask, error model,
placeholders while loading), per-entity bounds, model-space triangle BVHs, `PickIndex` entity leaves
from model bounds, placement on props.

**Tests:** golden images of a fixture model with skin 0 and 1 and two bodygroup values; a prop rotated
on all three axes and scaled renders and picks where `entityTransform` says; a ray through a gap in a
fixture railing model misses it; entity placement on a prop's top face lands on it with its normal;
picks only count the selected bodygroup's triangles; a missing model draws and picks the error model;
an addon toggle swaps a model that only the addon provides.

**Exit:** tests pass; the release corpus map with the most props opens with every model drawn; the
owner selects props through gaps in perspective.

**As built (0.4.2):** `editor` cannot include `assets`, so the pick side is `editor::PickModel`
(positions, uint32 indices, triangle ranges per bodygroup choice, one `geometry::Bvh`) fed by
`ui::ModelPickCache`, which converts a `ModelData` and reorders its triangles per (part, choice). The
`EntityBoundsProvider` now returns an `EntityPickShape {model, body, fallback box}`; `Hit::modelTriangle`
marks a model hit, and `placeEntity` accepts it like a brush side. A model with an empty body selection
has no pick leaf. The mirror draws each model from one shared vertex/index/edge buffer triple; draws are
grouped by (model, first index, texture, colour, highlight) and instanced through the preview buffer:
`MeshDraw::instancedTransforms` sets the high bit of `p1.z`, and the shader adds `gl_InstanceIndex`.

## 5. Things that will bite

**1. Someone will call `processModelData`.** It's right there and works on the first fixture model,
which has one body part. Every bodygroup then draws at once. Defence: D1's bake is the only path;
P0 test 1 stays as a regression test; `tools/check_layers.py` (or a grep test) fails the build on a
call to `processModelData` in `src/`.

**2. Indices will be 16-bit somewhere.** The GPU index type, the BVH's triangle indices, or a copy into
a `uint16_t` vector "because mdlpp does". Defence: `ModelData` uses `uint32_t`, the renderer binds
`VK_INDEX_TYPE_UINT32` for models, and P0 test 2's synthetic model is rendered and picked.

**3. Angles will be applied in the wrong order, or the model's forward axis assumed.** Source applies
yaw, then pitch, then roll, and a model's forward is +X. A test with a single non-zero angle passes
with the wrong order. Defence: D4's one function, a test grid of mixed angles against srctools, and
every consumer calls it.

**4. Instance contents will leak into the parent map.** A template node handed to the clipboard, the
outliner or an edit writes it into the document. Defence: templates are separate `Document` values that
no `EditorSession` owns, picks return the `func_instance`, and the save-after-render test checks the
parent's bytes.

**5. Fixups will be written back.** Resolving `$skin` in the parent's keys (instead of in the draw path)
looks harmless until the parent is saved. Defence: fixups apply to copies in the mirror's input, and
the same save test covers it.

**6. Connections will be rewritten with commas** (or with ESC, for the 22 that use commas), producing a
diff in every connection Hammer later shows as changed. Defence: D6's per-connection separator and the
corpus byte-identity test.

**7. Validation will flag valid logic.** `!activator`, wildcards, classname targets, instance-prefixed
names, `instance:` inputs and names created at runtime by `point_template` all look like dangling
targets. Defence: the corpus invalid count is reviewed one by one before it becomes the baseline, and
validation never refuses an edit.

**8. Thumbnails will be rendered on the frame that matters.** A scroll through 2,204 models queues
thousands of offscreen renders on the main thread. Defence: an 8 ms time budget per tick, none during an
interaction, visible items first, and 0.4.6's test that a drag tick renders no thumbnail.

**9. Model materials will exhaust the bindless heap.** Thumbnails, the map's props and its brush
textures share 4,096 slots. Defence: thumbnails use their own recycled 64-slot range; the release
measurement records slot use on the most-dressed corpus map.

**10. `line()` helpers will make every entity change O(n²).** Each helper looks up its target by name;
rebuilding all helpers per change scans every entity per helper. Defence: `NameIndex` updated from
ChangeSets and per-entity helper updates; a test changes one entity on a 5,000-entity synthetic map and
checks the work done is bounded.

**11. The entity buffer will still be rebuilt wholesale.** The current mirror rebuilds every entity box
on any entity change; with models and helpers that becomes visible as a stall on large maps. Defence:
per-entity updates in 0.4.3, and the release frame-time measurement.

**12. Collapse will lose membership or reuse IDs.** It's paste, nearly, and the paste path does it right;
writing collapse from scratch doesn't. Defence: collapse goes through the clipboard's paste path for
ID allocation and membership, with a test of a grouped, visgrouped instance.

**13. Prefab placement will place by the origin, not the bounds.** A prefab's objects sit wherever they
were when it was created. Defence: placement uses the prefab's bounds' bottom centre, like an entity's
box, and the ghost shows it before the click.

**14. Hammer will overwrite Apex's addon toggle.** If Hammer keeps the list in memory and writes it on
exit, a toggle made in Apex while Hammer runs is lost silently. Result: P3 found Hammer writes the list at
startup only, so a running Hammer does not overwrite it; the panel shows a restart-Hammer notice (D15).

**15. Qt Multimedia will be missing in the Windows package.** It builds on Linux, `tools/package.py`
doesn't copy its plugins, and the Windows build plays nothing. Defence: P0 confirms packaging in the
VM, and 0.4.6's exit plays a sound there.

**16. A new tool action will be bound in one preset only.** 0.4 adds actions (collapse, open instance,
create prefab, the Find role, name labels). Defence: 0.2's registry completeness test already fails the
build.

**17. The ninth tool will sneak in.** A "Prefab tool" is the obvious way to place prefabs. Defence:
D13, and 0.3's slot test.

## 6. Sequencing

1. **0.4.1** first, alone. Its P0 can change D1, D3, D4, D7, D12 and D15, and the model bake is what
   0.4.2, 0.4.5 and 0.4.6 build on.
2. Then three tracks:
   - **Track A (models):** 0.4.2 → 0.4.3. Helpers draw `studioprop` through 0.4.2's path, and
     per-entity mirror updates land once, in 0.4.3.
   - **Track B (logic):** 0.4.4 needs only 0.4.1 and the headless half of template loading, which it
     lands first. It touches the inspector and `editor/`, not the mirror.
   - **Track C (instances):** 0.4.5 after 0.4.2 (contents include props) and after 0.4.4's template
     loader.
3. **0.4.6** after 0.4.2 (thumbnails render models). **0.4.7** after 0.4.6 (placement items come from
   the Models browser, and prefab thumbnails reuse its renderer).
4. **0.4.8** after 0.4.4 (Problems lists invalid connections) and 0.4.6 (asset kinds come from the
   indexes). **0.4.9** after 0.4.8 (the hints attach to D11's report).
5. **0.4 release** last: the scripted dressing needs every sub-milestone.

Merge order puts the pure layers first: `assets/` and `document/` changes merge with their tests before
the `editor/` code that uses them, and nothing in `ui/` merges before its `editor/` model has passed
headless tests.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-10-25. Each was presented with its alternatives, and each was
confirmed as the plan states it. They're recorded here with the alternatives turned down, so a later
reader does not reopen them without new information.

- **D8: *Open Instance* starts a second Apex process; the parent previews contents and hot-reloads.**
  The roadmap's "in-context instance preview" is read as preview, not editing. Turned down: in-place
  editing in the parent's frame (needs a second document and history in the session, and reverses D7),
  and tabs in one process (most of that cost without the in-context payoff). Revisit if the
  second-window loop proves too slow in the owner's manual dressing.
- **D13: no new tool; the Entity tool places classes, models and prefabs as placement items.** Turned
  down: a ninth Prefab/Model tool (forces the pie's "More" level now), and drag-from-browser only (no
  repeated placement, no ghost). Revisit when a tool genuinely needs its own slot.
- **D10: sound preview through Qt Multimedia.** Turned down: names only (no playback), and sndpp
  decoding (still needs Qt Multimedia's `QAudioSink`, and covers no MP3). Revisit if Qt Multimedia
  can't be packaged on Windows.
- **D10: particles listed by name only.** Turned down: a static preview (half a particle system, often
  wrong), and full simulation (would dominate 0.4). Revisit after 0.6's renderer work.
- **D6: renaming a `targetname` offers to update references, default on.** Turned down: the same
  prompt default off (Hammer's behaviour unless opted in), and never (Hammer). Revisit if deliberate
  link-breaking renames are common enough that the prompt gets in the way.
- **D12: prefabs are VMF files in Strata Hammer's `hammer/prefabs`, plus an optional user folder.**
  Turned down: an Apex-only folder (not shared with Hammer), and per-project folders (0.4 has no
  projects yet). Revisit if 0.4.1's probe shows Hammer uses another format there.
- **D16: the exit includes the owner's manual in-game playtest.** Turned down: the compiled entity lump
  check alone (can't catch logic that compiles and misbehaves), and an automated playtest (0.5's game
  launching brought forward).
- **D5: the wider helper set**, lights waiting for 0.6 and decals and overlays for 0.8. Turned down:
  the roadmap's eight only (leaves corpus-used helpers invisible), and drawing light helpers now (radii
  could disagree with 0.6's light model).
- **D9: collapse matches vbsp's instance merge, checked against srctools and vbsp.** Turned down:
  geometry plus name prefixing only (breaks I/O through proxies and `$`-variables). Revisit only if
  srctools and vbsp disagree, and then vbsp wins.
- **Scope: *Create Instance from Selection* moves to 0.5.** Turned down: adding it to 0.4.5.
