# Apex: 0.9 implementation plan: Extensibility

**Status (2026-11-16): reviewed by the owner; ready for 0.9.1 once 0.8's open work merges (§6).** Drafted
against `28224b0` on the 0.8 branch, with 0.8 not yet released and uncommitted 0.8.8/0.8.9 work still in the main
checkout. No sub-milestone has started. Every decision was confirmed as drafted; the appendix records the
alternatives turned down.

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.9: Extensibility.** Plugin API (stable C ABI with a header-only C++ wrapper), a scripting host (language
> decided in the 0.9 plan), custom tools/panels/importers, keymap editor for the Hammer and Blender presets
> (0.2 D15), theme editor, plugin manager, scriptable and persistent parametric primitives (including Strata
> Hammer's AngelScript ones; 0.3 D6), user-editable pie menus (0.3 D20).
> **Exit:** a third-party tool can be built, loaded and shipped without rebuilding Apex.

The interface itself is designed in [plugins.md](plugins.md), whose D1–D13 the owner accepted on 2026-11-16:
in-process native plugins (D1), versioned C interface tables (D2), a header-only C++ wrapper and an SDK (D3),
main-thread callbacks with thread-safe VFS providers (D4), document reads by ID and writes through the session's
`edit()` (D5), tools as host-side `editor::Tool` adapters (D6), namespaced actions (D7), declarative panels (D8),
folder packaging with a KV3 manifest and startup-only loading (D9), AngelScript (D10), primitives gated on a probe
(D11), ABI major 1 frozen at the 0.9 release (D12), and the extension-point table (D13). This plan does not
restate them; it cites them as "plugins.md D*n*". Its own decisions (D1–D9 below) are what reading the code
forced on top of that design. [godot-acoustics.md](godot-acoustics.md) is one input among others (plugins.md §9).

This document does not supersede research.md, the roadmap or plugins.md; where they disagree, those win, and the
0.9 release lists the amendments. Four of them change what an earlier document said:

- D1 changes 0.2 D15's preset rule ("a preset binds every action; `validate` rejects a missing one") to "a preset
  binds every **built-in** action; plugin actions are optional".
- D1 changes 0.2.12's preset file rule ("unknown actions are dropped", `preset_io.hpp`) for IDs in the `plugin.`
  namespace, which are kept.
- D3 corrects plugins.md §2 and D5: `document::Document::Observer` already receives a `ChangeSet`; it is
  `EditorSession::observe` that has no payload. The gap is that the `ChangeSet` holds handles.
- D7 narrows plugins.md §7 and the roadmap's "keymap editor" and "theme editor": both already exist (0.2.12's
  Keybindings page with `PresetStore`; 0.3.4's `ThemeEditorDialog`).

0.9 also owes answers that earlier plans handed forward (collected in plugins.md §1):

- **Tools through `editor::Tool`, Qt-free** (0.2 D1, 0.3 D1, research.md §6): plugins.md D6; 0.9.2.
- **The keymap editor over 0.2 D15's registry** (0.2 §4): D7; 0.9.8.
- **User-editable pies and pie layouts in presets** (0.3 D20, 0.4 D13): D7; 0.9.8.
- **Re-editable and Strata scriptable primitives** (0.3 D6): plugins.md D11, after P0 probe P2; 0.9.7.
- **Two-way game link** (0.5 D9: "plugin territory"): not built by 0.9; it is a test of plugins.md D13's
  `apex.jobs/1` and `apex.actions/1` that a third party can write (§4).
- **Polygon tool, sprinkle, physics drop** (0.8 §4): the polygon tool is an example plugin (0.9.2); the others
  are not in 0.9 (§4).

**What 0.9 inherits.**

- **`editor::Tool` and the session's tool map.** `EditorSession` fills `tools_` (`std::map<ToolId,
  unique_ptr<Tool>>`) in its constructor from fixed `EditorSession::Tool::*` IDs. A tool's ID is also its action
  ID (`"tool.select"`), so activating a tool is performing an action.
- **One write seam.** `EditorSession::edit(label, fn(Transaction&), coalesceKey)`, over `Transaction`'s finite op
  list. Sidelist upkeep (0.8 D11) runs inside `commit()`.
- **Change sets.** `Document::observe(fn(const ChangeSet&))`; the set is built at commit and, for undo/redo, in
  `restore()`. Both loops walk `Delta`s that carry `NodeId id`; the set they emit holds `NodeHandle`s, and a
  destroyed node's handle no longer resolves once the slot's generation moves on.
- **Actions, presets and the keybinding editor** (0.2 D15, 0.2.12). `actionRegistry()` is one static list.
  `validate()` reports "Missing action" for any registered action a preset lacks and "Unknown action" for any it
  has that isn't registered, and `Keymap`'s constructor throws on either. `parsePreset` drops unknown actions.
  `PresetStore` saves user presets as JSON; the Preferences dialog's Keybindings page edits, imports and exports
  them.
- **Pies** (0.3 D20). `PieMenu{title, items[{action, slot, label}]}` is data, but `toolPie()`, `objectPie()` and
  `pieFor()` (`pie_menus.cpp`) are code.
- **Panels and layouts.** `viewport::AreaRole` is an enum with `kAreaRoles[]`, stable JSON names, and
  `createPanel(AreaRole, …)` (`ui/area_frame.cpp`) switches over it. Layout parsing fails the whole layout on an
  unknown role.
- **Tools drop-down.** `kToolActions[]` in `ui/main_window.cpp` is a fixed list.
- **Problems** (0.5). `ProblemRegistry::add(name, ProblemCheck)` already takes checks; `ProblemKind` is a closed
  enum.
- **Jobs.** `core::JobPool::submit(priority, fn, onMain)`: thread-safe submit, completion on the main thread.
- **VFS** (`assets/vfs.hpp`): main-thread owner, earlier mounts win, `walkTask()` runs on workers.
- **Themes.** `ThemeEditorDialog`; themes import and export as `.json`.
- **Packaging.** `cmake/Packaging.cmake` installs the `apex` component; `tools/package.py` builds the `.deb`,
  `.rpm`, Windows zip and installer. Dependencies come through CPM (`cmake/deps.cmake`); `tools/check_licenses.py`
  checks them.
- **Headless UI tests** (`tests/ui/`, `QT_QPA_PLATFORM=offscreen`) and the layer checker.

**What 0.9 does not have.**

- Any way to load code at run time, or an install layout for headers and CMake config (D8).
- A mutable action registry, or presets that tolerate actions that come and go (D1).
- Layouts that tolerate a panel that comes and goes (D2).
- Change sets that name destroyed nodes by ID (D3).
- A defined point in startup where extensions register (D4).
- Registries in place of the fixed lists above (D5).
- A safe way back from a plugin that crashes on start (D6).
- A scripting language (plugins.md D10; 0.9.7).

## 1. Decisions

Each records what would reverse it.

### D1: Plugin actions are optional in presets, and preset files keep `plugin.*` bindings they can't resolve

Two rules change, both in `editor/actions.cpp` and `preset_io.cpp`:

1. `validate()` requires a binding for every **built-in** action, as now, and treats a registered plugin action
   with no entry as unbound. So `hammerPreset()` and `blenderPreset()` stay complete without knowing any plugin,
   and registering an action never makes a built-in preset invalid. Today it would: `Keymap(hammerPreset())`
   throws "Missing action" as soon as the registry holds one action the preset lacks (P0 test 1).
2. `parsePreset()` keeps entries whose ID starts with `plugin.` even when no such action is registered, as
   **dormant** bindings: they are carried through `serializePreset`, skipped when building the `Keymap`, and not
   reported by `validate`. Other unknown IDs are dropped as today (the older-build rule 0.2.12 documents). Today a
   preset saved with a plugin loaded and re-saved without it loses those bindings (P0 test 2); that is the
   documented rule doing what it says, which plugins turn into data loss.

A plugin's suggested bindings (plugins.md D7) are applied when the effective keymap is built, only where the
chord is free in that context and the user's preset has no entry for the action; a conflict leaves it unbound with
the conflicting action named. A user's own binding always wins and is never rewritten.

*Alternative:* merge plugin actions into each preset at load (write default entries into the user's preset so
`validate` stays strict). It keeps one rule, but every load rewrites preset files, a plugin removed and re-added
comes back with whatever the merge chose rather than the user's binding, and the built-in presets would need a
merge too.

*What would reverse it:* a need for dormant bindings outside the `plugin.` namespace (for example renamed built-in
actions), which would call for a general alias table instead.

### D2: A layout keeps a plugin panel the plugin can't supply, as a placeholder pane

`AreaRole` gains `Plugin`, and a pane with that role stores the panel's ID (`plugin.<id>.<panel>`) in the layout
JSON beside `"role": "plugin"`. When the plugin is not loaded, the pane shows a placeholder naming the plugin and
the panel ("Plugin *Face stats* is not loaded"), with a button to open the plugin manager. The pane keeps its place
and size, and is filled when the plugin is back. Unknown non-plugin roles still fail the layout as today.

Today a saved layout with any unknown role fails to parse as a whole (P0 test 3), so removing one plugin would reset
the user's entire layout.

*Alternative:* drop the pane and re-flow the layout. Simpler, but disabling a plugin for one session then loses
the panel's place for good, and a user debugging a plugin by toggling it rebuilds their layout every time.

*What would reverse it:* the placeholder confusing users more than a missing pane does, in the owner's use.

### D3: `ChangeSet` carries `NodeId`s, filled in `document/` where they are already known

`ChangeSet` gains `createdIds`, `modifiedIds` (with flags) and `destroyedIds`, filled in the same two loops that
build it (`Transaction::commit` and `Document::restore`), from `Delta::id`, which both loops already read. The
plugin host converts a `ChangeSet` to the C notice of plugins.md D5 with no lookup and no state.

*Alternative:* a handle-to-ID shadow map in `plugin_host`, updated on every change set. It leaves `document/`
untouched, but it has to see every create before the matching destroy, is a second copy of the arena's identity
that can drift, and costs memory proportional to the map. Filling IDs is three `push_back`s where the ID is
already in a local.

*What would reverse it:* a profile showing the extra vectors matter on large edits (the change set is built once
per commit; this is not expected).

### D4: Extensions register only during startup, before presets, VFS mounts and the layout

Startup order becomes:

1. Settings, logging.
2. **Plugin discovery and activation** (plugins.md D9). Each plugin's `activate` registers its tools, actions,
   panels, providers, checks and importers. Registration outside `activate` is refused, except by the script
   host for script plugins.
3. The registry is frozen; the effective action list and panel list are final for the session.
4. The preset is parsed and the `Keymap` built (D1), the game profile mounted (VFS providers in place), the
   layout restored (D2), the last document opened.

Document lifetime is a notice, not a registration: `on_document_opened` / `on_document_closing` (plugins.md D5's
`apex.document/1`), so a plugin never registers per document.

*Alternative:* register lazily at any time, with every registry notifying the UI. That is what hot reload needs
(plugins.md D9 defers it), and it would make every registry observable and every consumer re-entrant now, for a
feature not in 0.9.

*What would reverse it:* native hot reload moving into scope.

### D5: The fixed lists become registries with the built-ins registered first

- `actionRegistry()` → an `ActionRegistry` with a built-in part (as now) and a plugin part, appended in load
  order; IDs outside the registering plugin's namespace are refused.
- `kToolActions[]` → the tool registry's order: built-ins, then plugin tools.
- `EditorSession` gains `addTool` for registration in D4 step 2; built-in tools register through it too, so there
  is one path.
- `AreaRole::Plugin` + panel ID (D2); the role menu lists plugin panels under a separator.
- `ProblemKind::Plugin`, and `Problem` gains `source` (the plugin ID), so the Problems list can group and filter
  by plugin; plugin checks go through the existing `ProblemRegistry::add`.
- `pieFor()` reads pie layouts from the preset (D7), with today's pies as the built-in defaults.

Each registry is a plain data structure in the layer that owns the list today (`editor/`, `viewport/`); the
plugin host only calls them, so nothing below `plugin_host` learns plugins exist.

*Alternative:* leave the lists fixed and have the plugin host append to the UI directly (extra menu, extra
panels outside the layout system). Less change, but plugin tools would miss the tool pie, the drop-down and
tool-scoped bindings, which is the 0.2 D1 / 0.3 D1 promise.

*What would reverse it:* nothing expected; this is the cost of the promise.

### D6: Safe mode, and a breadcrumb around every plugin callback

The host writes the plugin ID and callback name to a small breadcrumb file before each call into a plugin and
clears it after (a memory-mapped page, so the cost is a store, not a syscall). On start, a breadcrumb left behind
means the last session died inside that plugin: the plugin manager opens, names it, and offers to disable it.
`apex --no-plugins` (also offered by the breadcrumb prompt as "start without plugins once") starts with no
plugins loaded, without changing which are enabled.

*Alternative:* nothing beyond the manager's enable switch. Then a plugin that crashes in `activate` makes Apex
unstartable until the user finds the plugin folder by hand.

*What would reverse it:* out-of-process plugins (plugins.md D1's alternative) making crashes recoverable anyway.

### D7: The keymap and pie work is pie layouts in presets plus plugin awareness; the theme work is plugin themes

The keybinding editor (0.2.12) and theme editor (0.3.4) exist. What 0.9 adds:

- **Pie layouts in presets.** `Preset` gains `pies` (`std::map<ActionId, PieMenu>` keyed by the `pie.*` action
  that opens it), serialised by `preset_io` and defaulted from today's code pies. A Pies page beside Keybindings
  edits a pie's items (any action, including plugin actions and tools) and slots, and can add a pie with a new
  `pie.user.<name>` action. 0.4 D13's "More" level is a pie item that opens another pie.
- **Plugin awareness in the keybinding page**: plugin actions grouped by plugin; dormant bindings (D1) shown
  greyed with the plugin's name; suggested bindings shown as such until the user changes them.
- **Tool-scoped bindings** (`BindingContext::forTool`) shown and edited per tool, if the page doesn't already;
  0.9.8's P0 checks.
- **Plugin themes**: theme `.json` files in a plugin's `themes/` folder appear in the theme list, read-only, with
  "Duplicate to edit".

*Alternative:* a separate keymap editor window as the roadmap's wording implies. The page already exists and is
tested (`tests/ui/settings_test.cpp`); a second editor would duplicate it.

*What would reverse it:* the owner wanting a Blender-style keymap tree with per-tool sections as its own window.

### D8: The SDK is an install component, and its out-of-tree build is a test

`cmake/Packaging.cmake` gains a `sdk` component: `include/apex/apex_plugin.h`, `include/apex/plugin.hpp`,
`lib/cmake/ApexPlugin/ApexPluginConfig.cmake` (an `apex::plugin_sdk` INTERFACE target and `apex_add_plugin()`),
the example plugins' sources, and `docs/plugins/`. `tools/package.py` gains `--sdk`, producing
`apex-plugin-sdk-<version>.zip` (one archive for every platform: the SDK is headers and CMake only).

In the build tree, the examples are built twice:
- as ordinary targets of the Apex build (fast; the loader and API tests use them), and
- by one ctest case, `plugin_sdk_out_of_tree`, that installs the `sdk` component into a temporary prefix and
  configures and builds `examples/plugins/` from there with no Apex include paths, passing `-j` from `APEX_JOBS`
  (default 2) so the nested build stays inside `scripts/test.sh`'s memory cap.

The release gate (D9) then repeats this from the published archive against the published binary.

*Alternative:* examples only as in-tree targets. Fast, but an in-tree target can include `src/` by accident, which
is exactly what the exit criterion forbids; the layer checker cannot see a CMake include path.

*What would reverse it:* the nested build proving too slow for every test run; it would then move to `tools/ci.py`
only.

### D9: The exit is a scripted plugin round trip on Linux and Windows, from the published SDK and binaries

0.9's exit ("built, loaded and shipped without rebuilding Apex") is tested as one scenario, on Linux and on the
Windows machine, using only the release artefacts:

1. Unpack `apex-plugin-sdk-0.9.x.zip`; build `polygon-tool` and `face-stats` with the platform's compiler against
   it. No Apex source tree on the machine's include path.
2. Install the published Apex 0.9 package. Install both plugins through the plugin manager from their folders.
3. Restart. Bind the polygon tool to a key, put it in the tool pie, dock the face-stats panel. Draw a solid with
   the polygon tool, undo, redo, save. The map opens unchanged in Strata Hammer except for the new solid.
4. Disable `face-stats`, restart: the panel is a placeholder (D2), the polygon binding and pie slot remain (D1).
   Enable it, restart: everything is back.
5. Install the AngelScript `stair` script plugin; edit its script while Apex runs; the change shows without a
   restart.
6. Start with `--no-plugins`: nothing loads, and nothing in the preset or layout is lost on exit.

*Alternative:* the exit judged by the CI out-of-tree build alone (D8). It proves "built", not "shipped": the
archive, the installer layout and the plugin manager's install path are what a third party actually meets.

*What would reverse it:* the Windows machine not being available at release, in which case Windows moves to a
0.9.x point release as 0.7's baker validation did.

## 2. Where the seam goes

```
  include/apex/   apex_plugin.h (C, stdint/stddef only); plugin.hpp (C++ wrapper,     [public, no src/]
                  includes only apex_plugin.h).
        |
  app/            + startup order (D4); --no-plugins (D6).                                 [Qt]
        |
  ui/             + plugin manager panel; declarative form builder (plugins.md D8);       [Qt]
                    plugin panel/section/dialog hosts; Pies page; plugin-aware Keybindings
                    page (D7); placeholder pane (D2).
        |
  plugin_host/    NEW. Loader, manifest (KV3), breadcrumb (D6), interface tables,         [no Qt]
                    PluginTool : editor::Tool adapter, C <-> internal type translation,
                    VFS provider adapter, script host bridge.
        |
  editor/         + ActionRegistry (D5); dormant/optional plugin bindings (D1); pie        [no Qt]
                    layouts in Preset (D7); EditorSession::addTool; ProblemKind::Plugin.
        |
  viewport/       + AreaRole::Plugin + panel ID in layout JSON (D2).                       [no Qt]
        |
  render/         + per-face tint and world overlay lists outside tools (plugins.md D13).  [no Qt]
        |
  assets/         + Vfs provider mounts (plugins.md D4); VMT write-back.                   [no Qt]
        |
  document/       + ChangeSet IDs (D3).                                                    [pure]
```

`plugin_host` sits between `editor`/`assets` and `ui`: `check_layers.py` gains
`"plugin_host": ["editor", "assets", "render"]` and `"ui"` gains `plugin_host`. It is the only layer that
knows the C ABI; below it, each registry is ordinary C++ with built-ins as its first users. `include/apex/` is
checked by a new rule in `check_layers.py`: nothing there includes a path under `src/`, and `plugin.hpp`
includes only `apex_plugin.h` and the standard library.

## 4. Not in 0.9

- **Native hot reload** (plugins.md D9, D4 here). Restart to load or unload a native plugin. Script plugins reload.
- **Out-of-process plugins** (plugins.md D1). Possible later for non-interactive kinds behind the same manifest.
- **The unstable Qt tier** (plugins.md D8, owner 2026-11-16).
- **A plugin catalogue, Workshop publishing or automatic updates.** Install from a folder or zip.
- **Per-project or per-profile plugin folders** (plugins.md D9): a map's folder would decide what native code
  runs.
- **Sprinkle and physics drop** (0.8 §4). Good third-party plugins; physics drop needs a physics library.
- **The two-way game link** (0.5 D9). Buildable by a third party on `apex.jobs/1` and `apex.actions/1`; not
  shipped by Apex.
- **Python or Lua hosts** (plugins.md D10). A third party can build one on the same ABI.
- **Plugin data stored in the VMF** beyond what P2 answers for primitives. 0.1 D19 still forbids Apex-only keys.

## 5. Things that will bite

**1. A plugin registers after the preset or layout is loaded.** It is tempting to load plugins lazily, or after
the window is up so startup looks faster. Every launch then drops plugin bindings (D1's dormant rule saves them
from deletion, but they never bind) and shows placeholders for loaded plugins. *Defence:* D4's order, enforced by
refusing registration outside `activate`, and a startup test that loads a plugin with a binding and a panel and
checks both are live in the first frame.

**2. A plugin reads a pointer or handle and keeps it.** Handles look like IDs and survive a while in testing.
*Defence:* the ABI has no handles or pointers into the document (plugins.md D5); everything is `NodeId`/`SideId`.
The C++ wrapper's types make an ID the only thing you can hold.

**3. A plugin edit bypasses `EditorSession::edit()`.** A future interface could expose `Document::begin()` "for
speed". Selection undo and coalescing break silently. *Defence:* `plugin_host` has no access to `Document::begin`
(it is given the session only), and 0.9.3's test checks selection restore on a plugin edit.

**4. A plugin mutates the document from inside `on_changed`.** It is the obvious way to keep derived data in step,
and `Document` forbids observers mutating. *Defence:* the edit interface returns `APEX_ERR_STATE` during a
notification pass and names `defer`; 0.9.3 tests it.

**5. An exception crosses the C boundary.** A C++ plugin throws from a callback, and the host's unwinder meets a
frame compiled by another compiler. *Defence:* the wrapper's trampolines catch everything and return
`APEX_ERR_INTERNAL`; the host never throws into a plugin (it catches at each interface function); P1 runs a
throwing callback across compilers.

**6. A VFS provider is called on a worker and isn't thread-safe.** Its author tested on small mounts where the walk
finished on the main thread first. *Defence:* plugins.md D4 says so in the header; 0.9.6's test runs walks
concurrently from the first call; the wrapper's `VfsProvider` base is documented as `const` and thread-safe.

**7. A new built-in list is added as a fixed array again.** The next panel, tool or problem kind added in 0.10 goes
into a `constexpr` array out of habit. *Defence:* D5's registries are the only lists; `kToolActions` and
`kAreaRoles` are deleted, not kept beside them.

**8. The in-tree example build hides an `src/` include.** *Defence:* D8's out-of-tree ctest case and the
`include/apex/` layer rule.

**9. A plugin crashes in `activate` and Apex can't start.** *Defence:* D6's breadcrumb and `--no-plugins`, tested in
0.9.1.

**10. A nested out-of-tree build runs uncapped.** The SDK test runs `cmake --build` inside ctest, which
AGENTS.md's memory rules don't see. *Defence:* D8 passes `-j` from `APEX_JOBS` (default 2), and the test runs
under `scripts/test.sh`'s cgroup like every other test.

## 6. Sequencing

**Before any 0.9 code:** the 0.8.8/0.8.9 work in the main checkout merges. It touches `actions.cpp`, `pie_menus`,
`map_problems` and `editor_session`, which 0.9.1 restructures (D1, D5, D7).

0.9.1 first and alone: its three failing tests protect users the moment the first plugin exists, and every later
sub-milestone registers through its registries. 0.9.2 then 0.9.3 (tools commit through the edit interface). After
0.9.3, these can run in parallel because they touch disjoint code: 0.9.4 (UI), 0.9.5 (overlays, helpers, problems,
importers, jobs, watch), 0.9.6 (VFS and assets), 0.9.8 (pies and keybindings, which needs only 0.9.1's registry).
0.9.7 (scripts) needs 0.9.2–0.9.4 so scripts can register tools, edit and show forms; its primitive half waits on
P2. 0.9.9 last; its freeze reviews every interface, so it follows everything that adds one.

0.9.5's helpers and file watch, and 0.9.6, could slip to 0.9.x after the release without touching D9's scenario.
The script host (0.9.7) is in the scenario (step 5) because the roadmap names it.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-11-16. Each was presented with its alternatives, and each was confirmed
as the plan states it. They are recorded here with the alternatives turned down, so a later reader does not
reopen them without new information. D4–D8 were not put as questions; they stand as drafted unless the review of
0.9.1 turns them down.

- **D1: plugin actions are optional in presets, and preset files keep dormant `plugin.*` bindings.** Turned down:
  merging plugin actions into every preset at load (rewrites user preset files; a plugin removed and re-added
  returns with the merged default, not the user's binding). Revisit only on needing dormant bindings outside the
  `plugin.` namespace.
- **D2: a layout keeps an absent plugin's panel as a placeholder pane.** Turned down: dropping the pane and
  re-flowing (toggling a plugin loses the panel's place for good). Revisit if the placeholder confuses in use.
- **D3: `ChangeSet` carries `NodeId`s, filled in `document/`.** Turned down: a handle-to-ID shadow map in
  `plugin_host` (a second copy of the arena's identity that can drift). Revisit only on a profile showing the
  extra vectors matter.
- **D9: the exit is the plugin round trip on Linux and Windows from published artefacts.** Turned down: Linux only
  with Windows in a point release, and the CI out-of-tree build alone (proves "built", not "shipped"). Revisit
  only if the Windows machine is unavailable at release.
