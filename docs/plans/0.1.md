# Apex: 0.1 implementation plan: Foundations (open, view, save)

**Status: reviewed by the project owner, 2026-10-20. Ready for 0.1.1 P0.** No sub-milestone has
started. Every decision in the appendix was put to the owner. All draft choices were confirmed,
and the review added D21 (face identity), D22 (local CI) and D23 (Windows VM). D22 rewrites D1's
BUILD source and D20's CI description.

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.1: Foundations: open, view, save.** Build system, CI (Linux + Windows), pure core (math,
> handles, KV1), VMF document model with transactions and undo, brush kernel (construction and
> validation), game profile + virtual filesystem (gameinfo, mounts, VPK), VMT/VTF/FGD loading,
> Vulkan renderer foundation, multiple user-configurable viewports, and the main window shell.

This document does not supersede [research.md](../research.md) or the roadmap. Where they
disagree, those win, and 0.1.10 lists the amendments they need once 0.1 lands. One change is
already made: research.md §5 suggested KDDockWidgets, which is GPL-only. D16 replaces it with
Qt-ADS (LGPL-2.1), and research.md has been corrected.

0.1 is the first milestone, so it inherits no earlier plan. It does owe answers to research.md §8:

- **License**: D4.
- **"Is any 2D view needed?"**: settled by the owner as "a 2D view is a mode of the same
  viewport", and specified in D15.
- **Does mdlpp handle P2CE's models?** P2CE's loose models are `IDST` v44/46/48/49 (25 files
  checked), all inside mdlpp's stated v44–49 range. Model rendering is 0.4, so the full check is
  a 0.4 P0 item, not a 0.1 one.

  with **native Linux `vbsp`/`vvis`/`vrad`/`studiomdl`** in `bin/linux64`, `p2ce/p2ce.fgd`,

  `hammertest.vmf` were the owner's own test maps, not P2CE content, and are no longer corpus.)*
- **Toolchain present:** GCC 15.2, Clang 21.1, CMake 4.2, glslc (shaderc 2026.3), Qt 6.10.2

- **srctools** (Python) as an independent VMF parser to cross-check against.

## 1. Decisions

Each records what would reverse it.

### D1: The version is `MAJOR.MILESTONE.SUB.BUILD`; BUILD is the CI run counter, injected at configure time

The version names the last *completed* sub-milestone. A sub-milestone's merge commit bumps
`MILESTONE.SUB` in one file (`version.txt`) and gets tagged `vX.Y.Z`.

BUILD is not stored in the repo. It is the **local CI runner's run counter** (D22): `tools/ci.py`
increments `$XDG_STATE_HOME/apex/build_number` once per run, pass or fail, and passes it to every
configured preset (including the Windows VM, D23) as `-DAPEX_BUILD_NUMBER=<n>`. Ordinary
developer builds outside the runner report 0. The git hash and a dirty flag go into
`apex/version.hpp` with it, so a crash report or bug identifies the exact binary.

The alternative is a BUILD that counts commits since the tag (`git describe`). That's
reproducible from the repo alone, but it resets on every tag, and two branches can produce the
same number for different code. A runner counter is unique and monotonic, and its only cost is
that ad-hoc builds are "build 0".

*What would reverse it:* builds from more than one CI machine (counters would collide; move the
counter to a shared location or adopt a hosted CI's counter with an offset), or a need for
reproducible builds where the version must derive from the source tree alone.

### D2: One CMake monorepo, static libraries per layer, a single executable, C++23, no C++ modules

`CMakePresets.json` defines `linux-gcc`, `linux-clang` and `windows-msvc`, each in
debug/release/asan variants, built with Ninja. Each layer in §2 is a static library with an
explicit `target_link_libraries` DAG; CI checks the dependency direction (Bite 9). C++23 gives
`std::expected`, deducing `this`, `std::print`, `std::mdspan` and `std::flat_map`. The compiler
floor is GCC 14, Clang 18 and MSVC 17.10.

**C++20/23 named modules are out.** Qt's AUTOMOC and CMake module scanning still interact
badly, clang-tidy and clangd support is uneven, and SourcePP is header-based. Headers with
`#pragma once` cost nothing now, and a later switch to modules needs no design change.

*What would reverse it:* moc gaining reliable module support, combined with build-time pain
from header-heavy layers.

### D3: Qt and the Vulkan SDK come from the system; every other dependency is pinned by commit through CPM.cmake

Qt 6 (system packages on Linux, `aqtinstall` in Windows CI) and the Vulkan headers and loader are
found with `find_package`. SourcePP, Qt-ADS, volk, VMA, glm, spdlog, doctest and
nlohmann/json come in as source at exact commits via CPM.cmake, a thin FetchContent wrapper
with a download cache.

The alternative is a vcpkg manifest for everything. That gives binary caching and one way to
get Qt. But vcpkg's Qt takes hours to build on a cold Windows cache, SourcePP is not in the vcpkg
registry, and a vcpkg Qt diverges from the system Qt that Linux users' themes and platform
plugins expect. Accepted cost: CI caches the CPM source directory, and every dependency
compiles from source on a clean build (minutes, not hours, because Qt is excluded).

*What would reverse it:* the dependency count passing about 15, or a dependency whose build is
painful from source, such as Embree or OIDN at 0.7. Moving to vcpkg then is cheap, because only
the `cmake/deps.cmake` file changes.

### D4: Stay relicensable to GPLv3: MIT now, and only dependencies compatible with both MIT and GPLv3

Allowed licences: MIT, BSD, zlib, Boost, Apache-2.0, LGPL (dynamically linked, which covers Qt
and Qt-ADS), MPL-2.0. **Not allowed: GPL of any version** (this rules out KDDockWidgets) and
anything GPLv3-incompatible. Apache-2.0 (Embree, OIDN, Vulkan ecosystem pieces) is compatible
with GPLv3 but **not GPLv2**. The owner has confirmed that a future switch would be to
**GPLv3-or-later**, and that GPLv2 is deliberately not kept open.

Moving MIT → GPLv3 needs no contributor consent, because MIT permits redistribution under GPL
terms. So there's no CLA. Contributions come in under the DCO (`Signed-off-by`), and inbound
licence = outbound licence. Each dependency's licence is recorded in `THIRD_PARTY.md`, and CI
fails if a dependency is missing from it.

*What would reverse it:* wanting a GPL-only library such as KDDockWidgets or TrenchBroom code,
which would mean switching to GPL now rather than later.

### D5: `core`, `document`, `geometry` and `assets` do not link Qt

The bottom four layers use only the standard library and their own dependencies. Qt types
(`QString`, signals, `QFile`) stop at `ui/`.

The reasonable alternative is to let QtCore in everywhere: `QString` throughout, signals/slots for
change notification, `QFile` and `QThreadPool` for free. That's less glue in 0.1. It's turned
down because:
1. Headless tools (a VMF linter, batch converters, CI corpus tests, the 0.7 bake worker) would
   then drag QtCore along.
2. Signals per property are the wrong change-propagation shape (D11).
3. SourcePP, Embree and OIDN speak `std::` types, so Qt in the core would mean conversions on
   both sides.
4. A future UI swap or a separate CLI stays possible.

Accepted cost: the boundary layer converts between `std::string`/`std::u8string` and `QString`,
the document layer has its own observer mechanism, and `core/` has its own small job pool.

*What would reverse it:* the conversion layer growing into a meaningful share of `ui/` code, or
needing a QtCore-only facility (such as `QProcess` for compile jobs at 0.5) below `ui/`. Even
then, the fix is to wrap it in `app/`, not to admit Qt into the core.

### D6: The document is a set of typed arenas addressed by generational handles, not a polymorphic object tree

`Document` owns one pool per node kind: `Entity`, `Solid`, `Group`, `Visgroup`, `Camera`,
`Cordon`, and an `UnknownBlock` for anything unrecognized. Each node is addressed by a
`Handle<T>` (32-bit index + 32-bit generation, so stale handles are detectable). The hierarchy is
explicit `parent` / ordered `children` fields. **Sides live inside their `Solid` by value.** They
are never edited independently of the solid's geometry, and keeping them inline makes a solid
snapshot one copy (D10). A side's identity is its `SideId`, not its position (D21). Nodes are plain structs: no virtual functions, no back-pointers to the
document.

Turned-down alternatives:
- **A Hammer-style `CMapClass` virtual tree** (also what TrenchBroom does). This is the natural
  choice and fits the VMF hierarchy directly. But it makes snapshots and undo deep-copy problems,
  scatters nodes across the heap (bad for the per-frame picking and render-mirror walks), and
  invites tools to hold raw pointers that undo then invalidates.
- **A full ECS (EnTT).** Superb for hot iteration, but VMF data is *structural* (ordered
  children, blocks with fixed schemas, lossless round-trip). ECS components would rebuild a tree
  anyway, and the archetype churn from editing is wasted.

Accepted cost: tree operations go through `Document` methods rather than node methods, and
handles must be resolved on every access, which is a bounds check plus a generation compare.

*What would reverse it:* profiling at 0.2/0.4 showing handle resolution in hot loops (picking,
mirror rebuild) costs more than the gain from contiguous storage. That's unlikely, and the fix
would be caching resolved pointers within one frame, not a redesign.

### D7: Untouched content is written back byte-for-byte; only modified nodes are re-serialized

Every node keeps the source span of its block. Every keyvalue keeps its original text until a
transaction changes it. On save:
- unmodified nodes are copied from the original buffer verbatim, including whitespace, line
  endings (D7a), and odd number formatting such as `15.9999`;
- modified nodes are re-serialized in Hammer's formatting (tab indentation, `"key" "value"`,
  `%g`-style numbers with up to 6 significant digits, matching what Hammer writes);
- blocks and keys the schema doesn't know are preserved in their original position.

*Amended by [plan 0.2](0.2.md) (D18):* geometry numbers Apex writes (plane points, `point_data`, `origin`, `angles`) use shortest round-trip fixed notation instead of 6 significant digits; other numbers keep `%g`. Untouched values are still never reformatted.

**D7a:** the line-ending style of the file is detected on load and reused for written nodes.
New files use CRLF, because that's what Strata Hammer writes.

The reasonable alternative is canonical re-serialization (srctools' approach): parse fully, then
write everything from the model. It's simpler, with one code path. It's turned down because the
first save of any map would rewrite every line, which makes `git diff` useless for teams that
version their VMFs, and any formatting difference from Strata Hammer becomes a spurious change
for every collaborator. Accepted cost: the codec keeps the original file buffer alive (memory
≈ file size; the largest corpus VMF is 1.2 MB), and every schema type carries a "dirty" bit.

*What would reverse it:* Strata Hammer rewriting the whole file on every save anyway, which
would make our byte-stability invisible in mixed teams. The 0.1.1 P0 checks this. If it does,
D7 shrinks to "canonical, but in exactly Strata Hammer's formatting".

**Probe result (2026-10-20, Strata Hammer build 10773; `probe-results/`):** the condition did not
trigger. Hammer does re-parse and rewrite the file, but on Hammer-shaped input the output is
byte-identical apart from: comments dropped, five default `worldspawn` keys added
(`maxpropscreenwidth`, `detailvbsp`, `detailmaterial`, `maxblobcount`, `maxprojectedtextures`),
`editorextension` forced to `strata`, and unknown keys and blocks deleted (D19). So D7 stands:
Apex preserves untouched bytes, and Hammer is idempotent on them. Content Hammer does not
understand survives only in files Apex saves, not in files a collaborator re-saves in Hammer.

### D8: Brush geometry is vertex-authoritative; planes are derived

A `Solid` stores a convex polyhedron in **double precision**: vertex positions plus faces as
ordered vertex loops, each face carrying its material, UV axes, lightmap scale and smoothing
groups. The plane is derived from the face's vertices.
- **On load:** if the side has `point_data` and those points lie on the side's plane within
  ε (D9), they're used as-is. Otherwise vertices come from intersecting the planes (clipping a
  2^20-unit box).
- **On save:** each side's `plane` is written as three of its actual vertices (the three that
  span the largest triangle, in Source's winding order). In the Strata profile, `point_data` is
  always written.

The alternative is plane-authoritative brushes, the Hammer and TrenchBroom model. It's turned
down because plane intersection is exactly what produces the `15.9999` drift seen in 35% of the
corpus's planes, and Strata added `point_data` to escape it. For 3D vertex editing (0.3) the
natural operation is "move vertices, take the convex hull", which produces vertices, not planes.

Accepted costs:
- Faces can become non-planar during vertex edits, so the kernel needs a planarity invariant and
  a repair step (triangulate or split the face) in place of the free convexity that planes give.
- For maps without `point_data` (non-Strata profiles, later), the first save writes planes
  through real vertices, which can differ textually from the input. D7 limits that to brushes the
  user actually edited.

*What would reverse it:* VBSP producing different output from planes written through vertices
than from the original plane points (checked in 0.1.6), or the repair step proving unreliable
enough to corrupt user brushes.

*Amended by [plan 0.2](0.2.md) (D4):* the document stores solids as VMF blocks (sides with plane points and `point_data`) and derives the polyhedron from them; the polyhedron is derived from those blocks per use (the mesher derives it per job) rather than stored.

### D9: Double precision in the document; float on the GPU via camera-relative rendering; tolerances in one header

All document and kernel geometry is `double` (glm `dvec3`). That's needed for BSP v25's ±65536
bounds, where `float` steps are about 0.004 units. The GPU gets `float` positions relative to a
per-batch origin, rebased against the camera each frame, with **reversed-Z** and an infinite far
plane. All tolerances (`kPlanarEps`, `kPointMergeEps`, `kPointDataTrustEps`) live in
`geometry/tolerances.hpp`, so no other file can define its own epsilon.

*What would reverse it:* nothing foreseeable. Exact predicates (Shewchuk-style) may be added to
the kernel at 0.3 if the CSG operations need them. That adds to this decision rather than
reversing it.

*Outcome in [plan 0.3](0.3.md) (D8):* not needed. The hull and CSG kernel stayed in plain double with
these tolerances; the hull fuzzer (random clouds and splits near ±65536, in CI) found one volume-check
tolerance to align with the planar merge and no case that needed exact predicates.

### D10: Undo is transactional: before/after snapshots of touched nodes, not hand-written inverse commands

`doc.begin("Move 3 solids")` returns a `Transaction`. The first write to a node through it
copies the node's old value. `commit()` records `{handle, before, after}` for each touched node
plus structural edits (create, destroy, reparent). Undo swaps `before` back in; redo swaps
`after`. Tools never write undo code. The undo stack has a memory cap (default 512 MB) that drops
the oldest entries, and continuous drags merge into one entry.

The reasonable alternative is the classic command pattern, where each command implements
`do()`/`undo()`. It's memory-cheap, with tiny deltas for a translate. It's turned down because
every tool author must write an exactly-inverse `undo()`, and a wrong inverse silently corrupts
history, which is the bug class editors are notorious for. A persistent immutable document with
structural sharing is the other option, with free snapshots and lock-free readers, but it fights
D6's arenas and makes every write path allocate.

Accepted cost: memory proportional to touched nodes (a 10,000-solid move is ≈ 10,000 solid
copies, roughly 20–40 MB), handled by the cap and coalescing.

*What would reverse it:* undo memory under realistic editing (measured at 0.2/0.3) blowing past
the cap within a normal session. The fix would be delta-encoding inside snapshots, which keeps
the API.

### D11: Change propagation happens once per committed transaction as a `ChangeSet`, not as per-property signals

`commit()` emits one `ChangeSet` with created/modified/destroyed handles per kind. Each modified
handle has dirty flags: `Geometry`, `Material`, `KeyValues`, `Visibility`, `Hierarchy`. It's
delivered synchronously on the main thread to registered observers: render mirror, picking BVH
(0.2), outliner, lighting invalidation (0.7). Each observer rebuilds incrementally from that
set. Undo and redo emit the ChangeSet of the restored state, through the same path.

The alternative is fine-grained notifications ("keyvalue X of entity Y changed"). That's
easy to wire to Qt widgets, but it produces thousands of events for one bulk operation, and
observers see intermediate states mid-transaction.

*What would reverse it:* an observer that truly needs intra-transaction progress, such as live
drag preview. That's handled by a separate "preview" channel at 0.2, not by splitting
ChangeSets.

### D12: One writer: the document lives on the main thread, and background jobs get copies

All mutations happen on the Qt main thread. Background work (VTF decode, mesh building, VPK
reads) runs on `core::JobPool` (a small `std::jthread` pool with a priority queue). Jobs receive
**copies** of the node data they need, never handles, and post results back to the main thread.
In 0.1, rendering also runs on the main thread: one `VkDevice`, one graphics queue, every dirty
viewport recorded and submitted in one frame. Frames are drawn on demand, only on change,
camera motion or a pending stream-in.

The alternative is a dedicated render thread from day one. That isolates frame pacing from UI
stalls, but needs a double-buffered render scene and cross-thread ownership of Vulkan objects
before there's anything worth rendering.

*What would reverse it:* frame times on the largest maps suffering from UI-thread work (check at
0.4 with models, and at 0.6 with realtime lighting). The render mirror is already built from
ChangeSets, so moving it to its own thread changes only who consumes them.

### D13: A thin in-house layer over raw Vulkan 1.3; not QRhi, not NVRHI

Instance, device, swapchains, resources and pipelines go through a small `render::` wrapper over
Vulkan 1.3, using volk (loader) and VMA (allocation).

Device baseline:
- **dynamic rendering**, **synchronization2**, **descriptor indexing** (one bindless texture
  heap), and **buffer device address**;
- `VK_KHR_ray_query` + `acceleration_structure` detected and reported, but optional until 0.7;
- BC1–BC7 texture formats required, which is every desktop GPU, so textures upload still
  compressed.

The render layer creates the `VkInstance`. `ui/` wraps it in a `QVulkanInstance` with
`setVkInstance()` and asks for `VkSurfaceKHR`s from `QVulkanInstance::surfaceForWindow()`, so
`render/` never links Qt (D5).

Turned-down alternatives:
- **QRhi.** It integrates with Qt windows trivially. But it has no ray tracing, its compute and
  bindless support is limited, and its API is only semi-public (no compatibility promise across
  Qt minors). The 0.7 baker would have to bypass it anyway.
- **NVRHI** (MIT, Vulkan + D3D12, has ray tracing). It's the strongest "don't write your own
  RHI" option. But a second backend has no value: Strata already dropped macOS and everything
  else speaks Vulkan. It would also put its abstractions between us and the ray-query baker,
  which is the one place where low-level control matters.

Accepted cost: we own synchronization, barriers and resource lifetime. Validation layers are
mandatory in debug and in CI (D20).

*What would reverse it:* needing D3D12, for example if a Windows driver class turns out to be
unreliable on Vulkan. Even then, porting the thin layer to NVRHI is cheaper than having started
there.

*Spike result (0.1.1):* `QVulkanInstance::setVkInstance` plus one swapchain per viewport window
works on RADV (Mesa 26.0.8) under Wayland and XWayland, with recreate on resize and out-of-date.
Do not rely on `SurfaceAboutToBeDestroyed` to release swapchains: Qt does not deliver it when it
recreates a native window on Wayland, so viewports must never be reparented after creation.

### D14: Shaders are GLSL, compiled to SPIR-V at build time with glslc and embedded

Shaders live in `render/shaders/*.glsl` and a CMake rule compiles them with glslc (already
installed). SPIR-V is embedded as `constexpr` arrays. Debug builds also support hot-reloading
shaders from disk.

The alternative is Slang (Khronos-hosted). It has modules, generics, cleaner ray-tracing
syntax, and could share code with an HLSL path. It adds a compiler dependency that isn't
installed, and 0.1's shaders are trivial.

*What would reverse it:* the 0.6/0.7 shader families (clustered lighting, the baker, PBR
approximation) needing real code sharing or generics. Switching is then a per-file port, because
the pipeline layer consumes SPIR-V either way.

### D15: One viewport type; "2D" is a preset; tools see a `ViewContext`, never a view kind

Implements the owner's requirement.

```
Viewport = Camera × DisplayMode × Overlays
  Camera      = { projection: Perspective{fov} | Orthographic{height},
                  orientation: Free | AxisLocked{±X|±Y|±Z},
                  position, rotation, controller: Fly | Orbit | Pan2D }
  DisplayMode = Wireframe | Flat | Textured | (Lit: 0.6) | (Baked: 0.7)
  Overlays    = grid, entity helpers, bounds, normals, …   (toggles)
```

- The **"Top/Front/Side" presets** are `Orthographic + AxisLocked + Wireframe + grid`. The
  **"Camera" preset** is `Perspective + Free + Textured`. Users create, split and close viewports
  freely and change any field of any viewport at runtime.
- **Tools** receive a `ViewContext`: cursor ray, projection kind, view direction, the active
  `WorkPlane`, grid and snapping. Behaviour that differs in ortho comes from a `WorkPlane`
  policy, never from `if (is2D)` in a tool. For example, "new brush depth in an axis-locked view
  comes from the selection's bounds".
- **Layout** (D16): the viewports live in a dedicated central viewport area, a split tree of
  panes the user can split horizontally or vertically, resize, maximize and close. They are
  separate from the dockable side panels. Each pane hosts one Vulkan child window.
- **Per-map views:** Strata stores up to 4 views in `viewsettings/views/v0–v3` (`"3d"`,
  `"position"`, `"angles"`, zoom). Apex reads them into the first four panes and writes the first
  four panes back, so camera positions survive a trip through Strata Hammer. The full layout,
  with any number of panes, is a per-user setting.

The alternative is making viewports themselves dockable panels (Qt-ADS dock widgets).
Maximum flexibility: tear a viewport off to a second monitor. But every viewport becomes a
floating native child window inside the docking system, which is the most fragile combination
on Wayland (Bite 6). Users also end up with layouts where tools have no obvious "main" view.
Tearing off to a second monitor is possible later as a top-level window that hosts its own split
tree.

*What would reverse it:* the P0 Wayland spike showing a native Vulkan child window inside a
splitter is no more reliable than one inside a dock widget. Then viewports could just be docks.

*Spike result (0.1.1, `spikes/wayland-vulkan`):* the reversal condition did not trigger. A native
Vulkan child inside a QSplitter works on Wayland and XWayland (resize, keyboard once the container
forwards keys and takes widget focus on click, fly-cam capture via local-position fallback on
Wayland and centre-warp on xcb). As a dock widget it fails on Wayland: Qt-ADS floating gives a
fatal `wl_subsurface no parent` protocol error, ADS's drag-to-dock overlay hangs, and plain
`QDockWidget` float/redock destroys the VkSurfaceKHR without notifying the window and then
crashes in libwayland. Viewports stay in the splitter; a tear-off must be a top-level window with
its own split tree, created once, not a reparent.

### D16: Qt Widgets with a token-based custom style and Qt-ADS docking; no QML in 0.1

Qt Widgets runs the shell, inspectors, trees and dialogs. Qt Advanced Docking System (LGPL-2.1)
handles the side panels. Looks come from a single **design-token table** (colours, spacing,
radii, fonts) applied through a QSS template plus a small `QProxyStyle` for what QSS can't
reach. Dark is the default, with light from the same tokens. Strata Hammer's `-theme` KV format
is *not* adopted; we only borrow ideas from it.

The alternative is QML/Qt Quick Controls. It's better at animation, transitions and a "modern
app" feel, and `QQuickWindow` can host Vulkan. It's turned down because an editor's surface area
is dense trees, tables and property grids with heavy keyboard use, where Widgets is far more
mature. Mixing QML and Widgets in one window (`QQuickWidget`) costs a render pass per panel.
`QQuickWidget` can still host individual QML panels later where they earn it.

*Spike result (0.1.1):* Qt-ADS 4.4.1 builds against Qt 6.10 (needs `qt6-base-private-dev`) and
docks fine, but it must not host native Vulkan windows on Wayland (see D15). Side panels contain
only ordinary widgets, so D16 stands; ADS on xcb and with plain widgets was not exercised.

*What would reverse it:* the styled Widgets shell failing the owner's "clean modern UI" bar
after the 0.1.10 review. The token table carries over to QML, so only the views get rewritten.

### D17: Apex owns the virtual filesystem; SourcePP is used only behind adapters in `assets/`

`assets::Vfs` resolves paths across:
- `gameinfo.txt` `SearchPaths` in order, with `+`-combined path IDs (`game+mod+default_write_path`),
  the `|gameinfo_path|` token, `custom/*` globbing, and direct VPK entries
  (`portal2/portal2/portal2.vpk` → `portal2_dir.vpk`);
- `cfg/mounts.kv` Steam-app mounts (app ID → Steam library path via steampp; `vpk` /
  `mod_folder` / `head` / `required`).

Lookups are **case-insensitive on every OS** (Bite 4). VPKs go through vpkpp, VTFs through vtfpp,
FGDs through toolpp, Steam discovery through steampp. Each sits behind an `assets/` interface,
so no SourcePP header escapes `assets/`.

The alternative is SourcePP's `fspp`. It's marked incomplete with an unstable interface, and the
mount semantics are the part most specific to Strata. The adapters also mean a SourcePP licence
or API change touches one directory.

*What would reverse it:* fspp maturing to cover Strata mounts, in which case `Vfs` becomes a thin
shim over it.

### D18: Apex has its own lossless KV1 codec in `core/`

The tokenizer keeps source spans. Trees preserve **order and duplicate keys**. Values are raw
text until read through a typed accessor. It supports:
- `[$CONDITION]` suffixes (gameinfo, VMT);
- `#base` / `#include`;
- **escape handling as a per-profile mode**: `Strata` decodes `\n \t \" \\`, `Legacy` treats
  backslash as literal.

The writer emits Hammer formatting (D7). It's fuzzed with libFuzzer under Clang, and backs the
VMF, VMT, gameinfo, mounts.kv and settings readers.

The alternative is kvpp or srctools' parser. Neither guarantees span retention for D7's
byte-identical writes, and a map-based store would lose duplicate keys, as the corpus's 49
repeated `visgroupid` keys show.

*What would reverse it:* nothing short of kvpp adding span-preserving trees, and even then the
codec is small enough to keep.

### D19: Interop target: files open losslessly in Strata Hammer, and Apex keeps Strata's markers

Apex keeps `versioninfo` as found, and writes `"editorextension" "strata"` on maps it creates,
because that's the marker Strata Hammer and srctools key on. An Apex identity is added as an
extra `versioninfo` key (`"apexversion" "0.1.3.142"`) rather than by replacing the marker.
`viewsettings` keeps every Strata key; `nInstanceVisibility` and `views` are read and written.

The alternative is writing `"editorextension" "apex"`. That's more honest provenance, but it
risks Strata Hammer and the HammerAddons tooling not enabling Strata behaviour (such as
`point_data` trust) for our files. The 0.1.1 P0 checks how Strata Hammer reacts to both values
and to an unknown extra key.

*What would reverse it:* the P0 showing Strata Hammer strips unknown `versioninfo` keys (then
the Apex marker moves to a comment-free location, or is dropped), or that it ignores
`editorextension` entirely (then writing "apex" costs nothing).

**Probe result (2026-10-20):** Hammer rewrites `"editorextension" "apex"` to `"strata"`, and
deletes an unknown `versioninfo` key and an unknown top-level block on save. Consequences:
- Apex writes `"editorextension" "strata"` and never `"apex"`.
- `"apexversion"` is dropped by the first Hammer save, so it is a convenience for files Apex last
  saved, not durable provenance. Nothing in the format relies on it.
- Apex-specific data that must survive Hammer cannot live in unknown keys or blocks. A sidecar
  file, or an `entity` with a registered class, are the options if 0.2+ needs it.
- `point_data` 0.5 off its `plane` loaded as a flat face with no warning, and the mismatched
  point was written back unchanged. So Hammer does not repair stale `point_data`, and a
  Hammer-saved file can carry `point_data` that disagrees with `plane`. D8's rule (trust
  `point_data` only within `kPointDataTrustEps`, otherwise derive from planes) is therefore needed
  for real input. Which of the two Hammer renders from is not distinguished by this probe; the
  flat face suggests `plane`.

### D20: Tests: committed fixtures plus the P2CE corpus gate every CI run; GPU tests run on lavapipe and on real hardware

CI is local (D22), so the P2CE install is always available to it. The corpus moves from
"optional" to **part of the gate**.

- **Committed fixtures** (`tests/fixtures/`) are small hand-written or Apex-authored VMFs and
  KVs, under MIT. They cover every codec path, including those the corpus lacks: escapes,
  conditionals, duplicate keys, CRLF/LF, `point_data` that disagrees with `plane`, and ±65536
  coordinates. They're the only test data a checkout needs, so tests still pass for anyone
  without P2CE.
- **Corpus tests** read `APEX_P2CE_DIR`. They skip cleanly when it's unset (ad-hoc builds,
  future contributors); `tools/ci.py` requires it for the full gate, while `--fixtures-only`
  records the corpus stage as skipped. **No Valve or Strata content is ever committed.**
- **srctools cross-check:** a Python script compares Apex's parse against srctools' parse
  (counts, IDs, planes, keyvalues) over the corpus, run by `tools/ci.py`.
- **GPU tests** render offscreen twice per run, on Mesa **lavapipe** (deterministic golden
  images) and on the **RX 6600 (RADV)** (catches real-driver issues). Validation layers are on and
  validation errors fail the test. Golden images are compared with a tolerance against the
  lavapipe reference. The Windows VM (D23) runs the non-GPU tests only.
- doctest for unit tests; libFuzzer targets for KV1 and VMF (a 10-minute fuzz pass with each CI
  run).

*What would reverse it:* lavapipe missing a required feature (D13's baseline is all core 1.3,
which lavapipe supports, but confirm in P0), in which case golden images come from RADV alone,
with a looser tolerance.

### D21: A face's identity is its VMF side ID, carried through geometry rebuilds by plane matching

Raised in review as a consequence of D6 (sides by value) plus D8 (hull rebuilds).

Every face in a `Solid` carries its `SideId`. That ID is what face selection, `info_overlay`
`sides` lists, `info_overlay_transition`, undo references and ChangeSet dirty flags use, never a
face index. `Document` keeps a `SideId → (Handle<Solid>, face index)` index, updated from
ChangeSets.

When a geometry operation rebuilds a polyhedron (vertex edit, clip, carve, merge from 0.3; the
plane-derivation check in 0.1.6), `geometry::matchFaces(old, new)` pairs new faces with old ones
by plane: the normal within `kNormalMatchEps` and the distance within `kPlanarEps`. Matched faces
keep their `SideId`, material, UV axes, lightmap scale and smoothing groups. Unmatched new faces
get a fresh `SideId` and inherit texture data from the old face whose normal is most aligned.
Faces that disappear are reported in the ChangeSet, so overlays referencing them can be flagged
(0.8).

Turned-down alternatives:
- **Positional index** (solid, face index). Trivial, but any rebuild reorders faces, and
  references silently point at the wrong face.
- **Faces as their own arena nodes.** Stable handles, but it reverses D6's self-contained solid
  snapshots and adds a handle chase to every per-solid walk.

Accepted cost: a matching pass per rebuild (O(old × new) faces, tiny in practice) and the
`SideId` index.

*What would reverse it:* a geometry operation where plane matching gives visibly wrong texture
inheritance in common cases (0.3 vertex tool testing), in which case the tool supplies explicit
face correspondences and matching becomes the fallback.

*Reversed in part by [plan 0.3](0.3.md) (D2, D3):* the condition held before user testing (any vertex
move tilts every adjacent face, so plane matching loses all of them). Tools that know the
correspondence supply it to `Transaction::rebuildSolid` (the vertex tool by vertex sets, the clip tool
trivially), and `matchFaces` is the fallback for carve, hollow, merge and primitives, whose surviving
faces keep their planes. The `SideId` rules above are unchanged.

### D22: CI runs locally on the owner's machine, through `tools/ci.py`

The owner chose not to use a hosted forge for CI for now. `tools/ci.py` is the single entry
point. It:
1. checks that `APEX_P2CE_DIR` is set and the corpus is present;
2. increments the BUILD counter (D1);
3. configures and builds the `linux-gcc`, `linux-clang` and `linux-asan` presets, then runs unit,
   corpus, srctools cross-check, fuzz and GPU tests (D20);
4. syncs the tree to the Windows VM and builds and tests `windows-msvc` there (D23). By default
   (`--windows auto`) this runs only after build files or platform-sensitive code changed since
   the last green Windows run; `--windows always` is the gate before tagging a sub-milestone;
5. runs the `THIRD_PARTY.md` licence check (D4) and the layer-include check (Bite 9);
6. writes a summary report to `build/ci/<build>/report.md` and exits non-zero on any failure.

A `pre-push` git hook (opt-in) runs a fast subset. `--fixtures-only` still runs the fuzzer; use
`--fuzz-seconds 20` for a quick iteration run (the full gate defaults to the 600-second exit
criterion), or `--fuzz-seconds 0` to record it as explicitly disabled.

Gains: free, private, and the full corpus plus a real GPU on every run. Costs: there's no gate
for outside contributors until a hosted CI is added; CI capacity is the owner's machine; and
the scripts must stay portable enough to move to a hosted runner later (no hard-coded paths
except through environment variables).

*What would reverse it:* outside contributors arriving, or the repo going public on a forge.
Then add hosted CI for the fixture-only gate, and keep `tools/ci.py` as the full local gate.

### D23: Windows is covered by a local Windows VM driven from `tools/ci.py`

This keeps MSVC honest without hosted CI. A libvirt/QEMU **Windows 11 guest** with Visual Studio
Build Tools (MSVC 17.10+), CMake, Ninja, Python, an OpenSSH server, Qt 6.10 for MSVC (via
aqtinstall) and the Vulkan SDK headers and loader. `tools/ci.py` starts the VM if it's
stopped, syncs the working tree over SSH (`git bundle` of HEAD + a patch for uncommitted
changes, so the VM never sees untracked junk), runs the `windows-msvc` preset build and the
non-GPU tests, copies back the logs, and shuts the VM down.

The corpus is not copied into the VM. Windows runs fixtures only, because corpus behaviour is
OS-independent apart from path case, which Linux tests more strictly anyway.

Turned-down alternatives:
- **Linux-only until 0.5.** Lets MSVC incompatibilities pile up for four milestones and land at
  once.
- **clang-cl cross-checks without running anything.** Misses MSVC-compiler-specific behaviour and
  runs no tests.

Accepted cost: one-time VM setup (a Windows licence, ~60 GB disk, ~6 GB RAM while running) and
slower CI runs.

*What would reverse it:* a hosted CI with Windows runners being adopted (D22's reversal), which
makes the VM redundant.

## 2. Where the seam goes

```
  app/        executable: startup, game/profile selection, wiring. Links everything.         [Qt]
     |
  ui/         main window, Qt-ADS panels, viewport split tree, viewport host windows,          [Qt]
     |        theme tokens, dialogs. Converts std ↔ Qt types. Creates QVulkanInstance from
     |        render's VkInstance and hands VkSurfaceKHRs down.
     |
  viewport/   Viewport, Camera, controllers, DisplayMode, ViewContext, WorkPlane,          [no Qt]
     |        layout *model* (the split tree as data). Input arrives as apex::InputEvent.
     |
  render/     Vulkan device/queues, swapchains (given a VkSurfaceKHR), bindless heap,      [no Qt]
     |        pipelines, render mirror (consumes ChangeSets), offscreen render for tests.
     |
  assets/     Vfs (gameinfo, mounts, VPK, case-insensitive), VMT, VTF→GPU-ready blocks,    [no Qt, no GPU]
     |        FGD class table, game profiles. Only place SourcePP headers appear.
     |
  geometry/   convex polyhedron (double), point_data reconciliation, validity, UVs,          pure
     |        triangulation, tolerances.hpp.
     |
  document/   VMF schema, Document arenas + handles, Transactions, undo stack,               pure
     |        ChangeSet, VMF codec (lossless, D7).
     |
  core/       math (glm), Handle<T>, KV1 codec (D18), Result/Error, logging, JobPool,          pure
              string/path utilities.
```

`document` depends on `geometry`: a `Solid`'s value type *is* a polyhedron. `assets` depends on
`core` only and knows nothing of documents. `render` depends on `document` (to mirror it) and
`assets` (for textures), never the reverse. `viewport` depends on `render` for picking rays and
camera matrices, and on `document` for work-plane anchoring from 0.2. The link graph enforces
these edges, and a CI script checks that no `#include` crosses upward.

## 5. Things that will bite

**1. Someone will store keyvalues in a `std::map` or `unordered_map`.** It's the obvious
container, and it silently drops the second `visgroupid` (49 cases in the corpus) and every
repeated output name. Defence: the KV1 tree and `Entity::keyvalues` are ordered multimaps by
type, `operator[]` doesn't exist, and fixture test 0.1.3 case 3 fails on regression.

**2. Someone will reformat a number that nobody edited.** Parsing `15.9999` to double and
printing it back gives `15.9999`… until it doesn't (for example `1e-05`, `-0`, or `0.1`
round-tripping through `%g`). Every such change is a spurious diff for the whole team. Defence:
D7's raw-text retention, so untouched values are never printed from a double, plus 0.1.4 case 2
over all 512 files.

**3. Someone will treat side IDs and solid IDs as one space, or use a face index as identity.**
They collide in 180 corpus files. Merging them and "fixing" collisions renumbers sides, which
breaks overlay `sides` lists and `info_overlay` references. A face index looks equivalent until
the first hull rebuild reorders faces. Defence: two allocators with distinct types
(`SolidOrEntityId`, `SideId`), so mixing them doesn't compile; no public API takes a face
index except the kernel's internals (D21).

**4. Path lookups will work on Windows and fail on Linux.** Source paths are case-insensitive, and
VMTs reference `Tools/ToolsNodraw` while the file on disk is `toolsnodraw.vmt`. Defence: `Vfs`
only exposes case-insensitive lookups, backed by a lower-cased index. The 0.1.7 test does a
case-mismatch lookup on Linux.

**5. The plane-point winding will get inverted somewhere.** That turns every brush inside out, or
gets "fixed" with a flip that hides the real bug. Defence: one function derives plane normals
from VMF points, and is documented with the Source convention. A fixture with known
outward-facing normals tests it, and the kernel rejects inverted input instead of flipping it
(0.1.6 case 5).

**6. Native Vulkan child windows will misbehave on Wayland.** Resize flicker, lost keyboard focus
when the cursor moves into a viewport, broken pointer capture for fly-cam, wrong scale on HiDPI.
They all show up late, because developers test on one compositor. Defence: the 0.1.1 spike on
Wayland and XWayland; viewports in a splitter rather than docks (D15); and a manual test checklist
in the 0.1.10 exit review.

**7. A background job will read a live node.** It's tempting because the handle is right there,
and it races with the next transaction on the main thread. Defence: `JobPool::submit` only
accepts callables whose captures contain no `Handle<T>` or `Document&` (a static assertion over
the closure type via a `JobPayload` concept), so payloads are copies by construction.

**8. "Fix the coordinate system" will be done in the geometry.** Source is Z-up and Vulkan's clip
space is Y-down, and someone will flip a mesh to make a view look right. Defence: the only basis
change lives in `Camera::projection()`, and the golden-image tests catch any mirrored output.

**9. A layer will quietly include an upper one.** For example `render/` including a `ui/` header
"just for a type", or `document/` pulling a Qt header through a utility. Defence: the CMake
target graph, plus a CI script that scans `#include`s per layer against §2.

**10. The corpus will end up in the repo.** Copying `test1.vmf` into `tests/fixtures/` for
convenience redistributes Strata/Valve content. Defence: corpus tests only read
`APEX_P2CE_DIR`, `.gitignore` covers `corpus/`, and fixture files carry an "Apex-authored"
header comment that CI checks for.

**11. Undo memory will grow invisibly.** A drag that commits every mouse-move snapshots the whole
selection 60 times a second. Defence: drags merge into one undo entry (D10), the cap is enforced,
and the undo stack exposes its byte size in the status bar in debug builds.

## 6. Sequencing

1. **0.1.1** first, alone. Its P0 findings can change D7, D13, D15, D16 and D19 before code
   depends on them. Inside it, the Windows VM setup (D23) runs in parallel with the Wayland spike
   and the skeleton. The Strata Hammer probe needs the VM, so it comes after it.
2. **0.1.2 → 0.1.3** serial (KV1 needs core).
3. Then two parallel tracks:
   - **Track A (document):** 0.1.4 → 0.1.5 → 0.1.6. Serial: the codec, then arenas over it, then
     the kernel those arenas hold. 0.1.6 can start its pure polyhedron work alongside 0.1.4,
     and integrate after 0.1.5.
   - **Track B (assets):** 0.1.7 → 0.1.8. Needs only 0.1.3.
4. **0.1.9** needs 0.1.5 (ChangeSets), 0.1.6 (meshes) and 0.1.8 (textures). The device, swapchain
   and pipeline work can start once 0.1.1's spike has settled D13.
5. **0.1.10** last.

Merge order puts the pure core first: nothing in `render/` or `ui/` merges before the layer
under it has passed its corpus cases.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-10-20. Each was presented with its alternatives. All of
the draft's choices were confirmed, and the review added three decisions (D21–D23). They're
recorded here with the alternatives turned down, so a later reader does not reopen them without
new information.

- **D5: Qt-free core.** Turned down: QtCore throughout the lower layers. Revisit only if the
  std↔Qt conversion layer becomes a meaningful share of `ui/`.
- **D6: arenas + generational handles, sides by value.** Turned down: a polymorphic object tree
  (Hammer/TrenchBroom), and an ECS (EnTT). Revisit only on profiler evidence that handle
  resolution dominates hot loops.
- **D7: byte-identical untouched content.** Turned down: canonical writing in Hammer's format,
  and canonical writing in an Apex format. Revisit if the 0.1.1 probe shows Strata Hammer
  rewrites whole files on every save.
- **D8: vertex-authoritative brushes.** Turned down: plane-authoritative, and dual sources of
  truth. Revisit if 0.1.6 case 4 shows VBSP output differs, or if planarity repair proves
  unreliable.
- **D21: face identity = SideId with plane matching** (added in review). Turned down: positional
  face index, and faces as arena nodes. Revisit if 0.3 testing shows wrong texture inheritance in
  common cases.
- **D10: snapshot transactions for undo.** Turned down: the command pattern, and a persistent
  immutable document. Revisit if realistic sessions exceed the memory cap.
- **D13: raw Vulkan 1.3 with a thin wrapper.** Turned down: NVRHI, and QRhi. Revisit only if a
  D3D12 path becomes necessary.
- **D16: Qt Widgets + design tokens + Qt-ADS.** Turned down: full QML, and a Widgets/QML hybrid
  from day one. Revisit if the 0.1.10 UI review fails the "clean modern UI" bar.
- **D15: central split-tree viewport area.** Turned down: viewports as dock widgets, and a fixed
  Hammer-style grid. Revisit if the Wayland spike shows docks are just as robust.
- **Roadmap ordering: lighting at 0.6/0.7, after compile (0.5).** Turned down: realtime
  lighting moved to 0.4, and a throwaway vertical slice in 0.2.
- **D3: system Qt + CPM-pinned sources.** Turned down: a vcpkg manifest, and git submodules.
  Revisit when Embree/OIDN arrive (0.7), or past about 15 dependencies.
- **D1: BUILD = CI run counter.** Turned down: commits since tag, and total commit count. Now
  sourced from the local runner (D22).
- **D4: relicensing target GPLv3-or-later.** Turned down: keeping GPLv2 possible (would ban
  Apache-2.0: Embree, OIDN), and deciding at switch time.
- **D22: local CI via `tools/ci.py`** (added in review). Turned down: GitHub Actions, and other
  hosted forges. Revisit when outside contributors arrive or the repo goes public.
- **D23: Windows VM driven by local CI** (added in review). Turned down: Linux-only until 0.5,
  and clang-cl cross-checks only. Revisit if hosted Windows CI is adopted.
