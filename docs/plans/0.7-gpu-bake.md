# 0.7: GPU bake backend

**Status (2026-11-04): slices 1 and 2 have landed and the owner checked them in the editor; the Windows run is still owed.** Follows 0.7 D3/D4: the baker queries the
scene BVH with `VK_KHR_ray_query`, and the Embree baker stays as the fallback. OIDN is out of scope for now
(no visible noise in the editor).

**Why.** The Baked view takes about 7 s to converge on test1 with the tuned defaults (8 bounces, 4 passes),
which is too slow for fine light adjustment. Each luxel's work is independent, so it maps directly to a
compute dispatch.

## Shape

- **Scheduling stays on the CPU.** `lighting::Baker` keeps passes, budgets, selections, `adopt`, `resolve`, and
  the sums and counts. Only the per-luxel sampling (`sample`, `sampleBounce`) moves behind a kernel interface:
  given a level, a list of (face, luxel range) items and, for bounce, the level's source snapshot, the kernel
  returns each luxel's four-sample sum. The CPU kernel is today's code, unchanged. `BakeSession`, the diff,
  hybrid seeding and the controller do not change.
- **Geometry.** `BakeOcclusion` also keeps the caster mesh and its per-triangle tables (sky flag, bake face or
  none) that `bakeCastersFromDocument` already builds. The GPU kernel builds one BLAS/TLAS from them with
  `render::Accel`, so `faceOf` and `isSky` become buffer lookups.
- **Parity, not bit-identity.** The GPU uses 32-bit hashing and float maths. Point, spot and sun lights with
  hard shadows must match the CPU closely. Sky and bounce must match statistically (means within a few percent,
  and the energy tests hold).
- **Threading.** `Context` is "one graphics queue, main thread only" (0.1 D12), and `BakeSession::tick` runs on a
  JobPool worker. Slice 1 runs the kernel only where the caller owns the thread (tests and `render_pose`).
  Slice 2 picks between a queue mutex in `Context` and dispatching from the controller's main-thread poll.

## Slices

1. **GPU kernel, headless.** Kernel interface; GPU direct, sky and bounce; parity tests against the CPU kernel
   (skipped without ray query); `render_pose --bake-backend cpu|gpu` with wall-clock bake time.
2. **Editor.** Threading decision; a Bake device setting (Auto / GPU / CPU) with CPU fallback; tick budget
   retuned for GPU batches; hybrid and incremental restarts on the GPU path.
3. **Measure.** Time to converge on test1 and the corpus, CPU against GPU, on the RX 6600; the P0 diff
   (`--diff baked,vrad`) confirms that the GPU path keeps parity with VRAD.

## Slice 1 result (2026-11-04)

`render::GpuBakeKernel` (`src/render/gpu_bake.cpp`, `shaders/bake.comp.glsl`) behind `lighting::BakeKernel`; the
CPU path is unchanged. One BLAS/TLAS over the caster mesh retained in `BakeOcclusion::geometry`, one compute
dispatch per `Baker` step, one bounce-source buffer per level.

- **Speed.** test1, tuned defaults (8 bounces, 4 passes), `render_pose --mode baked` to idle on the RX 6600:
  CPU 5.87 s, GPU 0.155 s (38x).
- **Parity with the CPU kernel.** Direct point, spot and sun with an occluder: identical to 1e-3 per luxel.
  Sky and two bounces (corner scene): coverage-weighted means 0.9999, 0.9998, 0.9988 of CPU. Sealed room: each
  bounce carries 0.50 of the previous one (albedo 0.5). The test1 renders differ by 0.17/255 on average, at
  most 2/255.
- Validation layer clean in all five `render: gpu bake*` tests.

## Slice 2

- Editor Baked/Hybrid sessions select Auto, GPU or CPU; failed GPU creation falls back to CPU with a reason.
- Queue calls are serialized; worker one-shot commands use a separate pool and fence lock. GPU ticks share the
  graphics queue with frames, using a short slice and adaptive dispatch budget.
- Baker batches faces, caches bounce snapshots by upstream generation, and publishes only changed faces.
- `render_pose --bake-backend gpu` also drives Hybrid sessions.
- Measured (RX 6600, test1 with the pillar moved 64 units, the editor's session path through `render_pose
  --mode hybrid`): rebaking the 220 dirty faces to idle takes 3.81 s on CPU, 0.30 s on GPU. Hybrid vs VRAD
  is unchanged: median 1.000 both, within 10% 65.8% (CPU) and 66.1% (GPU), bounce ring 98.6% / 99.1%.
- Owner check in the editor (2026-11-04): it looks right and bakes much faster.
- RADV with `VK_LAYER_VALIDATE_SYNC=1` crashes or hangs every ray-query test, including the 0.7.3 smoke test
  that slice 2 does not touch; plain validation on RADV (20 runs) and sync validation on llvmpipe are clean.
