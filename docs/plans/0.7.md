# Apex: 0.7 implementation plan: Lighting II: baked preview

**Status (2026-11-01): draft, not yet reviewed by the owner.** Written against `0.6.8-release`. The
decisions below are proposals; each records what would reverse it, and none is confirmed until the review
appendix says so. The realtime indirect term for the unbaked view is explored in
[0.7-realtime-gi.md](0.7-realtime-gi.md); D8 proposes its method (a ray-traced irradiance probe volume on
D3's BVH) and 0.7.6 schedules it.

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.7: Lighting II: baked preview.** Luxel charting matching VBSP (`lightmapscale`, face splits, BSP v25
> limits), a progressive GPU baker (Vulkan ray query) with an Embree CPU fallback, bounce using VTF
> reflectivity, bumped lightmaps, sky, OIDN denoise, incremental invalidation with camera-priority
> scheduling, a background VRAD round-trip mapped back through `hammerfaceid`, an A/B compare view, and a
> luxel density view.
> **Exit:** preview vs VRAD error is under a threshold on the reference maps, and the preview re-converges
> interactively after moving a light.

The design is [research.md §4](../research.md), tiers 2 and 3. This document does not supersede
research.md or the roadmap; where they disagree, those win, and the 0.7 release lists the amendments.

0.7 also owes answers that earlier plans handed forward:

- **Bounce and AO** (0.6 D8, §4): tier 2's baker, and the realtime stand-in shown before a bake (D8).
- **The preview reads very dark** (0.6 release, owner's note on 2026-11-01): bounce is about half of
  test1's light. Fixed by D8 in the unbaked view and by the bake itself in the baked view.
- **The VRAD round-trip view** (0.6 §4, tier 3): D5.
- **A uniform surface-response scale** (0.6 release: the game reads about 0.8× Apex, fullbright too):
  measured in 0.7.0's P0 before any bounce work is tuned against it.

**What 0.7 inherits.**

- **The light model** (`lighting/`, 0.6 D1): `Light` values from keys after `missingEntityDefaults`, a CPU
  `irradiance()` with the measured (c + c²)/2 response, the spot axis cosine and the closed-form sky ambient.
  The baker's direct term is this model; it is not re-derived.
- **The parity harness** (`tools/light_parity.py`, 0.6.2): fragment reconstruction, HDR lump decoding, patch
  selection and the tolerance statistics. Today it runs `-bounce 0`; 0.7 runs it with bounce.
- **Lit** (0.6 D4–D7, D13–D16): clustered forward+, the shadow atlas, RGBA16F + reversed-Z D32 scene targets,
  the frame block, the CPU sky-visibility probe grid, piecewise-sRGB tone mapping with fixed exposure.
- **The compile path** (0.5): snapshots, native `vbsp`/`vrad`, `bsppp`.
- **Device features**: `VK_KHR_ray_query` and `acceleration_structure` are detected (`context.cpp:265`) but
  not enabled.

**What 0.7 does not have.**

- **A correct caster set for entity models.** Editor-only models cast shadows today (D1). This is fixed
  first, because every later lighting comparison inherits it.
- Luxel charting, a BVH over map geometry, a baker, a denoiser, lightmap storage in the renderer, a compare
  view, or a density view.
- A real indirect term in the unbaked Lit view. 0.6.9's constant ambient fill and depth AO (the
  "Approximate bounce" overlay, `136c89c`) are only a stand-in: the fill is uniform and AO darkens dim pixels,
  it adds no light from surrounding surfaces.

## 1. Decisions

### D1: Only geometry that reaches the compiled map casts; editor-only entity models never do

**The bug.** `RenderMirror` adds every entity model group to `list.shadowCasters`
(`render_mirror.cpp:2103`), gated only by `disableshadows`. The model comes from
`document::entityDisplayModel`, which falls back to the FGD's `studio()`, `studioprop()` and `lightprop()`
helper models when the entity has no `model` key (`entity_helpers.cpp:50`). So editor stand-ins (the lamp
drawn for a `light_spot`, the figure on an `info_player_start`, NPC and logic placeholders) cast shadows in
Lit, and a light's own helper model can shadow the light it represents. The game and VRAD see none of these.

**The rule.** An entity model casts only when its model comes from the entity's own `model` key and the
entity's class reaches the compile with that model (props, and brush-less model entities the game draws).
A model supplied only by an FGD helper is a helper: drawn, selectable, never a caster, and never part of the
baker's BVH (D3). `disableshadows` keeps its 0.6 meaning on top of that. Which classes VRAD lets cast
(`prop_static` by default; dynamic and physics props not in the bake) is recorded by 0.7.1's probe, the same
way 0.6.1 recorded brush casting (0.6 D13).

**Where.** `entityDisplayModel` reports the source of the model it returns (key or helper), and
`EntityState` stores it next to `castsShadow`; the caster gate in the model group loop reads both. One
predicate serves the shadow atlas, the baker's scene, and the VMF export check that the BVH and the compiled
map agree.

*What would reverse it:* a mapper workflow that relies on helper models casting (none known), or VRAD
evidence that some helper-model class does block light.

### D2: Luxels are charted the way VBSP charts them, in `lighting/`, on the CPU

Lightmap axes come from each face's texture axes scaled by `lightmapscale`; faces split at the BSP v25 limit
(128 luxels per axis for brushes). Charting is a pure function of a face, so it can be tested against
`bsppp` output face by face through `hammerfaceid`. Displacements stay out until 0.8 (roadmap).

*What would reverse it:* VBSP's splits depending on whole-map state that a per-face function cannot see.

### D3: One scene BVH, built from D1's caster set, serves the GPU baker and the realtime GI

A TLAS over per-brush and per-prop BLAS, refit or rebuilt per touched instance on edit. The baker queries it
with `VK_KHR_ray_query`; Embree 4 builds the same instance list on the CPU as the fallback. D8's
probe volume traces rays against this structure, not a second one.

*What would reverse it:* refit cost per drag on the largest corpus map exceeding a frame, which would make
the baker rebuild only on release.

### D4: The baker is progressive, bumped and HDR, with VTF reflectivity bounce and OIDN denoise

Per luxel: direct from the 0.6 light model, shadowed by BVH rays; sky as hemisphere rays against the
`light_environment` ambient; bounce weighted by the VTF reflectivity vector. Three bump-basis lightmaps plus
flat, stored HDR. Samples accumulate; OIDN 2 denoises the displayed result, never the accumulator.
Incremental invalidation: a light dirties luxels within its range; a brush edit re-charts the faces it touches;
luxels visible to the camera are scheduled first.

*What would reverse it:* OIDN's GPU path unavailable on target hardware at interactive rates.

### D5: The VRAD round-trip runs in the background and is drawn per BSP fragment

Export, `vbsp`, optional `vvis -fast`, `vrad` with the user's flags; read the lighting lump with `bsppp`;
map fragments back through `hammerfaceid`. A face keeps its compiled fragments until it is edited.

### D6: Parity is the 0.6 harness with bounce turned on

`light_parity.py` compares the baker against VRAD at default bounce on the reference scenes, same statistics
and masks. The tolerance is calibrated in 0.7.2's P0 and confirmed by the owner, as 0.6's was.

### D7: The compare and density views are display modes of the existing renderer

A/B (Lit realtime, Apex bake, VRAD round-trip) as a split or toggle on one viewport, labelled with which it is
showing; luxel density as a checker overlay from D2's charts.

### D8: The unbaked Lit view gets a ray-traced irradiance probe volume

**Proposal.** A camera-centred grid of irradiance probes, updated every frame from a budgeted subset of
rays against D3's TLAS (about 64 to 128 rays per probe). Each hit is shaded with direct light (a shadow ray
or the shadow atlas) plus the previous frame's probe irradiance, which gives multi-bounce for free, using
the baker's material table for albedo and VTF reflectivity. Results are blended over time into an octahedral
irradiance map and a depth map per probe; surfaces sample the eight surrounding probes with
depth-weighted visibility so light does not leak through walls. Sky is an emitter (a ray that misses
the BVH), which replaces the CPU `SkyVisibilityGrid`. Later cascades (about 64, 256 and 1024 units) bound the cost on maps spanning ±65536.

The seam is unchanged: an indirect-diffuse term added after direct and sky ambient, before tone mapping,
off in the baked and VRAD views, and labelled in the HUD as an approximation. `indirectMode` is honoured
(Dynamic lights feed the probes, Static ones do not), mirroring the game.

**Why probes, not SSGI.** SSGI only sees what is on screen, changes as the camera orbits, and leaks while
flying. The ceiling in the owner's report is lit mainly by surfaces behind or below the camera, which SSGI
cannot see. VRAD's bounce is diffuse, view-independent and whole-map, which probes match. Voxel/SDF tracing
and light-propagation volumes were rejected (exploration §3). A half-resolution SSGI layer for close-range
detail stays optional and off by default.

**No ray-query hardware.** The fallback is a per-light wide fill limited by the CPU sky grid's visibility,
labelled as such; the baker's Embree path is too slow for live probe updates. Whether to build it depends on
P0 below.

*What would reverse it:* refit cost per drag on the largest corpus map, which would make the probes update only
after release; probes at 64 units failing on 16-unit-thick brushes even with relocation and a normal-offset
bias; or one realtime bounce differing from `vrad -final` by more than a lighting-tolerance the owner accepts.

## 4. Things that will bite

**1. Comparisons inherit the caster bug.** Any capture or parity run taken before 0.7.1 includes shadows from
helper models. *Defence:* 0.7.1 lands first; earlier captures are re-taken.

**2. The BVH and the compiled map disagree.** A caster in one and not the other shows up as a bake error that
looks like a formula error. *Defence:* one predicate (D1) feeds both, and a test exports the map and compares
the compiled static-prop and brush lists with the BVH's instances.

**3. The realtime term makes the baked comparison look wrong.** *Defence:* D8's term is off in the baked and
VRAD views, and every view is labelled (D7).

**4. Probe light leaks through thin walls.** Source brushes are often 16 units thick. *Defence:* the depth map
and relocation in 0.7.6 step 2; the leak test in 0.7.6; P0 measures it before the grid spacing is chosen.

## 5. Sequencing

0.7.1 first: it is small, independent, and every later comparison depends on it. 0.7.2 and 0.7.3 touch
disjoint code and run in parallel after it. 0.7.4 needs both. 0.7.5 needs 0.7.2's harness and can overlap
0.7.4. 0.7.6 needs 0.7.1 and 0.7.3 and the baker's material table, so it starts once 0.7.4 has a first working
version and can overlap the rest of 0.7.4 and 0.7.5. It could slip to a 0.7.x release after the baker lands
without changing the 0.7 exit criteria, which are measured on the baked view.
