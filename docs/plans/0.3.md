# Apex: 0.3 implementation plan: Brush authoring in 3D

**Status: reviewed by the project owner, 2026-10-22; ready for 0.3.1's P0. Amended the same day at
the owner's request:** D19 adds a sub-milestone for read-only Strata addon mounting (0.3.7, from
[addons.md](addons.md)). The material index and face editing move to 0.3.8 and 0.3.9 in this plan.
They hadn't started, and numbers are only fixed when a sub-milestone lands. 0.3.1 landed on
2026-10-22 (tag `v0.3.1`, CI build 58 green including Windows). Every decision in the appendix was put to the owner. All draft choices were confirmed except
D10, where merge now takes the convex hull after a confirmation (with a "don't ask again"
preference) instead of refusing non-convex unions.

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.3: Brush authoring in 3D.** Block tool (draw on a surface or work plane, then extrude),
> primitives (wedge, cylinder, arch, spike, sphere), clip tool (3 points placed on surfaces),
> vertex/edge/face tool with convex-hull rebuild and invalid-state feedback, carve/hollow/merge,
> material browser, texture application and face editing (shift/scale/rotate, justify/fit, align
> to world/face, measure tool). Texture lock under transforms moved to 0.2 (plan 0.2 D7).
> **Exit:** a complete test chamber can be built from nothing without an orthographic view.

This document does not supersede [research.md](../research.md) or the roadmap. Where they
disagree, those win, and the 0.3 release lists the amendments they need once 0.3 lands. Three
decisions change what an earlier milestone said:

- D3 changes 0.1 D21 from "geometry rebuilds pair faces by plane matching" to "tools that know
  the correspondence supply it; plane matching is the fallback". 0.1 D21 named this exact
  reversal ("the vertex tool… supplies explicit face correspondences"), and the P0 test shows
  its condition holds by construction.
- D2 changes 0.2 D4's write call from "a geometry write never adds or removes faces" to "a
  geometry write may add, remove and split faces; the document allocates every new `SideId`".
- D18 records that 0.2.12 landed after `0.2.11-release`, against the roadmap's "nothing of 0.M
  lands after its release", and amends the versioning rule accordingly.

0.3 also owes answers that earlier plans handed forward:

- **Preview geometry for non-affine tools** (0.2 D6, "the 0.3 vertex and clip tools… publish
  preview geometry through the same channel"): D12.
- **`matchFaces` has no production caller** (0.1 D21, 0.2 D4): D2 and D3 give it one.
- **Persistent topology for the vertex tool** (0.2 D4's reversal condition): D7 shows the tool
  needs topology only during a gesture, so 0.2 D4 stands.
- **Exact predicates "may be added at 0.3 if the CSG operations need them"** (0.1 D9): D8.
- **`PickIndex::nearest` "for snapping to vertices later (0.3)"** (0.2 D2): D13.
- **Inspector `material` fields have a disabled browse button "until 0.3/0.4 browsers exist"**
  (0.2 D13): D14 enables it.
- **Spec drift from 0.2.12:** research.md §5/§6 still describe Qt-ADS docks, which 0.2.12 removed
  in favour of area roles. The 0.3 release amends them (§3, spec amendments).

**What 0.3 inherits.**

- **`geometry::ConvexPolyhedron`** (`fromPlanes`, `fromPointData`, `validate`,
  `sourcePlanePoints`, `generateUv`, `uvAt`, `triangulate`, `faceArea`) and **`matchFaces`**
  (tested, never called outside tests).
- **`geometry::solidGeometry(block)`**, the single read path (0.2 D4), and
  **`Transaction::setSolidGeometry`**, the single write path, which today rejects any change to
  the set of side IDs.
- **`Transaction::create`**, which allocates fresh solid and side IDs for a created block, and
  `destroy`/`reparent`, all linear in touched nodes (0.2 D17).
- **`editor::Transform`, snapping (`SnapSettings`, absolute/relative, `snap.suspend`), the modal
  G/R/S transform, gizmos, texture lock** (0.2 D6–D8, D15).
- **`editor::Preview`**: a `NodeId → DMat4` map the mirror applies to existing meshes. It cannot
  show a shape that does not exist yet, or a shape that is not an affine image of the old mesh.
- **`WorkPlaneState`** (pinned / hovered / fallback) and the surface-clipped grid (0.2 D9), built
  for "draw on a surface".
- **`PickIndex`** with `pick`, `frustum` and `nearest(point, radius)`; face selection mode keyed by
  `SideId`; selection highlight of individual sides (0.2.3 E1).
- **`assets::MaterialCache`** (async VMT/VTF, LRU budget, placeholder), `Vfs::list(dir, glob)`, and
  `TextureHeap` (4,096 bindless slots).
- **Renderer overlay primitives:** screen-space `OverlaySegment`/`OverlayTriangle`, drawn last with
  no depth test (the gizmos use them).
- **Area roles and workspaces** (0.2.12): a new panel is a new role, not a dock.
- **The action registry and both presets** (0.2 D15), the keybinding editor and user presets
  (0.2.12). Every new tool action lands in both presets or is explicitly unbound.
- **The release harness:** headless corpus replays, the srctools cross-check,
  `tools/hammer_wine_check.py` (Strata Hammer under Wine, headless) and
  `tools/vbsp_equivalence.py` (native Linux vbsp against a map in isolation).

**What 0.3 does not have.**

- **No tool abstraction.** `EditorSession::Tool` is a two-value enum (`Select`, `Entity`), and
  `ui/viewport_pane.cpp` branches on it. Tool behaviour lives in `EditorSession` (882 lines).
  0.3 adds six tools; adding six more branches to the session and the pane is the obvious path and
  the wrong one. D1.
- **No geometry write that changes topology.** `setSolidGeometry` throws "geometry side IDs do
  not match solid" when a face is added or removed. Clip, vertex edits, carve, hollow and merge
  all add or remove faces. It also throws when a solid with a redundant source side changes shape
  at all ("geometry side IDs have no matching boundary faces"), so such solids cannot even be
  moved today. D2, and P0 tests 1–2.
- **A latent identity loss under vertex edits.** Moving one vertex of a cube tilts the three faces
  that share it. Plane matching (`matchFaces`) then finds no match for those faces, so they would
  get fresh `SideId`s and inherited textures: face selection on them empties, and (from 0.8)
  overlays referencing them break. Nothing hits this yet because nothing rebuilds topology. D3,
  and P0 test 3.
- **No way to write a new solid from a polyhedron.** `Transaction::create` takes a KV1 block;
  there is no `polyhedron → solid block` writer, so the block tool has nothing to call. D4.
- **No convex hull.** The kernel builds from planes or trusted `point_data`, never from a point
  set. The vertex tool and merge both need a hull. D8.
- **Preview cannot show new or reshaped geometry.** D12.
- **No vertex or edge snapping.** `nearest` returns surfaces within a radius, not vertices or
  edges, and nothing snaps in screen space. D13.
- **The VFS cannot enumerate materials.** `Vfs::list` returns immediate files only, and does not
  return directories, so nothing can walk `materials/` recursively across mounts and VPKs. The
  material browser needs a full index. D14, and a P0 measurement.
- **The bindless heap has no eviction policy for browsing.** 4,096 slots, released only
  explicitly. A browser that uploads a thumbnail per visible material through it would compete with
  the map's own textures. D14.
- **No depth-tested world-space overlays and no text in viewports.** Vertex handles, clip planes
  and measurements need both. Qt widgets cannot be drawn over the native Vulkan pane windows on
  Wayland (0.1 D15), so text must come from the renderer or from outside the viewport. D16.
- **No face-edit UI.** Face selection exists, but the only side write is the inspector's raw
  `setSideKeyValue`.

## 1. Decisions

Each records what would reverse it.

### D1: Tools become objects behind one `editor::Tool` interface, and the session dispatches to the active one

`editor::Tool` has: `activate`/`deactivate`; `input(const InputEvent&, const ViewContext&) →
Handled`; `preview() → const Preview&` (D12); `overlay(const ViewContext&) → OverlayList` (D16);
`readout() → ToolReadout` (the header badge and status text); `cancel()`; and the actions it
contributes while active (for example `clip.cycle_keep`). Tools write to the document only through
`EditorSession::edit()`, so selection metadata (0.2 D3) and the one-commit-per-gesture assertion
(0.2 Bite 8) apply to every tool unchanged.

0.3.1 moves the 0.2 Select (with gizmo and modal transform) and Entity behaviour into
`SelectTool` and `EntityTool` with no behaviour change, proved by the existing 0.2 tool, session
and rearrangement tests passing untouched. `EditorSession::Tool` becomes a `ToolId` string from the
registry (`tool.select`, `tool.block`, …). `ui/viewport_pane.cpp` stops branching on tools: it
forwards translated events to the session and draws what the active tool describes.

The reasonable alternative is to keep 0.2's shape: an enum, with each tool's state and methods on
`EditorSession` and a branch per tool in the pane. It worked for two tools and needs no migration.
It's turned down because 0.3 brings the tool count to eight, each with its own gesture state
(block: base then height; clip: up to three points; vertex: element selection and drags), and that
state would all be fields on one class where any tool can corrupt another's. The interface is also
the shape the 0.9 plugin API exposes for custom tools (roadmap 0.9), so building it now avoids a
second migration.

Accepted cost: a migration of working 0.2 code before any new tool lands, and a dispatch layer.

*As built (0.3.1):* `editor/` may include only `document/`, `geometry/` and `core/`
(`tools/check_layers.py`), so tools take an `editor::ToolView` (cursor ray, pane size, a plain camera
snapshot and a picking callback the UI supplies) instead of `viewport::ViewContext`. Input is a
Qt-free `editor::InputEvent` tagged with an `InputSource` per pane, so each pane keeps its own gesture
state and a closed pane's state is dropped (`forgetInputSource`). The 0.2 session methods
(`pointerClick`, `beginGizmoDrag`, …), `EditorSession::Tool::Select` and `ui::TransformInput` remain
as thin forwards, which is how the 0.2 tests pass unedited.

*What would reverse it:* nothing short of abandoning per-tool state. If dispatch overhead ever
shows in profiles, the fix is inside the dispatcher.

### D2: Topology-changing geometry is written in place: one rebuild call keeps the solid, matches faces, and the document allocates every new `SideId`

`Transaction::rebuildSolid(Handle<Solid>, const ConvexPolyhedron&, FaceCorrespondence)` replaces a
solid's shape when faces may appear, vanish or change plane:
- **matched faces** (by D3) keep their side block: `id`, material, UV axes, `lightmapscale`,
  `smoothing_groups`, `dispinfo` (D11) and unknown keys; only `plane` and `point_data` are
  rewritten, and the UV only if the tool changed it;
- **new faces** get a fresh `SideId` from the document's side allocator and a side block built from
  the face they inherit from (material, axes, scale, `lightmapscale`, `smoothing_groups`; never
  `dispinfo` or unknown keys);
- **vanished faces** are removed and listed in `ChangeSet::vanishedSides`, which already exists and
  is already consumed by selection pruning;
- the solid's `NodeId`, VMF `id`, `editor` block and non-side keys are untouched.

Splitting a solid (clip "keep both", carve) uses `rebuildSolid` for the first fragment and
`create` for the rest, each created fragment copying the source block's `editor` block so group and
visgroup membership survive. `setSolidGeometry` stays for same-topology writes and becomes a thin
wrapper. A solid with redundant source sides goes through `rebuildSolid`, whose matching drops the
redundant side as vanished, so those solids become movable (P0 test 2).

The alternative is destroy-and-create: each tool deletes the old solid and creates a new block.
No new transaction call, and `create` already allocates IDs. It's turned down because it loses
the solid's VMF `id` (which compile errors reference, "brush id N", from 0.5), its unknown keys and
its `editor` block unless every tool copies them, and it makes the ChangeSet report a delete plus a
create, so the outliner and selection see a different object.

Accepted cost: a second write call with its own validation; new side blocks need a writer that
emits keys in Hammer's order (`id`, `plane`, `point_data`, `material`, `uaxis`, `vaxis`,
`rotation`, `lightmapscale`, `smoothing_groups`), checked against a Hammer-saved fixture
(`probe-results/e_control_saved.vmf`, `g_side_order_saved.vmf`; corrected in 0.3.1, the first draft
put `point_data` last).

*What would reverse it:* the Strata Hammer acceptance check showing it rejects or rewrites solids
whose side IDs are non-contiguous or out of order after a rebuild. Then rebuilds renumber sides
within the solid, still allocated by the document.

*P0 result (2026-10-22):* Strata Hammer (build 10773) opens and re-saves a box whose six sides are in
reverse order with ids 1057, 1009, 1031, 1012, 1088, 1004, keeping the order and every id
(`probe-results/g_side_order_saved.vmf`). The decision stands.

### D3: Tools that know the face correspondence supply it; plane matching is the fallback

`FaceCorrespondence` is an optional `newFaceIndex → oldSideId` map handed to `rebuildSolid`.
- **The vertex tool** supplies it: a hull face whose vertex set is mostly the moved images of one
  old face's vertices *is* that face, whatever its plane did. A face split by a non-planar move
  (D7) yields several new faces; the largest keeps the `SideId`, the rest are new and inherit from
  it.
- **The clip tool** supplies it trivially: every surviving face is the old face, clipped, and the cap
  is new.
- **Carve, hollow, merge and primitives** pass nothing, and `matchFaces` (plane matching, 0.1 D21)
  decides, which is exact for them because their surviving faces keep their planes.

0.1 D21 chose plane matching and named its own reversal: "a geometry operation where plane matching
gives visibly wrong texture inheritance in common cases (0.3 vertex tool testing), in which case
the tool supplies explicit face correspondences and matching becomes the fallback." The P0 test
shows the condition holds without user testing: any vertex move tilts every adjacent face, so plane
matching loses all of their identities.

The alternative is to widen `matchFaces`'s tolerances (a normal within a few degrees). It would
match small vertex moves, but the threshold is arbitrary, large moves still lose identity, and a
loose threshold makes clip and carve mismatch coplanar-ish faces.

*What would reverse it:* nothing foreseeable; the correspondence is information the tool has and
matching has to guess.

### D4: New solids come from one writer, take the active material, and get face-aligned UVs by default

`geometry::solidBlock(const ConvexPolyhedron&, const NewSolidStyle&) → kv1::Node` writes a
complete `solid` block (plane points, `point_data` in the Strata profile, D2's side key order) that
`Transaction::create` then IDs. Every creating tool (block, primitives, hollow's walls, clip's
second fragment through D2) uses it.

`NewSolidStyle` carries the material (the material browser's active material, D14; `tools/toolsnodraw`
never, unless chosen), texture scale (0.25, Source's default), lightmap scale (16) and the UV
alignment rule:
- **Face (default):** the U and V axes lie in the face plane, aligned to the face's dominant world
  axes; on axis-aligned faces this equals world alignment, and on slopes the texture is not
  stretched.
- **World:** `geometry::generateUv`'s dominant-axis projection (Hammer's world alignment), which
  stretches on slopes.

The choice is a persistent setting (status bar and Preferences), and per-face realignment is
always available afterwards (D15).

The alternative default is world alignment: it's what `generateUv` does today, it tiles seamlessly
across adjacent axis-aligned brushes, and Source mappers know it. It's turned down as the
*default* because 0.3's exit is built in 3D with clipped and vertex-edited slopes, where world
alignment visibly stretches every non-axial face, and on axial faces the two rules agree anyway.

*What would reverse it:* the owner preferring Hammer's world-aligned default; then only the
setting's default changes.

### D5: The block tool is draw-then-extrude: drag the base on the work plane, release, move to set the height, click to commit

1. **Base.** Press on the hovered surface (or the pinned/fallback work plane, 0.2 D9) and drag a
   rectangle in the plane's u/v axes, corners snapped to the work plane's grid (0.2 D8; `snap.suspend`
   applies). The rectangle shows as a ghost (D12).
2. **Height.** Release, then move the pointer: the height follows the pointer's closest point on the
   line through the base along the plane normal, snapped to the grid, defaulting to the last height
   used (initially the grid size × 8). Typed digits set it exactly (the modal transform's number
   entry). Dragging below the plane extrudes the other way.
3. **Commit** with a click or Enter: one transaction, the new solid selected and the select tool's
   scale gizmo available for adjustment. Esc at any stage cancels; right click steps back one stage.

A press-drag with Shift draws a cube-like base (square, height equal to the side). In an
axis-locked view the same steps work on the fallback plane, which faces the camera.

**As built (0.3.2 follow-up).** Block corners use grid + vertices, skipping edge and midpoint
snaps. A committed base plane is remembered for perspective presses over empty space that is not
over the drawn world grid (within its 4096-unit fade); idle hover shows the snapped start, and
Esc clears the last plane. While dragging, the base's side lengths are labelled at its edges. `block.pick_plane` (Hammer Ctrl, Blender
Alt) pins a clicked face through the session, or unpins over empty space. Pinned planes take
priority; orthographic views keep their camera-facing fallback.

Turned-down alternatives:
- **One drag, height fixed to the grid, adjusted afterwards** (TrenchBroom's default: Shift during
  the drag changes height). Fewer steps for flat floor tiles, but every wall and pillar then needs
  a second operation, and Shift-during-drag collides with Shift for a square base.
- **Hammer's 2D flow** (draw in a top view, set height in a side view). It needs an orthographic
  view, which the exit criterion excludes.

*What would reverse it:* the owner finding the two-stage flow slower in the exit session than a
fixed-height drag. Then a setting makes stage 2 optional (release commits at the last height).

### D6: Primitives are generated once and committed as plain solids; parameters stay editable only until the next action

The primitive tool draws a bounding box exactly as D5 does, then generates the shape inside it:
wedge, cylinder (sides 3–64), spike (sides 3–64), arch (sides, arc angle, start angle, wall width,
add height) and sphere (segments). A parameter strip in the tool's readout area (and typed values)
shows the parameters; changing them regenerates the preview. After commit, the same parameters
remain editable, Blender-style ("adjust last operation"): an edit *replaces* the last undo entry's
result, until any other edit is made.

Single-solid shapes (wedge, cylinder, spike) commit one solid. Multi-solid shapes (arch: one solid per
segment; sphere: Hammer's segmented approximation) commit their solids as one new VMF group, so a
click selects the whole shape (0.2 D10).

The alternative is persistent parametric primitives, re-editable at any time. Strata Hammer's
AngelScript scriptable primitives are the precedent. It's turned down for 0.3 because the parameters
would have to be stored in the file, and 0.1 D19 rules out Apex-only keys; Strata's own mechanism is
a scripting surface (roadmap 0.9, "scriptable primitives").

*What would reverse it:* the 0.9 scripting decision adopting Strata's scriptable-primitive format,
which would give re-editable primitives a file encoding Strata Hammer reads.

### D7: The vertex tool edits vertices, edges and faces as handles, and commits the convex hull of the moved points

Entering the tool (Hammer Shift+V; Blender Tab) shows every selected solid's vertices, edge
midpoints and face centres as handles. Element mode (vertex / edge / face; Blender 1/2/3) picks which
handles respond. Click and marquee select handles; dragging, the gizmo and modal G/R/S move them,
reusing `editor::Transform` and snapping (0.2 D6, D8), with the D13 snapper so a vertex can be
dropped onto another vertex. Moving an edge or face moves its vertices together.

During the drag the tool computes, per solid, the convex hull of the moved point set (D8) and shows
it as preview geometry (D12). **Invalid-state feedback** is shown live, before release:
- vertices that the hull absorbs (now inside it) are drawn red, with a status message naming how
  many will disappear;
- faces the hull adds (because a move made a face non-planar, so it splits into triangles) are
  outlined in a warning colour;
- a move that collapses the solid (volume or a face below the kernel's tolerances) is drawn red and
  **refuses to commit**: release snaps the handles back, with a message.

Commit writes the hull through `rebuildSolid` with D3's correspondence. Merging two vertices onto
one position is how a user deliberately removes a vertex (Hammer's vertex merge), and the tool
offers it as a confirmation when a drag ends on another vertex.

The alternative is Hammer's rule: keep the topology, allow only moves that leave every face planar
and the solid convex, and refuse (or revert) anything else. Nothing ever vanishes unexpectedly. It's
turned down because most useful vertex moves (pulling one corner of a box up into a slope) make a
face non-planar, which that rule refuses, so users learn to split faces by hand; the roadmap names
"convex-hull rebuild" and Hammer++'s tool behaves this way.

Accepted cost: a vertex dragged inward disappears on release. The live red marking is the defence.

*What would reverse it:* the owner finding absorbed vertices too surprising in the exit session.
Then a "strict" toggle refuses commits that would absorb a vertex, keeping the hull for everything
else.

### D8: The hull and CSG kernel use double precision with the existing tolerances; exact predicates are added only if fuzzing finds a failure

`geometry::convexHull(span<const DVec3>) → expected<ConvexPolyhedron, Problems>` is an incremental
3D hull (quickhull) in double, welding points within `kPointMergeEps` and merging coplanar triangles
into one face within `kPlanarEps`, so a cube's hull has six quads, not twelve triangles.
`geometry::split(poly, plane) → {front, back}` and `geometry::subtract(target, carver) →
vector<ConvexPolyhedron>` build on the existing plane clipper.

Robust geometric predicates (Shewchuk-style adaptive orientation tests) are the alternative 0.1 D9
held open. They give exact orientation and coplanarity decisions, at roughly 2–4× the cost of
plain doubles in the common case. They're deferred because every hull and clip in 0.3 ends in
`validate()` with the same tolerances, so a near-degenerate case shows up as a refused edit, not
as a corrupted brush; and the coplanar merge needs a tolerance either way.

The fuzz target: random point clouds and random plane splits near ±65536, with results checked by
`validate()`, volume conservation (split pieces sum to the original within tolerance), and hull
containment of every input point. It runs in 0.3.1 and in CI.

*What would reverse it:* the fuzz target producing a valid-looking but wrong result (a missing
point, a non-conserving split) that tolerance tuning can't fix. Then the orientation test becomes
adaptive-exact, behind the same functions.

### D9: The clip tool places up to three points with the snapper; two points in an axis-locked view are enough

The clip plane is defined by points placed by clicking (D13 snapping: vertex, edge, then grid on the
hovered surface). After two points, in a view whose projection is orthographic the plane contains
the view direction, so two clicks clip (Hammer's habit, and the case where the view kind does matter
because the plane depends on it, which `ViewContext` exposes as projection, not view type). In
perspective a third point is required. Points remain draggable handles until commit.

The kept side cycles front / back / both (Hammer's Shift+X repeats; a tool action); the discarded
part is shown as a ghost. Enter commits. "Both" splits each solid with D2: the front keeps the
solid's identity, the back is created with the source's `editor` block. The cap face is new and
inherits its material and axes from the most-aligned old face, per D2's new-face rule. Solids the
plane does not cross are untouched.

The alternative is a gizmo-placed clip plane (TrenchBroom's later "clip by plane" drags a plane
handle). It's turned down because the roadmap names "3 points placed on surfaces", and points
snapped to existing vertices are exactly what makes a clip line up with neighbouring geometry.

*What would reverse it:* nothing beyond user testing; a plane gizmo could be added alongside.

### D10: Carve subtracts with Hammer's fragment rule; hollow builds one wall per face; merge requires the hull to equal the union

- **Carve** (Hammer Ctrl+Shift+C): every visible solid intersecting the selection (the carvers) is
  replaced by `subtract(target, carver)` fragments, one per carver plane the target crosses
  (Hammer's sequential split, deterministic in carver face order). The first fragment keeps the
  target's identity (D2), the rest are created with its `editor` block, and the carvers remain.
  Fragments inherit their faces' sides through plane matching (D3); the new faces where carver planes
  cut get the carver's face material and axes, which is what makes a carved doorway's reveal match
  the carver's texture.
- **Hollow** (Hammer's Tools > Make Hollow; Strata binds no key to it, P0): each selected solid becomes one wall solid per face, of a typed
  thickness (negative: walls grow outward), each wall clipped by its neighbours' inner planes so
  walls don't overlap at the corners. Walls become one new group. The solid's identity goes to the
  first wall.
- **Merge:** the selected solids become their convex hull. Before committing, the tool carves the
  hull by every input; if any fragment above tolerance remains, the hull would fill space the user
  didn't select, so the added volume is shown as a ghost (D12) and a confirmation asks "Merging
  fills N units³ outside the selection. Merge anyway?" with **Merge**, **Cancel** and a **Don't ask
  again** checkbox. The checkbox sets the preference `editing/confirmNonConvexMerge` (on by default,
  also in Preferences > General), after which a non-convex merge commits without asking. A merge whose
  union is already convex never asks. The merged solid keeps the first selected solid's identity;
  faces match by plane (D3).

Turned-down alternatives for merge:
- **Refuse non-convex unions, with hull-merge as a separate action.** Never changes unselected space
  silently, but users who want Hammer++'s behaviour must find and bind a second action, and a refusal
  gives no way to proceed.
- **Always hull, never ask** (Hammer++'s "merge to convex"). Fast for blocking out, but it silently
  fills gaps (an L-shape becomes a filled block), which can seal a doorway unnoticed. The preference
  gives exactly this behaviour to users who opt in.

Accepted cost: a modal confirmation in a 3D workflow, mitigated by the ghost showing what will be
filled and by the preference.

*What would reverse it:* the confirmation proving disruptive in the exit session, in which case the
preference's default flips; or users wanting the refusal back, which becomes a third preference value.

### D11: Solids with displacement sides are read-only for topology tools until 0.8

Clip, vertex, carve (as a target), hollow and merge refuse solids that have any `dispinfo` side,
with a message naming the reason. Transforms (0.2) keep working on them, as now. Carving *with* a
displacement solid as the carver is also refused.

The alternative is to apply the operation and drop the displacement (Hammer warns and does this for
some operations). It's turned down because the drop is silent data loss on one click, and
displacements are their own subsystem in 0.8 (roadmap), where these rules belong.

*What would reverse it:* 0.8's displacement work, which defines what each tool does to them.

*P0 result (2026-10-22):* no side in the 512 corpus maps has `dispinfo`, so the refusal costs nothing
on P2CE's own content. It is kept for user maps that have displacements.

### D12: Preview gains geometry: ghost solids and replacement meshes, meshed on the main thread within a per-tick budget

`editor::Preview` adds two maps next to its transforms:
- `replacements: NodeId → ConvexPolyhedron` (and per-face material): draw this shape instead of the
  node's mesh (vertex tool, clip "keep", merge);
- `ghosts: vector<GhostSolid>`: shapes with no node yet (block and primitive tools, clip "both"'s
  back half, carve fragments), drawn with the active material at reduced opacity and an outline.

`RenderMirror::setPreview` meshes these on the main thread when the preview's revision changes, with
a budget of 2 ms per tick; past the budget the remainder is meshed on following ticks and the
outline is drawn for what isn't meshed yet. Meshing one convex solid is a few microseconds, so the
budget covers any interactive vertex drag on a selection of hundreds of solids. Carve and hollow on
large selections show a summary ("142 fragments") and the outline only.

0.2 D6 said non-affine previews would be "meshed on a job". The alternative, a job, keeps the
main thread free whatever the size, but adds at least one tick of latency between pointer and
preview, which is visible exactly where precision matters (a vertex dropped onto another). It's
turned down for interactive tools; jobs remain the path for the summary-only operations if they
need a preview later.

Bite 9 of 0.2 extends: the preview and the commit derive from the same polyhedron value, and a test
compares them for every tool.

*What would reverse it:* the 2 ms budget being exceeded in the exit session's normal editing. Then
replacement meshing moves to a job and the preview shows the previous frame's mesh until it lands.

*As built (0.3.1):* meshing is about 3.3 µs per box (release, RX 6600), as expected, but the GPU
upload dominates: with one upload submission per tick, counted inside the budget, a tick meshes
about 135 solids in 1.7–2.1 ms. A drag over a few hundred solids therefore fills in over 2–3 ticks
(the rest drawn as outlines), not one. The first tick after a revision change runs over (about
3.4 ms with 2,000 ghosts) while it retires the previous snapshot. Labels are not depth-tested; they
are culled when their anchor leaves the view.

### D13: One snapper for every point-placing tool: vertex, then edge, then surface grid, within a screen-space radius

`editor::Snapper::snap(ray, view, settings) → SnapResult { point, kind, source }` checks, in order:
1. a **vertex** of a visible solid within 8 px of the cursor (screen space, so the radius means the
   same in any zoom and projection);
2. an **edge** (closest point on it, or its midpoint within 8 px of the midpoint);
3. the **hovered surface** (or work plane), snapped to its grid (0.2 D8, absolute mode).

`snap.suspend` (Alt / Ctrl by preset) skips 1–3 and returns the raw surface hit. The result kind is
shown at the cursor (D16) so the user knows what was hit. The block tool's corners, the clip tool's
points, the vertex tool's drop targets and the measure tool all call it.

**As built (0.3.2 follow-up).** Block corners use grid + vertices, skipping edge and midpoint
snaps. A committed base plane is remembered for perspective presses over empty space that is not
over the drawn world grid (within its 4096-unit fade); idle hover shows the snapped start, and
Esc clears the last plane. While dragging, the base's side lengths are labelled at its edges. `block.pick_plane` (Hammer Ctrl, Blender
Alt) pins a clicked face through the session, or unpins over empty space. Pinned planes take
priority; orthographic views keep their camera-facing fallback.

Vertex and edge queries come from a new `PickIndex::nearestFeature(ray, pixelRadius, view)` over the
same BVH (solids' vertices and edges are already derivable from the polyhedra the index holds).

The alternative is world-space radii per tool, which is what `nearest(point, radius)` offers. It's
turned down because a world radius is huge when zoomed in and useless when zoomed out, and per-tool
radii drift apart.

*What would reverse it:* nothing; the priority order may be tuned in testing.

### D14: The material browser is a panel role over a full material index, with thumbnails decoded on the CPU, not uploaded to the bindless heap

**Index.** `assets::MaterialIndex` walks `materials/` across every mount (VPK and loose directory,
including mounted Strata addons, D19) once per profile load, and again when the mount set changes (a new `Vfs::walk(directory)` that recurses, which `Vfs` lacks today), and
records each VMT's path, shader, `%keywords`/`$keywords`, `%tooltexture` and base texture name. The
walk runs on a worker; the browser shows a progress state until it finishes. Its cost is the P0
measurement.

**Panel.** A new area role, *Materials* (0.2.12), with: a name filter (substring and `*` glob), a
keyword filter, a shader filter, toggles for "used in this map" and "tool textures", a recent list,
and a thumbnail grid with size slider. Clicking sets the **active material** (D4's new-solid material
and D15's apply target); double-clicking applies it to the selected faces; dragging a thumbnail onto
a face in a viewport applies it there. The inspector's `material` browse button opens the same panel
in a pick mode.

**Thumbnails** decode the smallest mip at or above the thumbnail size from the VTF on a worker
(vtfpp, as `MaterialCache` already does) into a CPU image cache with its own LRU budget (64 MiB by
default), and the panel draws them with Qt. Nothing in the browser touches `TextureHeap`.

The alternative is to render thumbnails through the Vulkan renderer: upload each material to the
bindless heap and draw quads, which shows the material exactly as the viewport would (shader,
translucency, `%ToolViewportTexture`). It's turned down because the heap has 4,096 slots shared with
the map, browsing thousands of materials would evict or exhaust them, and a Qt panel cannot host
Vulkan content in an area that may float as a tool window. CPU thumbnails use the same
`%ToolViewportTexture`/base-texture choice as `MaterialCache`, so they show the same image.

*What would reverse it:* the P0 index walk being too slow to run at load (then it's cached on disk,
keyed by mount mtimes), or CPU thumbnails differing visibly from the viewport for a material class
users care about.

*P0 result (2026-10-22):* 4,529 VMTs (without addons; D19 re-measures with the owner's mounted
addons, and EverythingPBR alone is about 1.9 GB of content). Listing them across every mount takes 41 ms, and parsing them
all takes 79 ms warm, so the index is built on a worker at each profile load with no disk cache.
Keywords are sparse (760 VMTs, a few dozen distinct words), so the keyword filter is a plain word
match inside the name filter's popup, not its own panel section.

### D15: Face editing is a *Face Properties* panel plus an apply tool; `rotation` is written from the axes, never the other way

**Face Properties** (an area role, Hammer's Face Edit sheet) edits the selected faces (face selection
mode): material; U/V shift, scale and rotation; lightmap scale; smoothing groups; justify left,
right, top, bottom, centre and fit; align to world or to face; "treat as one" (justify and fit use
the combined bounds of all selected faces, Hammer's option). Each edit is one transaction; typing
coalesces per field focus (0.2 D13's mechanism). Mixed values across the selection show as mixed and
are untouched unless edited.

**Apply tool** (Hammer Shift+A, the texture application tool): left click selects faces (Ctrl
toggles, Shift adds); right click applies the active material to the clicked face; Alt+right click
applies the material *and* wraps the alignment from the selected face onto the clicked one, so a
texture continues across an edge (Hammer's "apply with alignment"); Alt+left click lifts the clicked
face's material as the active one. The Blender preset binds the same actions without the right-click
apply (Blender's right click is the context menu), using Ctrl+click instead.

**The measure tool** belongs here because the roadmap groups it with face editing: click two points
(D13), and the readout shows distance, the per-axis delta, and the angle between the two faces under
them, as a world-space line with a label (D16). It is session state and never written to the file.

**Rotation.** A VMF side stores both `uaxis`/`vaxis` (already rotated) and a `rotation` value that
Hammer shows in its dialog. Apex treats the axes as the truth (0.2 D7 already transforms them), and
whenever it writes axes it writes the `rotation` value derived from them relative to the face's
default alignment. Nothing reads `rotation` to compute UVs. The P0 count checks how often files
disagree.

The alternative is a dialog-only face editor (Hammer's floating sheet) with no apply tool. Simpler,
but applying a material to fifty faces then means selecting each first, which is the main workflow
for texturing a chamber.

*What would reverse it:* the P0 count showing corpus files where `rotation` disagrees with the axes
and Hammer honours `rotation` on load. Then the writer keeps whichever Hammer reads.

*P0 result (2026-10-22), probe:* Strata Hammer writes a side back verbatim when `rotation` and the
axes disagree, in either direction (`probe-results/h_rotation_vs_axes_saved.vmf`): it never derives
one from the other on load or save, so the axes it saves are the ones it read. Which value its Face
Edit dialog displays was not checked (it needs the VM). *Count:* 1,624 corpus sides have a nonzero
`rotation`, and only 355 of them agree with their axes under either sign convention. Because Hammer
does not reconcile the two, the decision stands: the axes are the truth, and `rotation` is rewritten
only when Apex writes the axes.

### D16: Viewports gain depth-tested world overlays and a small glyph atlas for labels

Overlays now come in two kinds:
- **world overlays**: lines, points (square handles of fixed pixel size) and translucent triangles
  in world space, rebased against the camera like geometry, depth-tested with an occluded pass at
  reduced alpha (the 0.2 outline's technique), for vertex handles, clip planes, ghosts' outlines and
  measurement lines;
- **labels**: short text strings at a world position, drawn from a glyph atlas built once at startup
  from the UI's own font, with no shaping beyond ASCII and Latin-1 in 0.3.

The alternative is to show all text outside the viewport: the status bar and the header badge (0.2.12)
already carry tool readouts. No font code in the renderer. It's turned down because a measurement or
a snap kind shown in the status bar is far from where the user is looking, and 0.4's FGD `worldtext`
helper and the entity names Hammer draws in views need world-space text anyway, so the atlas is built
once for both.

The atlas is rasterised by `ui/` with Qt (`QPainter` onto a `QImage`, the UI's own font and
hinting) and handed to `render/` as plain R8 bytes plus glyph metrics, so `render/` stays Qt-free and
no font library is added. Headless tests rasterise a fixed bitmap font fixture instead.

Accepted cost: an atlas upload path and a label pass in the renderer.

*What would reverse it:* the owner preferring status-bar-only text in 0.3, deferring the atlas to
0.4's helpers.

### D17: The exit test is a scripted chamber build plus the owner's manual build, checked by vbsp, Strata Hammer and srctools

"A complete test chamber" is defined, so the exit can be checked:
- a sealed room of at least 512 × 512 × 256 units built from block-tool solids, textured with P2CE
  portalable walls and floors and non-portalable ceiling (white/black concrete tile families);
- one doorway carved through a wall, its reveal textured;
- one angled panel made by clipping, and one sloped face made with the vertex tool;
- a ramp or stairs (wedge primitive), and a cylinder pillar;
- an exit door frame using an arch;
- `info_player_start` and one `light`, placed with 0.2's entity tool;
- every face aligned (no stretched textures on visible faces), checked by eye in the manual run.

Three gates:
1. **Scripted build** (headless): a replay that builds the chamber above through tool inputs only,
   from an empty map, using perspective camera rays only. The saved VMF passes `validate()` on every
   solid and the srctools cross-check.
2. **Compile check**: `vbsp` (native Linux, as `tools/vbsp_equivalence.py` runs it) on the result
   reports **no leak**, and `vvis -fast` completes. 0.5 owns the compile pipeline; this is a gate,
   not a feature.
3. **Owner's manual build** in the app, with no orthographic viewport open, of a chamber meeting the
   same list, then opened and re-saved in Strata Hammer via `tools/hammer_wine_check.py` with ids and
   planes unchanged.

The alternative is the roadmap's sentence as written, judged by the owner. It's turned down because
"complete" then means whatever the session happened to include, and the scripted build is what keeps
0.3's tools from regressing in 0.4–0.10.

*What would reverse it:* the owner wanting a different chamber list; the list is data in the test.

### D18: Post-release sub-milestones are allowed when the owner asks; they don't move the release tag, and the next milestone still starts at .1

0.2.12 (Preferences, keybinding editor, areas and workspaces) landed after `0.2.11-release` at the
owner's request, and `version.txt` now reads `0.2.12`. The roadmap's versioning section says
"Nothing of 0.M lands after its release; the next landed work is 0.(M+1).1." The plan records the
exception as a rule:

- a sub-milestone may land after a milestone's release only at the owner's request; it takes the next
  number in that milestone (`0.2.12`), is tagged `v0.2.12`, and does not create a new release
  (`v0.2.11-release` stays the 0.2 release);
- the next milestone's first sub-milestone is still `0.(M+1).1`, so 0.3 starts at **0.3.1**.

The alternative is to treat 0.2.12 as 0.3 work: renumber it 0.3.1 and start 0.3's plan at 0.3.2. That
keeps the rule as written, but rewrites history that's already in `version.txt`, a commit message and
the 0.2 plan, and 0.2.12 has nothing to do with brush authoring.

*What would reverse it:* the owner preferring the rule as written, in which case 0.2.12 is retagged
and this plan's numbers shift by one.

### D19: Strata content addons are mounted read-only in 0.3, following Strata Hammer's addon list, before the material index

Design and research: [addons.md](addons.md). Maps that use addon materials currently open with
error textures, and D14 would index a different material set from the one Hammer shows. Both of the
large PBR packs mappers use on the dev machine are addons. 0.3 takes the read half of that design:

- a text-only KV3 reader in `core/` that records each value's byte span (addons D5);
- an addon mount layer in `Vfs`, owned by the P2CE profile, that records which addon each mount
  came from (addons D1);
- it follows `hammer/addons/addonlist.kv3`, or the game's list when Hammer's doesn't exist, with a
  profile setting for `hammer`, `game` or `apex` (addons D2's read half);
- Wine and drive-letter path normalisation through the existing case-insensitive `expand()`
  (addons D4);
- the search order that addons P2 measures (addons D3).

Apex writes nothing to either list in 0.3. The user toggles addons in Hammer, and Apex re-reads the
list at profile load and on Reload. The Addons panel, write-back and the "provided by an unmounted
addon" hints are 0.4. Compile parity and addon authoring are 0.5.

The alternative was leaving addons to 0.4 with the other browsers. It's turned down because D14's
index, the inspector's material browse button and the 0.3 exit chamber would all be built and tested
against the wrong material set, and the mount layer is small.

*What would reverse it:* P2 showing that addon order depends on runtime state Apex can't reproduce
from the list. Then 0.3 mounts nothing, and the whole design moves to 0.4.

reads the projection kind, which principle 1 permits. `tools/check_layers.py` gains no new layer.

## 5. Things that will bite

**1. A tool will allocate `SideId`s itself.** It's tempting when building a cap face or a fragment, and
it collides with IDs the document allocated (sides have their own ID space, research §1). Defence:
`rebuildSolid` and `create` are the only allocators; `FaceAttributes::sideId` of a new face is ignored
on write, and a test passes a deliberately colliding ID and checks it's replaced.

**2. Clip "both" or carve will lose group and visgroup membership on the created fragments.** `create`
takes a block, and copying sides but not the `editor` block is the natural mistake. Defence: one
`createFragment(source, poly)` helper used by clip, carve and hollow, and a test clipping a solid that
is in a group and two visgroups.

**3. The vertex tool will match faces by plane.** `matchFaces` exists and works for every other tool.
Defence: D3's correspondence is a required argument for the vertex tool's commit path, and P0 test 3.

**4. Coplanar hull triangles will not merge.** Quickhull naturally outputs triangles, and a box then saves
twelve sides; Hammer accepts it, so nothing fails visibly until a texture is misaligned across a
diagonal. Defence: the hull merges coplanar faces within `kPlanarEps`, and a test checks a cube hull has
six faces.

**5. Justify and fit will ignore the texture's size.** Shift and scale are in texels, so fit needs the
VTF's dimensions; `uvAt` takes them, but a face-edit path that defaults them to 512 looks right on most
P2CE textures. Defence: the face-edit model takes the material's dimensions from `MaterialCache` and
refuses to justify a material that has not loaded, with a message.

**6. The preview and the commit will disagree.** Preview meshing and the committed write take
different paths (preview uses floats on the GPU; commit snaps, writes 17-digit numbers, re-derives).
Defence: both come from one polyhedron value, and each tool's test compares preview vertices with the
committed solid's (0.2 Bite 9, extended).

**7. Ghosts will be pickable.** The pick index is ChangeSet-driven, but a tool may call `pick` and hit
its own ghost if ghosts are ever added to it, or miss a surface the ghost covers. Defence: ghosts and
replacements live only in the preview, never in the `PickIndex`, and the block tool's second stage
uses a line, not a pick.

**8. Carve will remove the carver from the target set and still carve itself.** A selected solid that
overlaps another selected solid is both a carver and a target. Defence: carve's targets exclude the
selection explicitly, and a test carves two overlapping selected blocks through a third.

**9. The material index will be built on the main thread.** `Vfs` is main-thread-owned, so the walk is
tempting to run synchronously at load. On P2CE with its mounts it may take seconds. Defence: the index
snapshot is built on a worker from an immutable VFS listing, and the P0 measurement records its cost.

**10. `rotation` will be read.** Someone writing "rotate texture by 15°" will add 15 to the stored
`rotation` and recompute axes from it, which drifts when files disagree. Defence: D15's rule, one
function that rotates axes and derives `rotation`, and the P0 count.

**11. A new tool action will be bound in one preset only.** 0.3 adds about 30 actions. Defence: 0.2's
registry completeness test (Bite 13) already fails the build.

**12. Addon paths will be compared as written.** Wine Hammer lower-cases every `dir` and uses `z:\`,
so a byte comparison against the real `~/snap/steam/.../Steam/...` path misses, and the addon silently
doesn't mount. Defence: every list path goes through D19's normaliser and `expand()`, an unresolved
entry is reported in the log and the status bar, and a fixture uses a lower-cased Wine path to a
mixed-case folder.

## 6. Sequencing

1. **0.3.1** first, alone. Its P0 can change D2, D11, D14 and D15, and its D1 migration touches the
   same files every later tool touches. Within it, the D1 migration lands first, proved by the
   unchanged 0.2 tests, before any new tool code.
2. Then two tracks:
   - **Track A (geometry tools):** 0.3.2 first (it provides the shared base-drawing gesture and the
     `solidBlock` path in use). Then 0.3.3, 0.3.4, 0.3.5 and 0.3.6 touch different tool files and kernel
     functions and can run in parallel; 0.3.5 reuses 0.3.2's gesture, 0.3.6 reuses `subtract` from
     0.3.1.
   - **Track B (materials):** 0.3.7 → 0.3.8 → 0.3.9, serial (the index needs the addon mounts, and the
     apply tool needs the active material). Needs only 0.3.1 (for D1 and D16's labels in the measure
     tool). 0.3.7 touches only `core/` and `assets/`, so it can start as soon as 0.3.1 lands.
3. **0.3 release** last: it needs every tool for the scripted chamber build.

Merge order puts the pure layers first: `geometry/` and `document/` changes merge with their tests
before the `editor/` tool that uses them, and nothing in `ui/` merges before its `editor/` model has
passed headless tests.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-10-22. Each was presented with its alternatives. All draft
choices were confirmed except D10, which changed in review. They're recorded here with the
alternatives turned down, so a later reader does not reopen them without new information.

- **D1: an `editor::Tool` interface, with Select and Entity migrated first.** Turned down: the
  interface for new tools only (two tool mechanisms, gizmo code left tangled in the session), and
  keeping the enum. Revisit only if per-tool state is abandoned.
- **D4: face-aligned UVs on new solids, with world alignment as a setting.** Turned down: Hammer's
  world-aligned default. Revisit if the exit session shows face alignment confusing on axial work.
- **D5: draw the base, release, extrude, click.** Turned down: one drag with a fixed height
  (TrenchBroom), and both behind a setting. Revisit if the exit session shows the extra click costs
  more than it saves.
- **D6: primitives committed as plain solids, adjustable until the next edit.** Turned down:
  persistent parametric primitives (needs Apex-only keys, against 0.1 D19), and a parameter dialog
  before drawing. Revisit with 0.9's scriptable-primitive decision.
- **D7: vertex edits commit the convex hull, with live red marking and refusal of collapses.** Turned
  down: Hammer's strict topology, and the hull with a strict toggle. Revisit if absorbed vertices
  surprise users in practice; the toggle is then the fallback.
- **D10: merge takes the hull after a confirmation, with a "don't ask again" preference** (changed
  in review). The draft refused non-convex unions and offered hull-merge as a separate unbound
  action. Turned down: that refusal, and always-hull without asking (Hammer++), which the preference
  reproduces for users who opt in.
- **D12: preview geometry meshed on the main thread within 2 ms per tick.** Amends 0.2 D6's "meshed
  on a job". Turned down: worker meshing with a tick of latency. Revisit if the budget is exceeded in
  normal editing.
- **D14: CPU-decoded thumbnails drawn by Qt.** Turned down: shaded thumbnails through the Vulkan
  bindless heap. Revisit if thumbnails differ visibly from the viewport for a material class users
  care about.
- **D16: in-viewport labels from a Qt-rasterised glyph atlas.** Turned down: status-bar-only text.
- **D17: a defined chamber list with three gates (scripted build, vbsp no-leak, manual build with the
  Hammer re-save).** Turned down: the list judged manually only, and owner judgement of the roadmap
  sentence.
- **D18: post-release sub-milestones allowed at the owner's request; 0.3 starts at 0.3.1.** Turned
  down: renumbering 0.2.12 as 0.3.1, and re-releasing 0.2 as 0.2.12-release.
