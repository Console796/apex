# Apex: 0.5 implementation plan: Compile & play

**Status: 0.5.1–0.5.6 landed; 0.5.7 and 0.5.8 implemented in the working tree, 2026-10-28.**
The owner confirms real playtests on commit `1f89631`; those playtests are complete (platforms
were not specified). The full gate (build 14) was stopped at the owner's request after GCC and MSVC failures;
release verification remains incomplete. GCC's new BSP-comparison test link has been corrected;
Windows portability failures still need fixes and a rerun. CI now uses the POSIX `apex_tests --jobs=N`
runner for Linux, with the remaining CTest entries kept separately. `version.txt` is `0.5.8`; no 0.5 release tag has been made.

### As built: closing work (2026-10-28)

- **0.5.7:** compile profiles persist an addon target and optional campaign ID. Source Save As starts
  in the target's `mapsrc`; snapshots remain isolated in cache (D4), BSP copies go to the target's
  `maps`, and compile content includes the target before the editor's ordered mounts. The game keeps
  its original game directory and receives `-campaign addon:<folder>/<id>` when a campaign exists.
  Multiple campaigns require an explicit ID; a missing/invalid manifest or ID fails before compiling.
- The summary lists addon provenance and unmounted providers. A visible warning names game/editor
  mount differences and unmounted targets; no installed list is rewritten. *New addon* creates the
  observed text-KV3 manifest shape, `mapsrc/instances`, `maps` and `.assets`, optionally with an empty
  `scripts/campaigns.kv3` stub. The uploader opens without unverified selection switches. Authors
  finish thumbnails/campaign chapters and mount the addon in Strata's tools. Dependency entries
  remain empty; P4's nonempty syntax is not guessed.
- **0.5.8:** *Create Instance from Selection* is in Instancing and the Outliner's selection context
  menu. It writes a new VMF centered on the current selection pivot, uses no name fixup to preserve
  existing names, then replaces the selection in one undoable transaction. Incoming/outgoing
  connections across the boundary require confirmation and retain their names. Existing files
  are never overwritten. Undo restores the source selection but leaves the VMF, allowing redo and
  other maps to keep referring to it. Texture-locked transforms preserve geometry/material alignment.
- Snapshot instance handling follows parsed `func_instance` records, including source-relative `..`,
  absolute and nested paths, and places external instances under an isolated snapshot folder. Source
  documents and templates remain unchanged.
- The profile panel now exposes `.wc` export. Native Windows game lookup follows the shipped
  `p2ce.bat`: `bin/win64/p2ce.exe`. The real-tool gate includes baseline, cut cordon and created-instance
  addon-target cases, and is registered in the full CI graph.

**Release evidence (2026-10-29):** [compile_0_5_release.md](probe-results/compile_0_5_release.md) records
the Linux real-tool gate (Fast, Final, a leak, a cordon cut and a created instance in an addon target),

**Remaining evidence:** Hammer cordon thickness/material/union behavior has not been measured against

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.5: Compile & play.** Compile profiles (including import of Hammer `.wc` via toolpp),
> vbsp/vvis/vrad/postcompiler as cancellable background jobs using the **native Linux tools** on

what an earlier plan said:

- D12 adds a `compile/` layer to the layer graph of 0.1 §2 (core only; no Qt). The roadmap's
  `compile/` line in research §6 already names it.

- **Addons this map uses, in the compile summary** (addons.md D7): D10.
- **Addon authoring: create, compile target, `-campaign`, Workshop Uploader hand-off** (addons.md D9;
  P4, the `dependencies` syntax, is settled only if the scaffold writes one): D10.
- **Create Instance from Selection** (0.4 §4, owner, 2026-10-25): D11.
- **Compile-time checks: missing models as compile errors, map validation** (0.4 §4): D8.
- **The postcompiler on Linux**, which the roadmap lists with the native tools but which has no Linux
  build in the game's `bin/linux64` on this host: D13.
- **Per-compile entity keys that need a sidecar or a compile option** (0.4 D12 note, "out of scope
  until 0.5's compile profiles"): D2 (profile options) and D7 (cordons); nothing is written to the VMF.
- **The owner's manual in-game playtest** (0.4 D16, gate 4): 0.5 automates the launch (D9); the
  judgment of "the button opens the door" stays manual.

**What 0.5 inherits.**

- **`tools/vbsp_equivalence.py` and `tools/chamber_compile_check.py`.** Both already run the native
  `bin/linux64/{vbsp,vvis}` against a copy of a VMF in `/tmp`, with `-game` pointing at the game
  directory, and refuse to write inside the install. That is the working recipe D5 turns into
  editor code. Measured on this host: the tools exist as `vbsp`, `vvis`, `vrad`, `vbspinfo`, `bspzip`,
  `studiomdl`, `workshopcli` and `workshopgui` in `bin/linux64`, and with no `-game` they exit with
  "Unable to find gameinfo.txt", so `-game` is always passed.
- **`toolpp::CmdSeq`** (SourcePP v2026.9.11, already linked). It parses binary and KeyValues
  command-sequence files, including Strata's `special_cmd` values (256 change directory, 257 copy,
  258 delete, 259 rename, 261 copy if exists), and can write them back. Hammer's own
  `hammer/cfg/cmdseq.wc` on this host is the Strata KeyValues flavour with `$bsp_exe`, `$vis_exe`,
  `$game_exe`, `$postcompiler_exe`, `$gamedir`, `$path` and `$file`.
- **`core::JobPool` and `CancelToken`** (0.1 D12): background work with main-thread completions. A
  compile step is a job whose work is a child process, so cancellation has to kill it (Bite 2).
- **The world overlay path** (0.3 D16): depth-tested lines, handles and triangles, and a glyph atlas.
  The leak line and the portals draw through it.
- **`document::Cordon`** and the VMF `cordons` block. The block round-trips today (`Cordons` in
  `vmf.hpp`, the plural form the corpus uses), but `Cordon` is an empty `Node`: nothing reads its
  box and no tool edits it.
- **`assets::AssetReport` (0.4 D11), `editor::connection_validation` (0.4 D6) and the
  unmounted-addon index (0.4 D15).** These are the checks map validation (D8) collects, and the hints
  that name an addon.
- **Instance collapse that equals vbsp's instance merge** (0.4 D9), verified against vbsp. Compiling
  a collapsed copy is available as a fallback (Bite 3).
- **The `Vfs` addon mount layer and the addon list** (addons.md D1–D6, 0.3.7 and 0.4.9): the
  editor's mount set, and the `addons/addonlist.kv3` reader and writer for D10's comparison.
- **The Windows VM** (`tools/winvm.sh`): the exit test needs it.

**What 0.5 does not have.**

- **A process runner.** The only child process Apex starts is a detached second Apex window
  (`MainWindow::openSelectedInstance`). Nothing captures stdout, merges stderr, kills a tree or
  reports an exit code: D1.
- **Compile configuration.** There are no game or compile preferences beyond the profile's game
  directory: D2.
- **A way to find the compile tools.** The `Vfs` knows the game directory (`gameinfo.txt`), not
  `bin/linux64`/`bin/win64`: D3.
- **Cordon editing, rendering or export:** D7.
- **A problems list.** Reports exist per kind (assets, entities, connections), with no shared model:
  D8.
- **Any record of where a compiled BSP went**, or of which compile a leak file belongs to: D4 and D6.

## 1. Decisions

Each records what would reverse it.

### D1: Compiles are command sequences run by a Qt-free `compile/` layer over a `ProcessRunner` interface; `ui/` implements the runner with `QProcess`

A compile is a `Sequence` of `Command`s, the same shape as toolpp's `CmdSeq` (an executable or a
special command, an argument string, an enabled flag, a wait flag). `compile/` owns: variable
expansion (D2), the in-process special commands (copy, delete, rename, change directory), step
ordering, the status machine (queued, running, ok, failed, cancelled, skipped) and the log parsers
(D4). It does not start processes. It calls `ProcessRunner::start(program, args, cwd, env)`, which
returns a handle with `readyRead`-style line callbacks, `terminate()` and an exit code. `ui/`
implements it over `QProcess`, and the tests implement it with a scripted fake that replays recorded
logs. The real tools are exercised by a gated CI stage (`APEX_P2CE_DIR`), like 0.4's.

The alternative is a small Qt-free process wrapper over `posix_spawn` and `CreateProcess`. It would
let `compile/` be tested against real processes in the plain test binary, but it means writing and
maintaining pipe, tree-kill and Windows job-object code that `QProcess` already has and that 0.4's UI
already links. The interface keeps that decision cheap to reverse.

Accepted costs: process-tree termination is whatever `QProcess` gives (Bite 2 names the defence), and
the real-tool test is skipped where the game is not installed.

*What would reverse it:* `QProcess` failing to kill `vrad`'s worker threads or the game's wrapper
shell on one OS in the 0.5.1 probe; then a Qt-free runner replaces the `ui/` one without touching
`compile/`.

### D2: A profile is Apex's own data; Hammer's `.wc` is imported once as a copy, not followed

`CompileProfile` is a name, a game profile reference, an ordered list of commands (as D1) and a few
named options (run the game after, copy the BSP to `maps`, compile the cordon only). It lives in the
user's preferences, not in the VMF (0.1 D19: nothing is added to the VMF that Hammer would drop).
Three built-in profiles mirror what Hammer ships: *Fast* (vbsp, vvis `-fast`, vrad `-fast`),
*Normal*, and *Final* (full vvis, vrad with bounce and HDR as P2CE's defaults ask). Each ends with
*copy BSP to `maps`* and *run game*, both toggleable.

*Import* reads a `.wc` through `toolpp::CmdSeq` (any of its three formats, so Hammer++'s and the older
binary files too) and creates profiles with the same sequence names. The default offered path is
`<game>/hammer/cfg/cmdseq.wc`, from the profile. Import is a copy: there is no link back, and Apex
never writes a `.wc` that Strata Hammer will read. A second *Export* writes a Strata-flavour `.wc`
on request, so a profile built in Apex can be handed over.

Variables are expanded by `compile/`, from one table: `$gamedir`, `$path`, `$file`, `$bspdir`,
`$bsp_exe`, `$vis_exe`, `$light_exe`, `$game_exe`, `$postcompiler_exe`, and Apex's own `$addon`,
`$mapname` and `$work`. The names Hammer uses are kept so an imported file works unchanged. An unknown
variable is an error before the first step, never an empty string.

Accepted costs: a user who edits the sequences in Hammer afterwards must re-import. The alternative,
reading `cmdseq.wc` live, shares edits for free but ties the compile to a file Hammer owns and rewrites
(with the same wine-path drift as the addon list: addons.md §1.2), and gives Apex no place for its own
options.

An imported profile is a script: it can run any executable and delete files. Import therefore lists
the executables it will run, other than the known tools, and asks once per profile before the first
compile (Bite 5).

*What would reverse it:* owners editing sequences in Hammer often enough that re-importing is a chore;
then a "follow this file" option is added over the same import code, with the cost that conflicts are
Hammer's to win.

### D3: Tools are found from the game profile, per OS, and a missing tool is a named error before the first step

`GameProfile` gains `toolDirectory()`: `<root>/bin/linux64` on Linux and `<root>/bin/win64` on
Windows, where `<root>` is the folder holding the game directory (`p2ce/`). Each tool name maps to a
file (`vbsp`, `vvis`, `vrad`, `bspzip`, `vbspinfo`; `.exe` on Windows; the game is `p2ce.sh` on Linux
and `p2ce.exe` on Windows). A profile that names a tool by absolute path overrides the lookup. Only the postcompiler may be
absent (D13); every other missing tool is an error. The
runner sets the library path Valve's tools need on Linux (`LD_LIBRARY_PATH` to `bin/linux64`, as
`p2ce.sh` does), and passes `-game <gamedir>` itself unless the command already has it. The
resolution is checked for all enabled steps before the first one runs, so a missing `vrad` is reported
in the profile's header, not 40 seconds into a compile.

*What would reverse it:* P2CE moving the tools, or a second profile with tools in several roots.

### D4: A compile runs on a snapshot in a work directory, and its outputs are copied out by an explicit step

Apex writes the document (with the cordon filter, D7, if on) to `<cache>/compile/<mapname>/<mapname>.vmf`
using the same VMF writer as File → Save, runs every step with that as `$path\$file`, and the profile's
*copy BSP* step puts `<mapname>.bsp` in `$bspdir` (`<game>/maps`, or the addon's `maps`, D10). The
document need not be saved first, the user's own file is never touched by a compile, and the game
install is written to only by the copy step. This is the rule `tools/chamber_compile_check.py`
already enforces for CI.

The alternative, Hammer's, is to save to disk and compile in place beside the VMF. It is simpler to
explain, and every relative path in the VMF just works, but it forces a save on every compile, leaves
`.bsp`, `.prt`, `.lin` and `.log` files beside the user's sources, and cannot compile an unsaved map.

The cost is relative paths. `func_instance` files resolve from the VMF's own location and the
content search paths, so a snapshot in a cache directory can lose instances that sit beside the
source (Bite 3). 0.5.1's P0 measures it. The fallback is a collapsed snapshot (0.4 D9), which embeds
the instance geometry and fixups exactly as vbsp would, at the cost of compiling something that is
not the source.

*What would reverse it:* P0 showing the instance path cannot be reproduced for common layouts, or the
owner asking for compile-in-place (then the work directory becomes the VMF's folder, with a
`compile/` subfolder for outputs).

### D5: Log lines are parsed by a table of rules per tool, built from recorded logs, into diagnostics that carry object ids

`compile/` turns the merged output of each step into `Diagnostic { severity, tool, text, objects }`,
where `objects` are VMF ids: `Brush N` (a solid id), `Entity N` or `hammerid N` (an entity id), and
`Side N` where vbsp reports it. The parser is a list of rules (a regular expression, a severity, how
to read the ids) per tool, with a golden-log test for each rule. The logs come from real runs on the
Linux tools, captured in 0.5.2's P0 by compiling deliberately broken maps (a leak, an invalid brush, a
missing model, a duplicate `targetname` reaching an output, an unresolved instance, a vrad light
overflow), because a rule written from memory of Hammer's output will not match P2CE's.

Ids are looked up in the document at click time, not stored as handles: a diagnostic from a compile
of a snapshot may name an id that has since been deleted, which shows as *no longer in the map*.
Clicking selects the node, frames it in the viewport and, for a leak, hands off to D6.

The alternative is to treat the log as plain text with a regex highlight for "error". It is cheap
and shows the same text, but the exit criterion ("error → object mapping") asks for the click.

*What would reverse it:* a tool's output having no stable id in its error lines. Then that rule
degrades to text and the panel says so, rather than guessing from coordinates.

### D6: `.lin` and `.prt` are read by `compile/` and drawn as overlays that belong to a compile result, marked stale when the document changes

The leak file is lines of `x y z` points that make a path from the first entity to the outside. The
portal file is `PRT1` with a cluster count, portal count and for each portal its cluster pair and
polygon points. Both parsers are pure, tolerate truncation, and are checked against files the real
tools write in the work directory. The leak draws as a thick polyline with its start marked and
a *Go to leak start* command; portals draw as outlined polygons coloured by cluster, with a cluster
filter. Both use the 0.3 D16 overlay primitives; neither adds a render pass.

An overlay belongs to a `CompileResult` (a document revision stamp plus its work directory), so the
viewport can say *shown from a compile at revision N* and grey it once the document has moved. The
overlay never moves with edits: it is a record of what the compiler saw.

*What would reverse it:* portals becoming too many to draw as lines in the largest corpus maps; then
they draw only for the camera's clusters.

### D7: Cordons are edited and exported as Hammer does: a plural `cordons` block, several boxes, walls added at compile time only

`Cordon` becomes a box with a name and an `active` flag, read from the `cordons` block's children and
written back with unknown keys preserved. Cordon boxes draw in every viewport and are edited with a
drag-handle box (the 0.3 block tool's handles are reused, not a new tool; 0.4 D13 keeps the pie at
eight slots). *Select cordon from selection* sets the box to the bounds of the selection.

When the profile's *cordon only* option is on and a cordon is active, the snapshot (D4) holds only
nodes that touch an active cordon, and a closing set of six wall brushes in a profile-chosen material
is added to the snapshot, never to the document. Hammer does the same thing, so a map compiled in either
editor behaves alike. 0.5.4's P0 reads what Strata Hammer writes for a cordon compile on this host
(a probe, not a guess) and the wall rule follows it.

*What would reverse it:* the probe showing Strata Hammer's cordon compile differs from the above in a
way that changes compile results (for example, which entities count as touching).

### D8: "Check for problems" is one list over checks that already exist, run before every compile and on demand, and it fixes nothing by itself

A `Problem { severity, kind, text, objects, fixId? }` list is built by registered checks:
invalid or degenerate solids (0.3 D2's validity), missing assets (0.4 D11, including *missing models
as errors*), broken or unresolvable I/O targets (0.4 D6), duplicate `targetname` where a unique one is
required, unresolved or recursive instances, entities and brushes outside ±65536 (BSP v25's range,
research §1), empty brush entities, point entities with no `origin`, a missing `info_player_start`
or the game's equivalent (from the profile), and an active cordon that holds nothing. Severity
is *error* (the compile is likely to fail), *warning* or *note*. A pre-compile run shows the errors and
asks to continue; the panel keeps the list so the compile summary can show *problems before* beside
*diagnostics after*.

It doesn't compute leaks. A flood fill from entities through solids duplicates what vbsp does in a
second, and gets it wrong on `func_detail` and `nodraw` subtleties; vbsp's `.lin` is the leak report
(D6). A *fix* is an offered action (select, or open the right panel), not an automatic edit, in 0.5.

*What would reverse it:* the pre-compile run being slow on the largest corpus maps (then checks run
incrementally from the change set, like the other consumers in principle 4 of the roadmap).

### D9: Playing runs the profile's game command, detached, with `-map`; the log can be tailed, but Apex does not manage the game's life

The game step runs `$game_exe` with the profile's arguments, by default `-game <gamedir> -map <name>`
on Linux through `p2ce.sh` and on Windows through `p2ce.exe`. A campaign launch adds `-campaign
<bucket>/<id>` (D10). The process is started detached and its exit code ignored; the sequence is
done when the game has started. The game's console log (`-condebug`, as 0.5.6's P0 confirms) is
offered in a Game log view, with a *Reload map* command that re-runs the sequence. Apex does not
inject console commands, attach a debugger or track the game's window.

*What would reverse it:* wanting a two-way link (map reload on save, console commands) — that is a
plugin (0.9), or a separate milestone, not 0.5.

### D10: Addon parity is a pre-compile comparison and a warning; the addon target is a profile option; the scaffold writes only what the uploader needs

Before the first step, `compile/` compares the mount set the editor edits with (the `Vfs` addon list)
with what P1 (0.5.7's P0) found the tools read. If P1 shows `-mountmod <absolute path>` adds an addon,
the difference is passed that way. If not, Apex warns with the exact list of addons that differ and
the unmounted addon that would provide each asset the map uses (the 0.4 D15 hint). It never edits the
game's `addonlist.kv3` silently (addons.md D8).

An *addon target* is a profile option naming an addon folder: the snapshot is saved from the addon's
`mapsrc/`, the BSP is copied to its `maps/`, and the run command adds `-campaign addon:<folder>/<id>`
when the addon's `campaigns.kv3` has one. *New addon* writes `addon.kv3` in the uploader's format (as
seen in a real addon on this host, not remembered), creates `mapsrc/` and `maps/`, and a stub
`campaigns.kv3` only if asked. *Open in Workshop Uploader* starts `workshopgui` with the addon
selected if it accepts that, or just starts it. Apex does not upload, does not pack VPKs and does
not edit `campaigns.kv3` beyond the stub (addons.md D9).

The compile summary lists *addons this map uses* (addons.md D7) from `Vfs` provenance, with each
one's mounted state, computed on demand and not recorded in the VMF.

*What would reverse it:* P1 showing the tools read the addon list from a place Apex can write safely
(for example a per-game list under `-game`); then the comparison can become an automatic sync.

### D11: Create Instance from Selection writes a VMF with the selection and replaces it with a `func_instance`, in one transaction

Moved from 0.4 by the owner (2026-10-25). The command saves the selected nodes to a new VMF (0.4 D12's
writer, the prefab path) in the target folder (the addon's `mapsrc/instances` when D10's target is on,
else the profile's instances folder), recentres them on the selection pivot, and in one transaction
removes them and adds a `func_instance` at that pivot whose `file` is the path vbsp resolves from the
instance directory. It is undone as one step (0.1 principle 4). *Collapse* (0.4 D9) is its inverse,
and a test checks that selecting, creating and collapsing returns the original nodes, modulo ids.

It does not rewrite connections that cross the selection boundary: such connections would point into
an instance and are listed in a warning first (Bite 7).

*What would reverse it:* the boundary-connection rule being wrong for common maps; then a rewrite
through `instance` name prefixes is considered, as Hammer++ does, with 0.4 D9's fixup rules as the
spec.

### D12: A `compile/` layer depends on `core` only; the editor owns the session state and the UI owns the runner

`compile/` (Qt-free; includes `core` only) holds the sequence model, variable expansion, the special
commands, log rules and parsers, `.lin` and `.prt` readers, and the status machine. `editor/` gains
`CompileSession` (the current profile, the last `CompileResult`, diagnostics with document revision
stamps, problems) and the cordon operations. `ui/` gains the Compile panel (an area role, like Find),
the profile editor, the run command, the Problems panel and the overlays' toggles. `tools/check_layers.py`
adds `compile` with `["core"]` and lets `editor` and `ui` include it. The special copy and delete
commands go through a `FileOps` interface so tests never touch a real disk outside a temp directory.

*What would reverse it:* `compile/` needing `assets/` (for example to read `gameinfo.txt`). Then it
takes the paths as plain arguments from `editor/`, which already depends on both.

### D13: The postcompiler is an ordinary profile step; a missing executable is skipped with a warning

Hammer's config points at `bin/win64/postcompiler/postcompiler.exe`, and the game's `bin/linux64` on
this host has no postcompiler. So the postcompiler is not special in Apex: it is a step whose
executable is `$postcompiler_exe`, resolved by D3. When the executable cannot be found, the step is
marked *skipped*, the sequence continues, and the summary says which step was skipped and why (so a
Fast compile on a stock Linux install runs vbsp, vvis and vrad, and says the postcompiler did not
run). A user who has srctools' Python port or a wrapper sets the step's executable in the profile.
Apex ships no postcompiler, probes no Python environment and does not run Windows binaries under Wine.

Imported sequences keep their postcompiler step, so a profile moved between machines behaves per
machine. Every other tool in D3 stays a hard error when missing.

Accepted cost: default Linux compiles lack propcombine and the other HammerAddons transforms until the
user configures the step; the summary line is how that is made visible.

*What would reverse it:* a native Linux postcompiler shipping with P2CE (then D3 finds it and the
skip never triggers), or the skip causing maps to break in play often enough that failing is the
better default.

## 2. Where the seam goes

```
  app/        unchanged.                                                                    [Qt]
     |
  ui/         + QProcessRunner (D1); Compile panel, profile editor and import dialog (D2);   [Qt]
     |          Problems panel (D8); leak/portal toggles (D6); Cordons in the tool options
     |          (D7); Addons panel gains New addon and Open in Workshop Uploader (D10).
     |
  editor/     + CompileSession: profile, results, diagnostics, problems (D5, D8); cordon     [no Qt, no Vulkan]
     |          ops and the filtered snapshot (D7); addon target and scaffold (D10);
     |          Create Instance from Selection (D11).
     |
  viewport/   unchanged.                                                                    [no Qt]
     |
  render/     + overlay draws for a CompileResult's leak line and portals, cordon boxes.   [no Qt]
     |
  assets/     + GameProfile::toolDirectory and tool names per OS (D3).                      [no Qt, no GPU]
     |
  compile/    NEW: sequence model and variables (D1, D2); special commands over FileOps;    [no Qt, no GPU]
     |          log rules and parsers (D5); .lin / .prt readers (D6); status machine.
     |
  geometry/   unchanged.                                                                    pure
     |
  document/   + Cordon box and writer; cordon filter for a snapshot (D7).                   pure
     |
  core/       unchanged.                                                                    pure
```

`compile/` never starts a process and never reads the document: `editor/` hands it a snapshot path and
a profile, and `ui/` supplies the runner. The overlays are plain data (`std::vector<Vec3>` lines and
polygons) that `render/` draws without knowing where they came from.

## 3. Sub-milestones

Sub-milestones are numbered in the order they land. The release is the closing step, "0.5 release",
and is not numbered in advance (roadmap, Versioning).

## 5. Things that will bite

**1. The compile will run on stale or unsaved state.** A snapshot taken before the last edit (or a
queued compile starting after one) gives a BSP that does not match the viewport. Defence: the snapshot
is taken on the main thread at *Run*, carries the document revision, and every result, overlay and
diagnostic shows that revision; a result older than the document is marked stale.

**2. Cancel will not cancel.** `vrad` starts worker threads, and `p2ce.sh` is a shell that execs the
game: killing the immediate child leaves the rest running and writing to the work directory. Defence:
0.5.1's P0 measures it; the runner kills the process group (Linux) and a job object (Windows), and a
test starts a fake tool that forks.

**3. Instances will not be found from the work directory.** vbsp resolves a `func_instance` `file` from
the VMF's folder and the search paths. A snapshot in a cache folder compiles with a warning and no
instance, which looks like missing geometry. Defence: D4's P0 measurement; the diagnostic parser has a
rule for the unresolved-instance line; the fallback is the collapsed snapshot.

**4. Paths with spaces will break the argument string.** The Steam install is
`Portal 2 Community Edition`, and Hammer's `.wc` arguments are one string. Defence: the runner takes an
argument *list*; D2's expansion quotes at the tokenising step, and the test table includes the spaced
path on both OSes, and a Windows drive path in a Linux-imported file (Wine's `Z:\home\...`, as seen in
the addon list).

**5. An imported profile will run something the user did not mean to run.** A `.wc` from the internet
is a script with `delete` and `rename` commands. Defence: the first compile of an imported profile
lists its non-tool executables and special commands and waits for a yes; the special commands never
act outside the work directory, `$bspdir` and the addon folder (tested with a profile that tries `..`).

**6. Log rules will drift from the tools.** Rules written against one build's wording fail silently when
the text changes. Defence: every rule has a captured log; the CI stage compiles the planted-error maps
and fails if a planted error produces no diagnostic with an object id.

**7. Create Instance from Selection will break I/O.** Connections that cross the selection boundary
point at names that now live inside an instance. Defence: D11's warning lists them before the command
runs, and the round-trip test uses a selection with a crossing connection.

**8. A stale `.lin` will be shown for a fixed map.** vbsp leaves the old file when a later compile
succeeds. Defence: the work directory is emptied of outputs before each run, and an overlay belongs to
the `CompileResult` that produced it (D6).

**9. Cordon walls will end up in the document.** The walls exist only in the snapshot. Defence: the
filter works on the snapshot's copy of the VMF, and a test checks the document's revision does not move.

**10. The Windows path will not be tested until too late.** The tools differ in names, library paths,
line endings in logs and process termination. Defence: 0.5.1 and 0.5.6 each run their CI stages in the
Windows VM at their tags, not only at the release.

## 6. Sequencing

1. **0.5.1**, alone. Everything else needs the runner, the profiles and the snapshot.
2. **0.5.2**, then **0.5.3**. The overlays need a `CompileResult` and a work directory, which 0.5.1
   builds; they do not need the parsers, but 0.5.2's logs are the fixtures for 0.5.3.
3. **0.5.4** and **0.5.5** are independent of each other and of 0.5.3. They can land in either order
   after 0.5.2. 0.5.5 collects the 0.4 checks and wants none of 0.5.4.
4. **0.5.6** after 0.5.1 (any time after it). It is placed here so that 0.5.7's `-campaign` has a
   launch to extend.
5. **0.5.7** after 0.5.6. Its P0 (probe P1) needs the compile panel and can be done earlier by hand.
6. **0.5.8** last: it reuses 0.5.7's addon target for its destination folder, and carries the most
   risk of touching 0.4's collapse.
7. **0.5 release**.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-10-27. Each was presented with its alternatives, and each was
confirmed as the plan states it. They are recorded here with the alternatives turned down, so a later
reader does not reopen them without new information.

- **D4: a compile runs on a snapshot in a work directory.** Turned down: save and compile in place
  (Hammer's model), and a hidden snapshot beside the source. Revisit if 0.5.1's P0 shows relative
  `func_instance` paths cannot be reproduced for common layouts, or the owner wants compile-in-place.
- **D2: Hammer's `.wc` is imported once as a copy.** Turned down: following Hammer's file live, and
  built-in profiles with no import. Revisit if owners edit sequences in Hammer often enough that
  re-importing is a chore.
- **D13: a missing postcompiler is skipped with a warning.** Turned down: auto-detecting srctools'
  Python port, running the `.exe` under Wine, and failing the compile. Revisit if a native Linux
  postcompiler ships, or skipped transforms break maps in play often.
- **Sub-milestone order: cordons, validation, play, addons, Create Instance.** Turned down: play
  earlier, and addons earlier. Revisit if the playable loop is wanted for dogfooding sooner.
- **D1: `ProcessRunner` over `QProcess` in `ui/`.** Turned down: a Qt-free spawn wrapper in `compile/`.
  Revisit if 0.5.1's P0 shows `QProcess` leaves `vrad` workers or the `p2ce.sh` game alive on cancel.
- **D8: validation lists and selects; it fixes nothing.** Turned down: one-click safe auto-fixes.
  Revisit if the same few problems are fixed by hand on every map.
- **D7: cordon compiles add Hammer-style walls to the snapshot only.** Turned down: filter with no
  walls, and deferring cordon export. Revisit if 0.5.4's probe shows Strata Hammer's rule differs
  in a way that changes compile results.
- **D11: Create Instance from Selection stays in 0.5 (0.5.8).** Turned down: moving it to the start of
  0.6. Revisit if 0.5 runs long.
