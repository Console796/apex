# Apex: 0.2 implementation plan: Selection & manipulation

**Status: reviewed by the project owner, 2026-10-21. 0.2.1 (document write path:
D3, D4, D5, D17, D18) and 0.2.2 (picking index) and 0.2.3 (selection) and 0.2.4 (work planes and grid) and 0.2.5 (gizmos, modal transforms, preview) and 0.2.6 (clipboard, duplicate, delete, groups) have landed; 0.2.7 is next (0.2.11 viewport input polish is also planned).** Every decision in the appendix was put to the owner. Most draft choices were confirmed;
the review changed D8 (snapping is a user-selected mode, and Alt suspends snapping), D14 (the
marquee's enclosed/touching choice is a toggle) and D15 (a Blender preset with modal transforms
ships alongside the Hammer one).

Working plan for the milestone [roadmap.md](../roadmap.md) describes as:

> **0.2: Selection & manipulation.** Picking (BVH over faces, entities and models),
> object/face/solid selection modes, marquee/frustum select, gizmos (translate/rotate/scale,
> local/global, pivot) with snapping, surface-anchored grid and work planes, undo history panel,
> clipboard/duplicate/paste-special, groups, visgroups, hide/isolate, outliner (editable),
> FGD-driven entity property inspector, point-entity placement on surfaces, autosave + crash
> recovery.
> **Exit:** an existing map can be rearranged and its entity keyvalues edited entirely in 3D, and
> the result opens in Strata Hammer unchanged except for the edits.

This document does not supersede [research.md](../research.md) or the roadmap. Where they
disagree, those win, and 0.2.10 lists the amendments they need once 0.2 lands. Three decisions
change what 0.1 said:

- D4 changes 0.1 D8 from "a `Solid` stores a convex polyhedron" to "a `Solid` stores its VMF block;
  the polyhedron is derived through one function and written back through one transaction call".
  This records what 0.1.5/0.1.6 actually built, and keeps it.
- D18 changes 0.1 D7 from "modified nodes use `%g` with up to 6 significant digits" to "geometry
  numbers use the shortest round-trip form"; other values keep 6 digits.
- D7 pulls texture lock under transforms forward from 0.3 (roadmap) into 0.2.

0.2 also owes answers that 0.1 handed forward:

- **The "preview" channel for live drags** (0.1 D11): D6.
- **Undo memory under realistic editing** (0.1 D10, "measured at 0.2/0.3"): 0.2.10 measurements.
- **Handle resolution cost in hot loops** (0.1 D6, "profiling at 0.2"): the picking index (0.2.2)
  is the first hot per-frame consumer; measured there.
- **Apex-specific data that must survive Hammer** (0.1 D19): 0.2 adds none. Isolate and pinned
  work planes are session state (D11, D9), not file content.
- **`ViewContext` and `WorkPlane` have no consumers yet** (0.1 D15): every tool in 0.2 consumes them
  (D1, D9).

**What 0.2 inherits.**

- **`document::Document`** with arenas, generational handles, `NodeId`s that are stable across
  undo, `Transaction` (`create`, `destroy`, `reparent`, `setKeyValue`, `setSideKeyValue`), the
  undo stack with a memory cap, and one `ChangeSet` per commit. Undo of a destroy restores the
  same `NodeId` under a **new handle** (handles never revive).
- **Solids as VMF blocks.** A `Solid` node holds its whole `solid` block, sides included, as an
  immutable `kv1::Node`. Entities, groups and visgroups hold their own block with child blocks
  (`editor`, `connections`, nested solids) imported as separate nodes, `editor` becoming an
  `UnknownBlock` node.
- **`geometry::ConvexPolyhedron`** (`fromPlanes`, `fromPointData`, `validate`, `sourcePlanePoints`,
  `generateUv`, `uvAt`) and `matchFaces`.
- **The render mirror** (one mesh triple per solid and material, per-solid draw origin, entity
  boxes and sprites), rebuilt per ChangeSet, honouring `hidden { }` ancestry.
- **`viewport::ViewContext`, `WorkPlane`, `GridSettings`, `makeWorkPlane`, `cursorRay`**, built and
  unit-tested in 0.1.10 with no consumer.
- **Shell:** split-tree viewport area, read-only outliner (`OutlinerPanel::refresh()` rebuilds the
  tree), log console, status bar, theme tokens. `GpuHost` already observes the document.
- **`assets::EntityClassTable`** with name, type, bases, colour, size and `iconsprite` only.
  toolpp's `FGD::Entity` already exposes fields, choice fields, flag fields, inputs, outputs,
  descriptions and auto visgroups, so the inspector's data is one adapter away.
- **Local CI** (`tools/ci.py`), the P2CE corpus gate, lavapipe and RADV golden images, and the
  Windows VM (fixture-only, run at sub-milestone tags).

**What 0.2 does not have.**

- **No way to write geometry.** There is no transaction call that changes a solid's shape: the
  only side write is `setSideKeyValue`, which sets one scalar key and cannot touch `point_data`.
  Moving a brush therefore has no API. D4 adds one.
- **No way to edit a solid's `editor` block.** It lives inside the solid's block, and
  `setKeyValue` only sets top-level keys. Group and visgroup membership of solids is uneditable.
  D5 adds an API.
- **A latent bug in duplicate keys.** `setKeyValue` (via the internal `set`) replaces the *first*
  key with the given name. On an entity's `editor` node, adding a second visgroup with
  `setKeyValue("visgroupid", …)` overwrites the first membership, which is exactly 0.1's Bite 1.
  Nothing calls it that way yet; the visgroups panel will. D5, and the first P0 test.
- **A latent quadratic cost in bulk transactions.** `Transaction::touch` finds its delta with a
  linear search, and `create`, `destroy` and `reparent` each call `indexSides()`, which walks the
  whole document. Duplicating, hiding or deleting N objects is O(N²) and O(N × map) respectively.
  0.1 never did bulk edits; 0.2 does them constantly. D17, and a P0 benchmark.
- **A latent precision loss on write.** `vmf::Value::set(double)` formats with 6 significant
  digits. A brush rotated near x = 12345 is written to the nearest 0.01 and loses up to ~0.05
  units per vertex. That pushes its `point_data` past `kPointDataTrustEps` from its own plane, so
  the next load silently discards the exact vertices. D18, and a P0 test.
- **The mesher ignores `point_data`.** `render::meshSolid` builds from planes only
  (`fromPlanes`), while D8 says `point_data` is the source of truth when it agrees with the
  planes. Render, picking and transforms must see the same polyhedron. D4.
- **The grid is a horizontal plane only** (`render::GridSettings::planeZ`). A surface-anchored
  grid needs an arbitrary plane. D9.
- **No picking, no selection, no tools, no Edit menu, and undo/redo are not wired to the UI.**
- **No knowledge of how Strata Hammer persists "Hide", or what it puts on the clipboard.** The
  corpus shows that visgroup-hidden objects are wrapped in `hidden { }` blocks (below), but not what
  the H key writes. D11 and D12 depend on this; the 0.2.1 P0 probe checks it.

**Facts from the corpus that the design depends on** (512 P2CE `sdk_content` VMFs, scanned for
this plan):

| Fact | Count | Consequence |
|---|---|---|
| `group` blocks | 246 in 102 files | Groups are common and must survive every edit (D10). |
| `editor { "groupid" }` memberships | 1,355 in 101 files | Membership is a key, not nesting; groups are flat siblings in `world` (D10). |
| `hidden { }` wrappers | 1,038 in 64 files | Hide state is file content that Hammer writes (D11). |
| `"visgroupshown" "0"` | 824 in 50 files, all inside `hidden { entity { editor } }` in the file sampled | Hammer wraps visgroup-hidden objects in `hidden` (D11). |
| `visgroup` definitions | 165 in 82 files | The visgroups panel has real data to test against. |
| `connections` blocks | 1,637 in 286 files | Copy/paste and duplicate must carry I/O verbatim (D12). |
| Numbers in exponent form (`-1.90735e-006`) | 2,295 planes, 358 origins, 207 angles (205 files) | Hammer writes and reads exponents, with MSVC's three-digit exponent. Apex's parser accepts them already; D18's writer avoids them. |

## 1. Decisions

Each records what would reverse it.

### D1: Selection, picking, tools and gizmo math live in a new Qt-free `editor/` layer

`editor/` sits between `viewport/` and `ui/`. It holds the `Selection` model (D3), the
`PickIndex` (D2), the `Tool` interface and every 0.2 tool (select/transform, entity placement),
gizmo geometry and hit-testing, snapping, the clipboard codec (D12), the group and visgroup
indices (D10), the inspector's *model* (D13), and the autosave policy (D16). It links `document`,
`geometry`, `assets` and `viewport`, and uses no Qt and no Vulkan API.

A tool receives `apex::InputEvent`s with a `ViewContext` and produces three things: a selection
change, a `Preview` (D6), and at most one committed transaction per gesture. `ui/` turns Qt
events into `InputEvent`s, owns the widgets, and draws what `editor/` describes.

The reasonable alternative is Hammer's and TrenchBroom's shape: tools as Qt event handlers in
`ui/`, with picking in `render/` next to the meshes. Less plumbing, and the tool can reach any
widget. It's turned down because tool behaviour is the bug-dense part of an editor and must be
testable without a window: with `editor/`, a test replays "press at (412, 300), drag to
(500, 300) with Ctrl, release" against a corpus map and a scripted camera and asserts on the
written VMF. It also keeps the 0.9 plugin API's tool surface free of Qt.

Accepted cost: `editor/` defines its own input event, cursor and key types, and `ui/` translates
into them. `editor/` depends on `viewport/`, which links `render/` for camera matrices; that's a
link edge, not a GPU dependency, and the layer check enforces "no Vulkan headers in `editor/`".

*What would reverse it:* a tool that truly needs GPU results to decide what to do (for example
GPU-accelerated model triangle picking at 0.4). That goes through an interface `editor/` declares
and `render/` implements, not by moving tools.

### D2: Picking is a CPU BVH in double precision, not a GPU ID buffer

`editor::PickIndex` is a BVH over:
- every visible solid's faces (from the D4 polyhedron, leaf = face, carrying `NodeId` and
  `SideId`);
- every visible point entity's box (FGD size, or 8 units when unknown) and sprite quad;
- later, model triangles (0.4) and displacement triangles (0.8).

It's updated from ChangeSets (refit for modified nodes, rebuild for large changes) and answers:
`pick(ray) → {NodeId, SideId?, point, normal, t}` sorted by `t`; `frustum(planes, mode)` for
marquee selection; `nearest(ray, radius)` for snapping to vertices later (0.3).

The alternative is GPU ID-buffer picking: render object IDs into an R32 target, read back the pixel
under the cursor. It's pixel-exact for whatever is drawn, including sprites and thin wireframe
edges, and almost free to write given 0.1.9's offscreen target. It's turned down because:
1. it needs a device and a frame round-trip, so tool tests and headless tools can't pick (D1);
2. it only sees what's visible, while marquee select in Hammer includes occluded objects;
3. it gives no exact hit point or normal in double precision, which surface-anchored grids (D9)
   and entity placement (0.2.8) need at ±65536.

Accepted cost: building and refitting the BVH on load and per ChangeSet (`JobPool` for the
initial build), and a second visibility predicate that must agree with the mirror's (Bite 7).

*What would reverse it:* model triangle counts at 0.4 making CPU picking too slow to refit on edit.
Then models get a GPU or per-model BLAS path behind the same `pick()` interface.

### D3: Selection is editor state keyed by `NodeId` and `SideId`, outside the undo history; transactions record it so undo restores it

`editor::Selection` holds an ordered set of `NodeId`s (objects or solids, by mode) or `SideId`s
(face mode), the active (last-clicked) element, and the mode. It is not part of `Document`, so
selecting does not dirty the file or create undo entries.

Each undo entry records the selection *before* and *after* its transaction as metadata, and
undo/redo restore it. This is what users expect from Hammer ("undo the move" also puts the
selection back) without the cost of selection entries cluttering history.

Turned-down alternatives:
- **Selection changes as undo entries** (TrenchBroom). Exact, but Ctrl+Z after a few clicks walks
  back through selections instead of edits, and the history panel fills with "Select".
- **Selection fully independent of undo.** Simplest, but undoing a delete leaves the restored
  objects unselected and the user has to find them again.

Keyed by `NodeId`, not `Handle`, because handles never revive: undo of a delete recreates the
node under a new handle (Bite 1).

*What would reverse it:* the owner preferring TrenchBroom-style undoable selection. The metadata
already holds before/after selections, so that's a policy change in one place.

### D4: Solids keep their VMF block as storage; geometry is read through one function and written through one transaction call

0.1 D8 described a `Solid` that stores a polyhedron. 0.1.5 built a `Solid` that stores its
`solid` block, and 0.1.9's mesher derives the polyhedron per job. That turns out to be the right
shape for D7 (lossless, byte-identical untouched sides, unknown keys and `dispinfo` in place), so
0.2 keeps it and adds the two missing pieces:

- **`geometry::solidGeometry(const kv1::Node& solid) → Result<SolidGeometry>`** in one place: reads
  planes, `point_data` and texture attributes and builds with `fromPointData` (the D8 rule). The
  mesher, the pick index, transforms and validation all call it, so they see the same vertices.
  Today the mesher calls `fromPlanes` and ignores `point_data`.
- **`Transaction::setSolidGeometry(Handle<Solid>, const SolidGeometry&)`** writes each side's
  `plane` (three real vertices, Source winding), `point_data` (Strata profile), `uaxis`/`vaxis`
  (D7), and nothing else. Sides are matched to existing side blocks by `SideId`, so side order,
  unknown keys, `dispinfo` and untouched sides' bytes are preserved. A transform never adds or
  removes faces, so 0.2 does not need `matchFaces`; 0.3's clip and vertex tools do.

The alternative is to do what 0.1 D8 literally says: give `Solid` a `ConvexPolyhedron` value and
serialize sides from it on save. One derivation on load instead of one per consumer, and a typed
solid for tools. It's turned down for 0.2 because it means a second source of truth per solid that
must stay in sync with the block D7 writes back, for every key the kernel doesn't model, and it
reworks 0.1.5's snapshot and memory accounting. Derivation per consumer costs microseconds per
solid; a per-solid cache in `editor/` can be added if picking refits show up in profiles.

*What would reverse it:* profiling showing repeated derivation dominates (picking refit plus mesh
plus validation per edit), or 0.3's vertex tool needing a persistent topology across edits that a
block can't hold. Then `Solid` gains a cached polyhedron, invalidated by geometry writes.

### D5: The `editor` sub-block gets a typed membership API that handles duplicate keys

`Transaction::setEditor(NodeHandle, EditorEdit)` edits an object's `editor` block wherever it
lives (inline in a solid's block, or as the `UnknownBlock` child of an entity or group):
- `setGroup(optional<int>)`;
- `addVisgroup(int)` / `removeVisgroup(int)`, which append or remove *one* `visgroupid` entry and
  never touch the others;
- `setColor`, `setVisgroupShown`, `setVisgroupAutoShown`, `setComments`.

The ChangeSet flags are `Hierarchy` for group changes and `Visibility` for visgroup changes, on
the object node itself (not on an `UnknownBlock` child nobody observes).

Separately, the generic `setKeyValue` gains a documented rule: it refuses keys that occur more
than once in the block (`std::invalid_argument`), rather than silently editing the first.

The alternative is to make `editor` keys ordinary keyvalues and teach `setKeyValue` about
duplicates (an index argument, or "set all"). That leaks VMF's encoding of membership into every
caller, and the bug it invites is the one 0.1's Bite 1 names.

*What would reverse it:* a second block type that needs the same treatment (a third would make a
generic "multi-key edit" worth it). None is known in 0.2's scope.

### D6: A drag is a preview: tools publish a transient transform the mirror draws, and commit once on release

During a gizmo drag, the tool publishes `editor::Preview { map<NodeId, DMat4 transform>, … }`. The
render mirror draws each named solid and entity with that transform applied; the pick index and
the document are untouched. On release, the tool converts the same transform into one
transaction (`setSolidGeometry` per solid, `origin`/`angles` per entity), and the preview is
cleared in the same tick. Esc cancels with no document change. This is the "preview channel"
0.1 D11 promised, kept outside ChangeSets as D11 required.

The renderer gets a per-frame storage buffer of preview transforms (3×4 floats each, rebased
against the camera like the draw origin), addressed through buffer device address; a draw carries
an index into it in a spare push-constant word. The 128-byte push block is already nearly full,
so the matrix cannot go there.

The alternative is a live transaction: begin on press, write geometry on every mouse move, let
observers re-mesh, commit on release. Exact (texture lock, snapping and validity all shown as they
will be saved), and no renderer change. It's turned down because:
1. 0.1 D11 forbids observers from seeing intra-transaction state, so there's nothing to drive a
   redraw without breaking that rule;
2. re-meshing N solids per mouse move puts a whole-selection rebuild in the frame loop: dragging
   2,000 solids would re-mesh 2,000 solids at 60 Hz.

Accepted cost: the preview is a rigid or affine transform of the old mesh. With texture lock on
(D7) that's exactly what commit produces. With texture lock off the textures appear to move with
the brush during the drag and jump on release; that mismatch is accepted. A test asserts preview
vertex positions equal committed positions (Bite 9).

*What would reverse it:* a tool whose preview isn't an affine transform of existing meshes (the
0.3 vertex and clip tools). Those publish preview *geometry* through the same channel, meshed on a
job, which extends this decision.

### D7: Texture lock for translate, rotate and scale lands in 0.2, on by default

The roadmap puts "texture lock under transforms" in 0.3. Without it, every brush moved in 0.2
keeps its world-space texture axes, so the texture slides across the face. That's a visible edit
on every moved face, which breaks the 0.2 exit criterion ("unchanged except for the edits") in
spirit: a user rearranging a map would retexture it by accident.

0.2 implements the affine part: `uaxis`/`vaxis` are transformed by the linear part, and the
shifts are recomputed so the texel under each vertex is unchanged. A non-uniform scale either
scales the texture with the face (lock) or keeps texel density (Hammer's separate "scale lock",
off by default). A toggle in the toolbar and status bar turns lock off. Justify, fit, align and
the face-edit dialog stay in 0.3.

The alternative is to follow the roadmap and leave textures world-locked until 0.3. Less work in
0.2, but every 0.2 edit then needs redoing in 0.3, and the exit test has to exempt texture axes.

*What would reverse it:* 0.3's texture work needing a different representation of locked axes
(for example storing an un-locked base plus a transform). The 0.2 code is a pure function of
(old axes, transform), so that would replace one function.

### D8: Snapping has two user-selected modes, absolute (the default) and relative; holding Alt suspends it

A persistent **Absolute / Relative** toggle (toolbar and status bar, saved per user, bindable
through D15's registry) sets how every gizmo snaps:

| | Absolute (default, Hammer) | Relative |
|---|---|---|
| Translate | The bounds corner nearest the grab point lands on the work plane's grid, so off-grid selections become on-grid when moved. | The delta is a multiple of the grid, so off-grid offsets survive. |
| Rotate | The resulting angle about the gizmo axis lands on a multiple of the angle snap (15°; Shift: 1°), measured in the gizmo's frame. A prop at yaw 7° goes to 15°, 30°… | The rotation is a multiple of the angle snap (7° → 22°). |
| Scale | The scaled bounds land on the grid. | The size changes by multiples of the grid. |

For a brush in local mode the gizmo frame starts at the brush's current orientation, so the two
rotate modes coincide there; the difference matters for entities and global mode.

**Holding Alt suspends snapping** for the current drag (free movement, as in Hammer). The action
is `snap.suspend`, so a preset can bind it elsewhere. Grid sizes run from 0.125 to 1024 in powers of
two (Hammer++'s microgrid).

Both modes exist because each has real uses: absolute repairs off-grid content (a common source of
leaks and micro-gaps) and is what Source mappers expect; relative preserves intentional off-grid
alignment, such as precise imported geometry. The owner chose a user-selected mode over a single
fixed rule, and a persistent toggle over a momentary modifier, which keeps Alt for "no snap".

The gizmo has local/global orientation (local = the active object's basis, or the face normal
basis in face mode) and a pivot: bounds centre (default), active object's origin, or a
user-placed pivot point that persists for the session.

Turned-down alternatives: relative only (Blender, TrenchBroom's move tool) and absolute only
(Hammer); a momentary modifier for the other mode; separate toggles per gizmo mode (three settings
to display and forget).

*What would reverse it:* users finding the mode toggle confusing in practice (then the status bar
shows the mode more prominently, or the default changes), never a return to a single rule.

### D9: The grid is drawn on the active work plane, which follows the hovered surface unless pinned

`WorkPlane` comes from, in order: a **pinned** plane (the user pins the hovered face's plane, or
picks one of the six axis planes through the selection; Esc unpins); else the **hovered surface**
(the face under the cursor, with its in-plane axes from the face's dominant world axes, so the
grid lines stay world-aligned where the face is axis-aligned); else 0.1's fallback (`z = 0` in
perspective, camera-facing in axis-locked views).

The renderer's grid generalizes from `planeZ` to a plane (origin, normal, u/v axes) with the same
fade, and is drawn only on the face's bounds plus a margin when anchored to a surface, so it reads
as "this face's grid", not an infinite sheet through the map.

The alternative is a fixed ground grid plus explicit work planes only (Blender-like): less visual
churn as the cursor crosses faces. It's turned down because "draw on a surface" (0.3's block tool)
and "place an entity on a surface" (0.2.8) both want the hovered plane, and the research brief
names TrenchBroom's surface-anchored grid as the model.

*What would reverse it:* user testing in 0.2.4 finding the hover-anchored grid distracting. Then
anchoring happens only while a tool that uses it is active.

### D10: Groups stay flat VMF groups with `editor.groupid` membership; the group tree is a derived index

VMF groups are sibling `group` blocks in `world`, and membership is a key on each member's
`editor` block (a group can itself be a member of a group). Apex keeps exactly that encoding.
`editor::GroupIndex` maps group → members and object → outermost group, rebuilt incrementally
from ChangeSets (`Hierarchy` on the member, via D5).

Selection respects groups: clicking a grouped object selects its outermost group, unless "ignore
groups" is on (Hammer's Ctrl+W toggle). Group (Ctrl+G) creates a `group` block and sets members'
`groupid`; Ungroup removes one level.

The alternative is to make groups real document hierarchy, reparenting members under the `group`
node and translating back on save. Nicer for the outliner, but it moves blocks around on save,
which breaks D7's byte-identical output for every grouped object (1,355 memberships in the corpus).

*What would reverse it:* nothing short of a change to the VMF format.

### D11: Hide writes VMF `hidden { }` wrappers, like Hammer; isolate is session view state

Hide (H) moves the selected objects into a `hidden` wrapper block under their parent, in one
transaction; Unhide all moves them back out. It's undoable, saved, and Strata Hammer reads it.
The render mirror already treats a `hidden` ancestor as invisible. Visgroup visibility sets
`visgroupshown` (D5) and wraps or unwraps the members, which is what the corpus shows Hammer
doing (824 `"visgroupshown" "0"` keys, inside `hidden` blocks).

Isolate (a shortcut, or the outliner's solo toggle) is per-session view state in `editor/`: it
filters the mirror and pick index without touching the document, and is cleared by "show all".

The 0.2.1 P0 probe confirms what Strata Hammer's own H key writes. If it doesn't use `hidden`
blocks (for example if it uses `visgroupautoshown`), Hide follows Hammer's encoding instead, and
this decision's mechanism changes, not its intent.

The alternative is editor-only hide (session state, like isolate): hiding never dirties the file
and never reorders blocks. It's turned down because hide state then doesn't survive a reopen or a
trip through Strata Hammer, and the file's existing `hidden` blocks would still need handling.

Accepted cost: hiding moves blocks, so a hide/unhide pair is not byte-identical to the original
(the object comes back at the end of its parent's children). That is a real edit and is reported
as one.

*What would reverse it:* the P0 probe showing Strata Hammer does something else, as above.

*P0 result (Strata Hammer build 10773, under Wine, `probe-results/`):* confirmed, no reversal.
Hide wraps in place: a world solid becomes `hidden { solid }` between its siblings; a hidden brush
entity becomes a top-level `hidden { entity }` and its own solids are wrapped as well; a point
entity becomes a top-level `hidden { entity }`. Hiding a user visgroup does the same wrapping for
its members and also writes `visgroupshown "0"` in each member's `editor` block (the brush
entity's wrapped solid carries `visgroupshown "0"` without its own `visgroupid`; membership is on
the entity). Auto-visgroups hide the same way with `visgroupautoshown "0"`. The `visgroups` block
lists the user visgroup (`name`, `visgroupid`, `color`) and holds no membership.

### D12: The clipboard carries a VMF fragment as text; paste allocates fresh IDs and remaps references

Copy writes the selected objects as a VMF fragment (`world`-less sequence of `solid`, `entity`
and `group` blocks, plus a `visgroups` block naming the visgroups they belong to) to the system
clipboard under a custom MIME type and as plain text. Paste:
- allocates fresh object, side and group IDs (`Transaction::create` does this already);
- remaps `groupid`s inside the fragment to the new groups;
- maps visgroup memberships by *name* onto the target map's visgroups, creating missing ones;
- places the result at the cursor's work-plane position (Ctrl+V) or at the original position
  (Ctrl+Shift+V, "paste in place");
- keeps `connections` verbatim.

Paste Special adds copies, per-copy offset and rotation, grouping the copies, and making entity
names unique with a prefix or suffix (Hammer's dialog). Duplicate (Ctrl+D) is copy + paste in
place without touching the clipboard.

The alternative is an internal clipboard holding node values. Faster for huge selections, and no
serialization. It's turned down because text works across Apex instances and into a text editor
or a bug report, and the codec already exists.

*What would reverse it:* the P0 probe showing Strata Hammer puts a VMF-compatible format on the
clipboard, which would make cross-editor paste worth matching exactly.

*P0 result (partial):* with a solid copied in Hammer, the Win32 clipboard lists CF_TEXT,
CF_UNICODETEXT, CF_OEMTEXT, CF_LOCALE and two registered formats (ids 49215/49216, which Wine
names `TOOLBAR_CUSTOMIZE` and `TOOLBAR_CREATE`). Their bytes could not be read from a second
process: `GetClipboardData` returns null and the OLE data object refuses `GetData`
(`DV_E_FORMATETC`), so the content is undetermined. A paste inside Hammer does duplicate the solid, and a
paste in a native app shows nothing, so Hammer's clipboard is not a usable VMF text. Nothing
found reverses D12. The entity copy was not probed.

### D13: The inspector is generated from an extended FGD model, with a raw-keys view always available

`assets::EntityClass` grows the FGD data the inspector needs, copied from toolpp: per-property
name, type, display name, default, description, read-only flag, choices and flags, plus inputs
and outputs (stored now, edited at 0.4), all in **declaration order** across bases.

The inspector (`editor::InspectorModel`, drawn by `ui/`) shows:
- the class picker (changing class keeps all keys);
- typed rows in FGD order: string, integer, float, choices (combo), flags (checkboxes),
  `color255` (picker), `origin`/`angle` (vector fields with the gizmo kept in sync), `target_*`
  (autocompleted from the map's `targetname`s), `studio`/`material`/`sound` (text with a
  browse button disabled until 0.3/0.4 browsers exist);
- an "other keys" section for keys the FGD doesn't declare, which are never dropped;
- a raw mode (Hammer's SmartEdit off) listing every key in file order, with duplicates.

Multi-selection shows shared keys; differing values display as mixed and are only written when
edited. Every edit is one transaction; typing into a field coalesces into one undo entry per field
focus.

The alternative is a raw key/value table only, deferring the generated form. Faster to ship, and
no FGD adapter work. It's turned down because the roadmap names an FGD-driven inspector, and
flags and choices are where raw editing produces invalid maps.

*What would reverse it:* toolpp failing to preserve declaration order or base-class merging
(checked in 0.2.1 P0). Then the adapter parses order itself from the FGD text it already loads.

*P0 result (toolpp v2026.9.11, read from `FGD.cpp`/`FGD.h`):* it does **not** preserve declaration
order across kinds: plain fields, choices fields and flags fields go to three separate vectors
(`fields`, `fieldsWithChoices`, `fieldsWithFlags`) with no sequence index, and `getEntities()` is an
unordered map. It also does not resolve bases (`base(...)` stays an opaque `classProperties`
entry), and re-loading a class merges by field name. So the reversal applies: the adapter parses
property order itself from the FGD text, and keeps the existing base resolution in `assets/fgd.cpp`
(first base wins) extended to properties, with the key's first declaration position deciding order.

### D14: One picking rule in every display mode; repeated clicks cycle through depth; marquee selects enclosed objects including occluded ones

A click selects the nearest hit along the cursor ray (faces for solids, boxes and sprites for
entities), the same in wireframe and textured, ortho and perspective. A second click at the same
pixel (within 3 px, without moving the camera) selects the next hit behind it, so a brush
behind another one is reachable in a top view. Hovering shows the candidate with a highlight
before the click.

Marquee (drag on empty space, or with a modifier anywhere) builds a frustum from the rectangle and
selects objects whose bounds are **fully inside** it, occluded or not. A persistent **Enclosed /
Touching** toggle beside the selection-mode buttons (saved per user, bindable) switches to
"touching". It's a toggle rather than a modifier because Alt suspends snapping (D8), Ctrl toggles
and Shift adds; drag direction (the CAD convention) was turned down as invisible until learned.

The alternative for wireframe views is Hammer's 2D rule: a solid is picked by clicking near one of
its edges or its centre handle, and clicking inside a brush's outline does nothing. Familiar to
Hammer users, but it's a display-mode branch in a tool, against principle 1 and 0.1 D15, and it
makes clicks in a textured ortho view behave differently from a wireframe one.

*What would reverse it:* user testing showing depth cycling is too slow for dense ortho layouts.
Then edge proximity becomes a pick *priority* (an edge within 4 px beats a face hit), still
applied in every mode.

### D15: Two binding presets ship in 0.2, Hammer (default) and Blender, both through one action registry

`editor::Actions` names every command (`edit.undo`, `selection.mode.solids`, `view.hide`,
`snap.suspend`, …). A **preset** is a data table mapping actions to bindings; `ui/` builds menus,
toolbars and shortcuts from the active preset, and nothing binds a key directly. The preset is
chosen in settings and switches without a restart. A test checks that every action is either bound
or explicitly marked unbound in every preset (Bite 13).

**Hammer preset (default).** Follows Hammer where Hammer has a binding: Shift+S select, Shift+E entity
tool, Ctrl+T tie to entity, Ctrl+Shift+W move to world, Ctrl+G group, Ctrl+U ungroup, Ctrl+W ignore
groups, H hide, Ctrl+M transform dialog, `[`/`]` grid size,
Ctrl+Z/Ctrl+Y undo/redo. Unhide and isolate take Hammer's bindings where it has them; the
0.2.1 P0 checks the list against Strata Hammer's keyboard settings. Gizmo mode cycles with W/E/R only while the select tool is active
(Hammer has no equivalent; these match most 3D tools).

**Blender preset.** Blender's object-mode bindings (A select all, Alt+A none, B box select, H/
Alt+H/Shift+H hide, unhide, hide unselected, Shift+D duplicate, X/Delete delete, Ctrl+G group) and
**modal transforms**: G, R or S starts a transform from the current mouse position with no gizmo
drag; X/Y/Z constrains to an axis (pressed twice: local axis), Shift+X/Y/Z to the plane excluding
it; typed digits set an exact value; Enter or left click commits, Esc or right click cancels; Ctrl
held suspends snapping (Blender's convention, bound to `snap.suspend`). Modal transforms reuse the
gizmo's `editor::Transform`, snapping (D8) and preview channel (D6), so they commit identical
results. Camera navigation stays as built in 0.1.10, which already follows Blender's middle mouse.

The alternative is shipping only the Hammer preset and leaving others to the 0.9 keymap editor.
Less work, but the owner wants Blender users served from 0.2, and the modal transform is a tool
flow, not just a binding table, so it can't wait for a keymap editor anyway.

Accepted cost: a second binding table kept complete, and a modal transform tool in 0.2.5.

*What would reverse it:* the Blender preset going unused, in which case it stays as a data file
and stops gating CI on completeness.

### D16: Autosave writes full VMF snapshots to the user state directory; a session lock detects crashes

Every 5 minutes (configurable), and only if the document changed since the last snapshot, the
main thread serializes the document (`Document::write()`; its cost on the largest corpus map is
measured in 0.2.9) and a job writes it to `$XDG_STATE_HOME/apex/autosave/<map-name>-<path-hash>/<timestamp>.vmf`
(`%LOCALAPPDATA%` on Windows), keeping the newest 10. A lock file per open document records the
source path and the last snapshot; a clean exit removes it.

On startup, a lock file without a running owner means a crash: Apex offers to open the newest
snapshot (as an unsaved document pointing at the original path), discard it, or keep it for later.

Turned-down alternatives:
- **Snapshots next to the map** (`mapname.autosave.vmf`, as some editors do). Easier to find, but
  it litters version-controlled map folders and gets committed by accident.
- **A transaction journal** replayed on recovery. Loses at most one edit instead of five minutes,
  but every `NodeValue` must be serialized per commit, and a replay depends on bit-exact
  determinism of the base file and every transaction.

*What would reverse it:* users losing meaningful work within the interval. Then the interval
shortens, or the journal is added on top of the snapshots.

### D17: Bulk transactions are linear: indexed deltas and an incremental side index

`Transaction` keeps a `NodeId → delta index` map next to its delta vector, and the side index is
updated per created, destroyed or modified solid instead of rebuilt from the whole document
(the rebuild remains, used after undo/redo restores and checked against the incremental index in
debug builds). `ChangeSet` construction and undo restore stay linear in touched nodes.

There's no reasonable alternative to fixing this; the decision is that it's fixed *first*
(0.2.1), with a benchmark, before any bulk tool exists.

*What would reverse it:* nothing.

### D18: Geometry numbers are written in their shortest round-trip form; other values keep 6 significant digits

Plane points, `point_data`, `origin`, and `angles` written by Apex use `std::to_chars` shortest
round-trip formatting in fixed notation (no exponent), after snapping values within `1e-9` of an
integer to that integer, so `63.99999999999999` becomes `64` and `1e-07` becomes `0`. Other
numbers (light values, scales, user keys) keep 0.1 D7's `%g`-style 6 digits. Untouched values are
never reformatted (0.1 D7).

The alternative is 0.1 D7 as written: Hammer's 6 significant digits everywhere. Textually closest
to what Hammer writes, but it is the precision loss that produced the corpus's `15.9999` drift,
and it defeats `point_data` for any rotated brush away from the origin (P0 test).

Accepted cost: transformed geometry is written with up to 17 significant digits, so diffs of
rotated brushes are longer, and the 0.2.1 probe must confirm Strata Hammer parses them without
truncating.

*What would reverse it:* Strata Hammer failing to read long or exact values, or rewriting them on
load in a way that makes the precision moot. Then Apex writes the most digits Hammer reads.

*P0 result (`f_17_digits_saved.vmf`):* Hammer reads 17-digit planes and `point_data` without error,
but re-saves the whole file with 6 significant digits (`12432.425625842205` becomes `12432.4`), for
planes and `point_data` alike, and drops the file's leading `//` comment and adds the missing
worldspawn defaults. Saved planes and `point_data` are truncated identically, so the saved file is
self-consistent (maximum plane distance of its `point_data` is 7e-15), but the brush itself has
moved by up to about 0.05 units at x = 12345. The reversal condition does not hold: the loss
happens when Hammer saves, not when it loads, and Apex's own files stay exact until then. D18
stands. The `kPointDataTrustEps` tolerance exists for exactly this class of Hammer-written drift.

```
  app/        executable: startup, wiring.                                                    [Qt]
     |
  ui/         + Edit menu and toolbars built from editor::Actions; inspector, visgroups,       [Qt]
     |          undo history and editable outliner panels; Qt input → editor::InputEvent;

     |        snapping, Preview, GroupIndex, VisgroupIndex, clipboard codec, InspectorModel,
     |        Actions registry, autosave policy. Headless-testable against corpus maps.
     |
  viewport/   + WorkPlane sources (pinned / hovered / fallback), grid sizes 0.125–1024.     [no Qt]
     |
  render/     + preview transforms (BDA buffer), selection/hover tint and outline pass,      [no Qt]
     |          arbitrary-plane grid; mesher calls geometry::solidGeometry.
     |
  assets/     + EntityClass properties, choices, flags, IO, declaration order, auto visgroups. [no Qt, no GPU]
     |

     |          and texture lock (D7), generic BVH.
     |
  document/   + setSolidGeometry, setEditor (D5), duplicate-key guard, linear bulk ops (D17),  pure
     |          selection metadata on undo entries (D3), shortest-form geometry writer (D18).
     |
  core/       unchanged (InputEvent types live in editor/, not core/).                        pure
```

`geometry::solidGeometry` takes a `kv1::Node`, so `geometry` gains a dependency on `core`'s KV1
types only, not on `document`. The undo stack stores selection metadata as an opaque blob
(`std::any`-free: a `std::vector<std::uint64_t>` pair) so `document/` doesn't learn about
`editor::Selection`. `render/` learns nothing about selection semantics: it receives per-node
tint/outline flags and preview transforms keyed by `NodeId`. `tools/check_layers.py` gains the
`editor` layer and forbids `vulkan`/`volk`/`Q*` includes in it.

### 0.2.11: Viewport input polish (found while testing 0.2.6)

Three defects the owner found in the viewport panes. 0.2.6 shipped the first aid (lost-release
recovery, a global-pointer splitter drag, aligned quad bars with a crossing drag); this closes the
rest. It is numbered by arrival, not order: it lands before 0.2.10, which stays the release.

1. **Endless mouse look.** A middle-drag (orbit/pan) and a right-drag (fly look) keep turning
   while the pointer leaves the pane, for wide flicks, as Blender does.
   - *X11 (`xcb`)* already warps to the pane centre for fly look (`PaneWindow::warp`); extend it
     to the middle-drag and warp when the pointer nears the edge instead of every move.
   - *Windows* gets `SetCursorPos` through the same seam.
   - *Wayland*, where the owner works, has no warping at all (`QCursor::setPos` is a no-op). The
     only real answer is the `zwp_pointer_constraints_v1` lock plus `zwp_relative_pointer_v1`,
     the pair Blender uses: lock the pointer on press, hide it, take motion from relative events,
     unlock and restore the pointer on release, focus loss or Esc. Qt 6.10 exposes neither, so
     a small `ui/pointer_lock` seam reaches the `wl_display`/`wl_surface` through
     `QGuiApplication::platformNativeInterface()` and binds the two globals itself. The two
     protocol XMLs are vendored (the `wayland-protocols` package is not installed here) and
     `wayland-scanner` generates the glue at build time, Linux only.
   - Fallback when the compositor lacks the protocols: today's behaviour, with the 0.2.6 recovery.
2. **Sluggish splitter drag.** Each drag step resizes four native Vulkan windows, and each resize
   recreates the swapchain behind `vkDeviceWaitIdle` (`Swapchain::recreate`), from the 16 ms
   tick, in every pane, with FIFO present. Fix by decoupling: during a handle drag the panes keep
   their last frame (the compositor scales it) and the swapchain is recreated at most once per
   drag step interval (about 100 ms) and always at release; no `waitIdle` per step (retire the
   old swapchain through `oldSwapchain` and per-frame fences instead). Measure before and
   after with a frame-time log of a scripted 200-step drag.
3. **A bar stops short of the pointer.** Cause unknown, so the first task is a diagnosis, not a
   guess: log, per drag step, the global pointer position, the position asked of `moveSplitter`,
   the handle's resulting position and `QSplitter::getRange` (reached through a test subclass).
   Hypotheses, in order of likelihood: (a) a nested minimum size (a pane header, the 80x60
   container floor, or a native window's own size hints) clamps the range; (b) on Wayland the
   global position of events delivered to a child `QWindow` is relative to a different origin
   than the handle's, so the delta jumps; (c) the filter misses moves while a swapchain
   recreation stalls the loop, then applies a stale position. The fix follows the finding; if (b),
   drag from `QCursor`-independent per-window local coordinates mapped through the window
   that received the event.

**Tests:** the splitter tests from 0.2.6 keep passing; a drag test asserts the bar ends within
one pixel of the target whenever the target is inside the legal range, and at the range edge
otherwise (catches 3); a swapchain test counts recreations across a 200-step resize (at most
one per interval, plus the last); the pointer-lock seam is tested through an interface with a
fake backend (press locks, release/focus-loss/Esc unlocks, delta accumulation across a flick
wider than the pane); the Wayland binding itself is a manual check.

**Exit:** tests pass; on the owner's Wayland session a wide middle-drag flick keeps rotating and
the pointer reappears where it was on release; a quad splitter drag follows the pointer without
visible lag and reaches it.

## 5. Things that will bite

**1. Someone will store the selection as handles.** `Handle<Entity>` is right there in the
ChangeSet, and it works until the first undo of a delete, which recreates the node under a new
handle: the selection silently empties or, worse, points at nothing while the UI shows it
selected. Defence: `Selection` stores `NodeId`/`SideId` only, by type, and a test undoes a delete
and checks the restored objects are selected.

**2. Someone will edit `editor { visgroupid }` with `setKeyValue`.** It's the generic path and it
appears to work on objects with one visgroup. On the 49 duplicate-key blocks in the corpus it
drops memberships. Defence: D5's typed API, and `setKeyValue` throwing on duplicated keys (P0
test 1).

**3. A mirror transform will turn brushes inside out.** A scale with a negative factor (flip)
reverses every face's winding, and the written planes then point inward. It's tempting to
"fix" with a normal flip in the mesher. Defence: the transform function reverses face loops when
the determinant is negative, `validate()` runs on every committed solid in debug builds, and a
flip fixture is in the 0.2.5 tests.

**4. Entity rotation will be done on Euler angles directly.** Adding 90 to `angles`' yaw works
for upright props and fails for anything pitched or rolled. Defence: entity rotation composes
bases with `core/math`'s Source angle convention and converts back once; tests compare against
angle results recorded from Hammer for a set of compound rotations.

**5. Moving a brush entity will forget its `origin`.** Brush entities such as `func_door` and
`func_rotating` have an `origin` key that must move with their solids, or doors rotate about
the wrong point after a move. Defence: one function moves an entity (point or brush) and handles
`origin`, and the 0.2.5 test moves a `func_door` fixture.

**6. Bulk operations will be quadratic again.** A future convenience (`touch` with a search,
a whole-document reindex) creeps back into a per-object path. Defence: the 0.2.1 5,000-solid
benchmark stays in CI with its budget.

**7. Render and picking will disagree about what is visible.** The mirror checks `hidden`
ancestry; the pick index adds visgroups and isolate; a hidden brush becomes clickable, or a
visible one unclickable. Defence: one `editor::isVisible(document, node, viewState)` predicate
used by both, and a test that hides by every mechanism and then picks.

**8. A drag will commit on every mouse move.** It's the obvious way to make the view update, and
it floods undo history and sends a ChangeSet storm through every observer. Defence: D6's preview
channel, and `Transaction` asserting in debug builds when more than one gesture commit happens
between a tool's press and release.

**9. The preview and the commit will disagree.** The preview applies a float matrix on the GPU;
the commit applies snapping, texture lock and number formatting in double precision. A brush
that looked aligned during the drag lands a unit off. Defence: both derive from the same
`editor::Transform` value, and the 0.2.5 test compares preview vertex positions with the
committed solid's vertices for every gizmo mode.

**10. Paste will keep the source map's group and visgroup IDs.** The fragment's `groupid`s
then point at unrelated groups in the target map, or at nothing, and Strata Hammer reports or
silently fixes them. Defence: D12's remapping, and the cross-map paste test.

**11. Geometry will be written with Hammer's 6 digits.** The writer's default is the safe-looking
`%g`, and it passes every test that doesn't rotate brushes away from the origin. Defence: D18's
dedicated geometry formatter, and P0 test 3.

**12. The inspector will reorder or drop keys.** Rebuilding an entity's keys from the FGD
property list writes them in FGD order and loses undeclared ones, which shows up as a whole-entity
diff. Defence: the inspector only ever calls `setKeyValue` for the key the user edited, and the
0.2.8 test checks that editing one key changes exactly one line of the saved file.

**13. The two presets will drift apart.** A new action gets a Hammer binding and nobody adds it
to the Blender table, or a Blender binding shadows a Hammer-only one, so the feature is
unreachable in one preset. Defence: actions are declared once in the registry, presets only map
them, and a test fails when an action is neither bound nor explicitly unbound in each preset, or
when two actions share a binding in the same context.

## 6. Sequencing

1. **0.2.1** first, alone: its P0 tests and probe can change D4, D5, D11, D12, D13 and D18 before
   anything depends on them. The probe needs the Windows VM; run it once, early, and shut the VM
   down.
2. **0.2.2 → 0.2.3** serial: selection needs picking.
3. Then two tracks:
   - **Track A (manipulation):** 0.2.4 → 0.2.5. Serial: gizmo snapping uses the work plane.
   - **Track B (editing features):** 0.2.6, 0.2.7 and 0.2.8 need only 0.2.3, touch different
     files (clipboard and groups; panels and visibility; FGD and inspector), and can run in
     parallel. 0.2.8's placement step needs 0.2.4's work plane, so it integrates after it.
4. **0.2.9** is independent of everything after 0.2.1 and can be done whenever a track is idle.
5. **0.2.11** (viewport input polish) can go any time after 0.2.6 and before 0.2.10.
6. **0.2.10** last.

Merge order puts the pure layers first: nothing in `ui/` merges before the `editor/` model under
it has passed its headless tests.

## Appendix: decisions confirmed in review

The project owner reviewed these on 2026-10-21. Each was presented with its alternatives. Most
draft choices were confirmed; D8, D14 and D15 changed in review, and the D8 and D14 follow-ons
came out of those answers. They're recorded here with the alternatives turned down, so a later
reader does not reopen them without new information.

- **D1: a Qt-free `editor/` layer.** Turned down: tools as Qt handlers in `ui/` (Hammer-style),
  and a split with data in `editor/` but tools in `ui/`. Revisit only if a tool needs GPU results
  to decide what to do, and then through an interface, not by moving tools.
- **D2: CPU BVH picking in double precision.** Turned down: a GPU ID buffer, and a hybrid (GPU
  click, CPU marquee). Revisit if model triangle counts at 0.4 make refits too slow.
- **D4: solids stay VMF blocks, with one read function and one write call.** Amends 0.1 D8.
  Turned down: a cached polyhedron on the node, and the polyhedron as the source of truth.
  Revisit on profiles showing repeated derivation dominates, or if 0.3's vertex tool needs
  persistent topology.
- **D6: GPU transform preview, one commit on release.** Turned down: a live transaction with
  per-frame re-meshing (breaks 0.1 D11), and a ghost outline only. Extended, not reversed, by 0.3's
  non-affine previews.
- **D7: texture lock in 0.2, on by default.** Turned down: keeping it in 0.3 as the roadmap had
  it.
- **D8: snapping modes chosen by the user, absolute by default; Alt suspends snapping**
  (changed in review). The draft had absolute only, with Alt for a momentary relative drag.
  Turned down: a single fixed rule either way; a momentary modifier for the other mode; per-gizmo
  mode settings. Follow-on: absolute rotation lands on multiples of the snap in the gizmo frame;
  turned down: rotation always relative.
- **D11: hide writes VMF `hidden` wrappers, undoable; isolate is session state.** Turned down:
  editor-only hide, and saved-but-not-undoable hide. The mechanism follows Strata Hammer's
  encoding if the 0.2.1 probe shows it differs.
- **D18: shortest round-trip geometry numbers.** Amends 0.1 D7. Turned down: fixed decimals, and
  Hammer's 6 significant digits. Revisit if Strata Hammer can't read long values.
- **D14: nearest hit with click cycling in every display mode.** Turned down: edge priority
  everywhere, and Hammer's 2D edge rule in wireframe views. Follow-on (after Alt went to
  snapping): enclosed/touching is a persistent toggle; turned down: drag direction, and a
  Ctrl+Alt chord.
- **D15: Hammer (default) and Blender presets both ship in 0.2** (changed in review). The draft
  had a Hammer preset only, leaving others to the 0.9 keymap editor. Turned down: Hammer-only,
  and Blender-only.
- **D3: undo restores selection; selection changes are not undo entries.** Turned down:
  undoable selection (TrenchBroom), and selection independent of undo.
- **D16: full snapshots in the user state directory, with lock files.** Turned down: snapshots
  next to the map, and snapshots plus a transaction journal. Revisit if users lose meaningful
  work within the interval.
- **D12: VMF text fragments on the system clipboard.** Turned down: an internal clipboard.
  Revisit if the probe shows Strata Hammer's clipboard format is worth matching.
